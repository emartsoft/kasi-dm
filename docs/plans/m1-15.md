## 1. Scope and decisions

M1.15 builds the measurements behind Kasi's headline claim, speed parity with IDM (`KASI-NFR-001`), and the 1 Gbit/s target (`KASI-NFR-002`).

- **Gate (TPL 6.1.5, plan.md 4.2):** the median over all sources of (median Kasi time ÷ median IDM time) is at most 1.10, and no single source is worse than 1.25. Release uses 1.05 (M5.5).
- **There is no Kasi command line.** `Kasi.App` is an empty shell, so the Kasi side of every comparison is `Kasi.Bench throughput`, which drives `DownloadEngine` directly. Both tools are timed the same way: from the first request to a **verified** file (TPL 6.1.3).
- **Benchmarks are not tests and never run in PR CI.** They touch the public internet and need a quiet machine (CLAUDE.md rule 5 is about tests). The micro-benchmarks stay in BenchmarkDotNet and are compiled in CI so they cannot rot.
- **Owner items.** The capped origin and the range-less origin (a VPS), the signed cloud object (a bucket) and the IDM sessions on the benchmark machine are owner evidence. 15a ships local equivalents so the harness works without them.
- **If a target is missed,** the harness records the number, a profile and the controls (2.3), and the result feeds the "tuning sprint before M2" already in `plan.md`. A miss is a finding, not a failing build.

## 2. Design

### 2.1 Sources (`bench/sources.json`)

One entry per TPL 6.2 archetype: `id`, `type`, `url`, `sizeBytes` (when known), `purpose`, `owner` (who maintains the URL) and `placeholder` (true until the owner replaces it). The six archetypes are the East Africa mirror, the European mirror, the CDN file, the cloud object (signed URL), the capped origin and the range-less origin. The file does not contain fake hosts presented as real: placeholder entries are marked and **skipped with a message**, never fetched. A `local` section lists the TestServer equivalents (`/files/…`, a throttled chaos profile for the capped origin, a range-less endpoint) that 15a runs end to end. The file is reviewed monthly (TPL 6.2). No URL with a query or credentials is stored or logged (CLAUDE.md rule 3).

### 2.2 `Kasi.Bench` modes

`Program.cs` routes: no arguments or `--filter` runs BenchmarkDotNet (existing); `throughput`, `local-1gbit`, `resources` and `compare` are the new modes. The micro-benchmarks stay where they are.

- `throughput --sources bench/sources.json --connections 8,16 --runs 5 [--local]` downloads each non-placeholder source with `DownloadEngine`, once per connection count and run, and writes one result row per source and connection count.
- `local-1gbit` starts `Kasi.TestServer` **as its own process** and downloads 4 GiB over 16 connections.
- `resources` samples the bench process (see 2.4).
- `compare <old.json> <new.json>` implements TPL 6.4 (2.5).

### 2.3 The 1 Gbit/s check and its controls (`KASI-NFR-002`)

- The server runs in a separate process, so Kestrel's byte generation does not compete with the engine for the same cores.
- **Controls:** a raw `HttpClient` run with 16 parallel range streams against the same server gives the ceiling of machine plus server; the engine result is reported with that ceiling and as a percentage of it.
- **What is timed:** first request to the sealed part file renamed to its final name. The SHA-256 check is done afterwards and reported separately, so hashing time is not charged to throughput; the hash must still match.
- **Pass:** at least 125 MB/s sustained (the median of three runs), and the SHA-256 equal to the generated content. **If the control itself is below 125 MB/s** the machine cannot judge the engine; the report says so and the check is marked inconclusive, not failed.

### 2.4 Resource sampling (`KASI-NFR-004`, `KASI-NFR-005`)

`ResourceSampler` reads private working set and processor time every 500 ms. These are **engine-only early signals**: NFR-004 and NFR-005 are about the whole app, and the real gate is M2 and later. The server is out of process, so its memory and CPU are not counted. Three scenarios: an idle engine with no jobs for 10 minutes (private working set < 80 MB), 20 concurrent active downloads (peak < 250 MB), and about 100 MB/s aggregate (CPU < 5% of one core over the window). The 10-minute idle run is not part of a PR build.

### 2.5 Result schema and regression tracking (`bench/results/*.json`)

One file per session: `schemaVersion`, `startedUtc`, `machine` (CPU, RAM, OS build), `lineSpeedMbps` (reference speed test, TPL 6.1.1), `window` (`business` or `night`, TPL 6.1.4), `dnsFlushed` (true for IDM comparison sessions), tool versions, and rows of `{source, connections, run, tool, seconds, bytes, mbps, peakConnections, sha256Ok}`. `compare` reads two files, prints the median change per source and **flags a throughput drop of more than 5% or a memory increase of more than 10%** against the previous session (TPL 6.4). The weekly run itself needs the dedicated machine, so the workflow is `workflow_dispatch` plus `schedule` on a self-hosted label, `main` only and never `pull_request` (same rule as the power-cut workflow); opening the High defect stays manual until M1 closes.

### 2.6 IDM comparison (`bench/Compare-Idm.ps1`, 15b)

1. Check that IDM (`IDMan.exe`) and a Release build of `Kasi.Bench` exist.
2. For each non-placeholder source and each connection count (8, then 16): warm the DNS, then `Clear-DnsClientCache` before every run; alternate IDM and Kasi five times each.
3. **IDM:** `IDMan.exe /d <url> /p <folder> /f <name> /n /q` only queues the download and returns, so the script waits by polling the target file until it reaches the expected size and stops growing, then verifies the SHA-256 (or the size when the source publishes no hash). Wall-clock is from the call to that verified file.
4. **Kasi:** `Kasi.Bench throughput --one <source> --connections <n>`, timed the same way.
5. Result per source is median Kasi ÷ median IDM; the scorecard shows the median of all sources and the worst source against the 1.10 and 1.25 limits and writes `bench/results/idm-comparison-<date>.json` plus a Markdown scorecard. A source that fails verification for either tool is excluded and listed, not silently dropped.

## 3. Verification

- **15a (automated):** result-schema round trip; `compare` unit tests on canned files (a 6% drop flags, a 4% drop does not; memory 11% flags); `sources.json` loader skips placeholders and rejects entries with a query string; `local-1gbit` with a small size (64 MiB) as a smoke test, with a loose bar on a shared CI runner (the smoke checks the pipeline and the SHA-256, not the number); the micro-benchmarks compile in CI. A full 4 GiB run on the developer machine is recorded in the PR.
- **15b:** the scorecard generator on canned alternating data (median and worst-source arithmetic, an excluded source); `Compare-Idm.ps1` dry run with a fake `IDMan.exe` script that copies a file after a delay, proving the completion polling; the PowerShell parses.
- **Owner evidence:** the real IDM sessions at two times of day on the benchmark machine, with the line speed recorded, and the weekly session. The M1.15 row in `plan.md` is marked ✅ when 15b merges, with these named as outstanding evidence for the gate, as for M1.14.
- Build, full tests and `dotnet format --verify-no-changes` for each PR.
