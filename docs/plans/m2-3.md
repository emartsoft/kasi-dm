## 1. Scope and decisions

M2.3 creates the TypeScript Manifest V3 codebase that M2.4 (interception) and M2.5 (popup, menus, picker) build on. It contains no interception logic yet.

- **One codebase, two bundles (`TRD 9.1`, `NFR-015`).** `dist/chromium` (a background **service worker**) and `dist/firefox` (a background **event page**, `background.scripts`) from the same sources, through `webextension-polyfill`. Chrome and Edge share the Chromium bundle.
- **Build per entry, not one build for everything.** Content scripts cannot be ES modules, so the content script and the background are built as IIFE bundles; the popup and options are HTML entries. A small `vite.config.ts` loops over the entries and the two targets and writes each manifest next to its bundle. Minimum versions are stated in the manifests: `minimum_chrome_version` and, for Firefox, `browser_specific_settings.gecko` with an add-on id and `strict_min_version` (the Firefox version that supports MV3 event pages with the permissions below); the exact numbers are set in 2.3a from the browsers' release notes and recorded in the ADR with `NFR-015` (latest three Chrome and Edge, latest Firefox and ESR).
- **The schema is the single source (`TRD 9.4`).** `npm run generate:types` runs `json-schema-to-typescript` on `docs/protocol/kasi-messages.schema.json` and writes `src/types/protocol.ts`. Two separate guards, named for what they actually check:
  - **schema → TypeScript:** `npm run check:types` regenerates and fails on a diff.
  - **C# ↔ schema ↔ TypeScript:** both test suites validate the same files in `tests/fixtures/ipc` (M2.1). Vitest validates every valid fixture and rejects every invalid one with Ajv against the schema; the C# side deserializes the same files. A change on one side without the other fails a suite.
- **Service worker lifetime.** A Chromium worker is stopped when idle, so nothing important lives in memory: the rules Kasi pushes are cached in `storage.local`, and the native port manager reconnects on disconnect with backoff and sends `hello` again each time.
- **Permissions (`TRD 9.1`)** are identical in both manifests: `downloads`, `cookies`, `webRequest`, `contextMenus`, `nativeMessaging`, `storage`, `scripting` and host permission `<all_urls>`. Firefox 127 and later show MV3 host permissions during install, but the user can deny or revoke them; the popup and options gain a permission-request step ("Allow Kasi on all sites") in 2.3b and show "needs permission" until granted. This is exercised in M2.4's tests.
- **Options page (decided).** The TRD says the options page "opens Kasi's settings" but TRD 9.4 had no message for it. The protocol gains **`openSettings`** (extension → Kasi, `ack` reply; added with the schema in M2.1a, which also updates TRD 9.4 and ADR 0016). The alternative, a `kasi://` URL handler registered by the installer, was rejected because nothing new would have to be registered on the machine. 2.3a ships the page with a request typed from the schema and a disconnected state. 2.3b connects that request through the native port manager; the end-to-end open is verified in M2.4/M2.5 with a registered host.
- **Logging (CLAUDE.md rule 3).** A redacting logger never writes query strings, cookies, headers or tokens; its tests prove it for URLs, cookie arrays and error objects.
- **Tooling.** ESLint 9 flat config with typescript-eslint strict, Prettier, TypeScript `strict`. `package-lock.json` is committed, Node is pinned (`.nvmrc`, `actions/setup-node` with npm caching), and `npm ci` is the only install in CI.

## 2. Design

```text
extension/
├── package.json  package-lock.json  .nvmrc  tsconfig.json  eslint.config.js  .prettierrc
├── vite.config.ts                  per-entry, per-browser build; writes manifest.json into each dist folder
├── manifests/
│   ├── manifest.base.json          the shared parts (permissions, icons, action, options)
│   ├── manifest.chromium.json      background.service_worker, minimum_chrome_version
│   └── manifest.firefox.json       background.scripts, browser_specific_settings.gecko
├── scripts/generate-types.ts       schema -> src/types/protocol.ts
├── src/
│   ├── background/index.ts         creates the native port manager, answers nothing yet (M2.4 adds interception)
│   ├── content/index.ts            empty entry, registered for the overlay and the picker (M2.5)
│   ├── popup/                      connection status and the Firefox permission request
│   ├── options/                    sends openSettings; shows the connection state when Kasi is unreachable
│   ├── shared/
│   │   ├── native-port.ts          connectNative("com.martsoft.kasi"), reconnect with backoff, hello on every connect, request/ack by id with a 2 s timeout
│   │   ├── rules-cache.ts          the pushed rules in storage.local
│   │   └── logger.ts               the redacting logger
│   └── types/protocol.ts           generated, committed, never edited by hand
└── tests/
    ├── unit/                       Vitest
    └── browser/                    smoke harness (nightly, see section 3)
```

## 3. Verification

- **PR CI job (Windows, new in `ci.yml`):** `npm ci`, `npm run lint`, `npx prettier --check .`, `npm run check:types`, `npm test`, `npm run build`, and a check that both `dist/chromium/manifest.json` and `dist/firefox/manifest.json` are valid (required keys, the right background form, identical permissions). No browsers are installed in this job.
- **Vitest:** the protocol fixtures against the schema with Ajv (valid accepted, invalid rejected); the native port manager with a fake `runtime.connectNative` (hello on connect and on every reconnect, backoff, ack timeout, ordering); the rules cache; the logger redaction (URLs with queries, cookies, nested error objects); the manifest checks as unit tests.
- **Browser smoke (nightly or manual workflow, not PR CI):** Playwright with a persistent **Chromium** context loads `dist/chromium` and checks that the popup renders the "not connected" state. **Firefox is not driven by Playwright** (it cannot load extensions); the Firefox smoke uses `web-ext run` or geckodriver's `installAddon` with the same check. These need `playwright install` and a Firefox build, which is why they run outside the PR job. They run against a registered native host in M2.4.
- **Mutation checks:** change the schema without regenerating (the drift guard fails); make a fixture the C# side accepts but the schema rejects (a Vitest case fails); log a URL with a query string (the redaction test fails).
- Format and lint are the CI gate for the extension, as `dotnet format` is for C#.
