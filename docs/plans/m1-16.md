## 1. Scope and decisions

M1.16 adds the CI that closes the M1 engine gate (plan.md 4.2, TPL 4). Fault injection already runs nightly (M1.14); this milestone does not repeat it.

- **Measure before gating.** The 80% gate (`KASI-NFR-018`) must not turn every PR red on the day it is switched on. 16a first records the current `Kasi.Engine` line coverage; if it is under 80% the PR adds the missing tests (or, only if that is out of proportion, a documented ratchet at the current value that rises to 80%, agreed with the owner).
- **Skipped is not passed.** The M1.14 suites report `SKIPPED` with exit code 0 when they cannot run (no elevation, no Toxiproxy daemon). A green workflow therefore does not prove every suite ran, and the gate check reads the reports.
- **Linux-only tools run on the Ubuntu leg.** Docker containers and libFuzzer need Linux; the Windows legs stay as they are.

## 2. Design

### 2.1 The coverage gate (16a, `KASI-NFR-018`)

- `ci.yml` already merges unit and integration coverage into ReportGenerator output. Add the `Cobertura` report type's merged file and a step that reads the `line-rate` of the `Kasi.Engine` assembly from that XML (not a regex on the Markdown summary), fails the job below 0.80, and writes the figure to the job summary.
- The gate script is a small PowerShell file under `build/` that takes the Cobertura path and a threshold, so it can be tested.
- Pull requests that lower engine coverage below 80% are blocked; the CI header comment ("switched on in M1") is updated.

### 2.2 Ubuntu container conformance (16b, `TC-ENG-019`, `TC-ENG-022`)

- New workflow `.github/workflows/ci-conformance-linux.yml` on `ubuntu-latest`, where Docker is available; it builds the solution projects the container tests need and runs `Category=ContainerIntegration`. It runs on `pull_request` (it needs no secrets) and on `main`.
- **Filters.** The Windows job's unit step is `Category!=Integration`, which would pick up a test tagged only `ContainerIntegration` and fail without Docker. Container tests carry `Category=Integration` **and** `Category=ContainerIntegration`, and both Windows steps add `&Category!=ContainerIntegration`, so they run only on Ubuntu.
- **Reuse, don't duplicate.** The existing proxy, FTP and FTPS test classes already assert the behaviour against in-process servers. The container tests run the same scenarios against the container endpoints (a shared base class taking the endpoint), so there is one set of assertions and two kinds of server.
- Containers, each **pinned by digest** and named in the ADR with its licence: vsftpd (passive range 21100 to 21110, authenticated user, explicit FTPS with a test certificate), Squid (HTTP forward proxy and `CONNECT`), Dante (SOCKS5 with username and password).
- Checks: a 16 MiB segmented download with SHA-256 through each; `REST` resume after a dropped connection on vsftpd; certificate chain verification for FTPS against the test CA; a proxy that requires credentials rejects wrong ones. The 1 GiB runs of TPL 5.1 stay nightly evidence, not PR time.
- Image pulls reach Docker Hub; that is accepted for Testcontainers (CLAUDE.md rule 5 names it), and the digests keep the runs repeatable.

### 2.3 Nightly fuzzing (16c, `TC-ENG-004`, `TC-ENG-005`, TPL 7.2)

- `FileNameFuzzTests.FuzzTarget` is `internal` in the test assembly and cannot be fuzzed from there. 16c adds a small `tests/Kasi.Fuzz` executable that references `Kasi.Engine` and calls the filename parser through one `FuzzTarget(ReadOnlySpan<byte>)` entry point (the test class keeps using the same method, moved or shared, so there is one invariant check).
- `.github/workflows/nightly-fuzz.yml` on Windows (libFuzzer runs natively there; ADR 0015): build, instrument `Kasi.Engine.dll` with the `sharpfuzz` tool, run libFuzzer through the pinned `libfuzzer-dotnet` build on the seed corpus built from `tests/fixtures/disposition-corpus/seeds.txt` and the saved findings in `tests/fixtures/fuzz/crashes/`. **Budget 3 minutes**, as TPL 7.2 gives the filename parser (the other targets belong to later milestones). Schedule plus `workflow_dispatch`, `main` only.
- **On a finding** (a crash, a hang over 2 s, or an allocation over 256 MB): the workflow fails, minimises the input with libFuzzer's `-minimize_crash`, uploads it as an artifact, and the owner adds it to `tests/fixtures/fuzz/crashes/` as a regression case and files a High defect (TPL 7.2). The seed-corpus run and the checked-in crash corpus also run as ordinary unit tests on every PR, so a fixed bug stays fixed.

### 2.4 The gate check (16c, `build/Check-M1Gate.ps1`, TPL 4.2)

One script covering the six gate criteria, with the three-nights logic inside it (it cannot be fully exercised until three nights exist, so its logic is tested on canned data).

1. **P1 test cases:** read the trx or a list of `TC` traits from the last `main` CI run and report any `TC-ENG-001` to `024` or `TC-RES-001` to `012` with no passing test. Cases owned by owner evidence (power cut `TC-RES-003`, sleep) are listed from a small evidence file, not guessed.
2. **Three consecutive nights:** `gh run list` for `nightly-faults.yml` on `main` with `event=schedule`, the last three runs must have concluded `success`, **and** each run's uploaded `summary.md` files must contain no `SKIPPED` leg and no `FAIL`. A skipped leg fails the check with its reason.
3. **Benchmark median** from the latest `bench/results/idm-comparison-*.json` (M1.15): median ratio at most 1.10, worst source at most 1.25; missing file means the criterion is open.
4. **Coverage:** the figure from the latest `main` CI run (2.1).
5. **Open Critical or High defects:** `gh issue list` with the agreed labels.
6. **Report:** a Markdown gate report with the build number and links to each piece of evidence, written to `artifacts/` and attached to the workflow run for the owner's sign-off.

Mutation check: break the `REST` offset in the FTP transfer and confirm the vsftpd test fails.
