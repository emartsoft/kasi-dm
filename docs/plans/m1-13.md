## 1. Scope and decisions

`DownloadEngine` is the headless entry point that owns what the M1.8 to M1.12 runners deliberately left open: the job state machine, persistence of every transition, recovery after a crash, and job-level pause, resume and restart. It runs one job per call to `HttpTransferRunner` (HTTP) or `FtpTransferRunner` (FTP); queues, scheduling and the tray are M2.

Decisions taken after review:

- **The database is the truth and a transition is atomic.** A transition is a compare-and-set in SQLite (`WHERE state = @from`); the event is raised only after it committed. A whole-row `UpdateAsync` is never used for a state change, because it would overwrite `done_bytes` written by the checkpoint writer in the meantime (the reason M1.9 added targeted updates).
- **Recovery edges are explicit.** The normal state machine is not loosened; recovery uses its own named edges (13a).
- **Why a job is paused is stored**, so that after a restart the facade resumes only the jobs that were paused for the network, never one the user paused.
- **No new job state.** Cancel is removal (`JobRemoved`); "Retrying" stays unused until the runner reports retries.
- **Out of scope:** queues and concurrency limits (M2: each started job runs), media and torrent kinds (rejected with a clear error), the UI, power-cut and reboot harnesses (M1.14).

## 2. Design

### 2.1 13a — Transitions, recovery edges and the core facade

- **`JobStateMachine` recovery edges (ADR 0002 updated, every edge unit-tested):** a separate `RecoveryNextStates` used only by start-up recovery: `Probing` to `Queued`, `Downloading` to `Paused`, `Retrying` to `Paused`, `Verifying` to `Paused`. Normal `CanTransition` is unchanged.
- **`IJobRepository.TryChangeStateAsync(id, from, to, error, pauseReason, ct)`** returns whether the row still had state `from` and changed it; one SQL statement that also sets the error text, the pause reason and the timestamps. A second, smaller member writes `done_bytes` reconciliation after recovery. A new migration adds the `pause_reason` column (nullable text).
- **`PauseReason`** (`UserRequested`, `NotEnoughSpace`, `NetworkOffline`, `CrashRecovery`, `CheckpointFault`) is stored in that column and shown as the job's message.
- **Events:** `JobStateChanged` (exists), `JobProgressed` (throttled, produced from the scheduler tick and the checkpoint), new `JobRestarted(JobId, Reason, DiscardedBytes)`. Events go through a bounded `Channel` read by one dispatcher, so a slow or throwing subscriber cannot block a transition; a subscriber exception is caught and counted.
- **`DownloadEngine`** (`src/Kasi.Engine/DownloadEngine.cs`): constructor takes the repositories, `ICheckpointWriter`, an optional `IJobSecretRepository`, the shared `BandwidthLimiter` (per-job `JobBandwidthLimit` built from `speed_limit_bps`), `ProxySettings`, `TimeProvider`. `StartAsync` runs recovery before it accepts any call; `StopAsync` pauses every running job with a final checkpoint (RES-001: flush on pause and shutdown). One lock per job id serialises actions on that job; a job's transfer runs under its own `CancellationTokenSource`.
- **Dispatch by kind:** `JobKind.Http` and `JobKind.Ftp`; Media and Torrent are rejected. The runner owns secret deletion on completion (it already does); the facade does not delete it a second time.
- **`AddJobAsync` uses `DuplicateDetector` (M1.12a)** and returns the conflict to the caller instead of adding a duplicate; the caller passes the chosen resolution.
- **Start-up recovery (`CrashRecovery`)**, for each job left in `Probing`, `Downloading`, `Retrying` or `Verifying`:
  - final file present with the expected size and no `.kasipart`: `Completed` (checksum re-verified when one is set);
  - `.kasipart` present with matching length and valid segment rows: `done_bytes = SUM(written)`, then `Paused` with `CrashRecovery`;
  - part file missing, or segments inconsistent with it, or a non-resumable job: reset segments and progress, `Queued`;
  - `Probing`: `Queued`;
  - `Verifying`: finalise the already sealed part file through the runner (resume with complete segments must seal-check, verify and commit with no lease; if the runner cannot do that today, 13a adds the entry point), then `Completed`, or `Failed` with "Verification failed".
  - Before any of this, `PRAGMA quick_check` on the database (`TC-RES-011`); a failure is reported and no job is touched.

### 2.2 13b — Pause, resume, disk full, offline, link refresh

- **Pause, cancel and shutdown are different cancellations:** pause cancels the runner, waits for its final snapshot and checkpoint, then `TryChangeStateAsync(Downloading, Paused, UserRequested)`; cancel stops the runner and removes the job (the files are deleted only when asked); shutdown pauses everything. The runner's `Cancelled` outcome is mapped using the reason the facade recorded, not guessed.
- **Disk full (`TC-ENG-015` job half):** `DiskNotEnoughSpace` pauses the job with `NotEnoughSpace` and keeps the part file and cursors. Resume is manual (`ResumeJobAsync`); an automatic free-space probe is not part of M1.
- **Offline (`TC-RES-004` engine half):** `INetworkStatus` (`IsOnline`, `OnlineChanged`); `SystemNetworkStatus` debounces `NetworkChange` events (adapter flaps, VPN) before it reports a change; tests use a fake. Going offline pauses running jobs with `NetworkOffline`; coming online resumes **only** jobs whose stored pause reason is `NetworkOffline`, also after a restart.
- **Auth failure:** `AuthRequired` pauses with a message that asks for fresh credentials or a refreshed link.
- **`RefreshLinkAsync(id, newUrl, newSecret)`** calls the existing `RefreshAndResumeAsync` (validated length and ETag, persisted URL and secret). A rejected refresh leaves the job `Paused` with the reason.

### 2.3 13c — Changed file, kill-loop smoke test, headless end-to-end

- **Changed remote file (`TC-RES-005`, `TC-RES-006`):** on `FileChanged` the engine deletes the old `.kasipart`, replaces the segment rows, calls `ResetProgressAsync`, raises `JobRestarted` with the discarded byte count and starts a fresh download; the job stays `Downloading` (ADR 0002). **The restart count is stored** (a column or the job's message counter), so the cap of 2 holds across app restarts; the third change fails the job with "File changed repeatedly".
- **Kill-loop smoke (`TC-RES-001`):** the `Kasi.FaultInjection` project from the solution layout is created now with one small child executable that runs a throttled download through `DownloadEngine`; the test kills it with `Process.Kill()` at random points (5 to 10 iterations, `Category=Integration`), restarts the engine, lets recovery run, resumes and verifies SHA-256; it asserts that no more than 2 s of data per connection is fetched again. M1.14 reuses the project for the full 100/200-iteration harness.
- **Headless end-to-end (`KASI-NFR-019`):** a multi-segment download from `TestServerHost` through `AddJobAsync`, `StartJobAsync`, `Probing`, `Downloading`, `Verifying`, `Completed`, SHA-256 checked, with no UI assembly loaded (the architecture test already forbids Avalonia references).

## 3. Verification

- **13a:** `JobStateMachineTests` for every normal and recovery edge; `JobRepositoryTests` for `TryChangeStateAsync` (wrong `from` changes nothing; `done_bytes` untouched; two concurrent callers, one wins); `CrashRecoveryTests` for each case above and for a failed `quick_check`; `DownloadEngineLifecycleTests` proving that when a `JobStateChanged` handler runs, the row already holds the new state; a throwing subscriber does not stop the engine; duplicate add returns the conflict.
- **13b:** disk full pauses with `NotEnoughSpace` and resumes from the saved bytes; going offline pauses, a user-paused job is **not** resumed on reconnect, also after a simulated restart; pause, cancel and shutdown each leave the right files and state; refresh success and rejection; debounce of the network status.
- **13c:** `/mutable` changed between sessions and mid-session restarts with `JobRestarted`, no mixed content, the old part file removed; the third change fails and the count survives a restart; the kill-loop smoke test; the headless end-to-end test.
- Mutation checks: state update without the `WHERE state = @from`, event raised before the commit, resume of every paused job on reconnect, restart count kept only in memory.
