## 2. Proposed Design & Public API (`src/Kasi.Engine/`)

The scheduler is a **pure, thread-safe (`Lock`), clock-driven (`TimeProvider`) state machine** over `Segment` instances, with zero HTTP or disk I/O dependencies.

### 2.1 `SegmentSchedulerOptions` (`src/Kasi.Engine/SegmentSchedulerOptions.cs`)

Immutable configuration record with TRD defaults and constructor validation:
- **[changed]** `int MaxConnections = 8`, validated in `1..32`. The original plan read these from `Job.DefaultConnections`, `Job.MinConnections` and `Job.MaxConnections`, which do not exist on the M1.1 `Job`; the constants live on the options type (`DefaultMaxConnections = 8`, `MinConnectionLimit = 1`, `MaxConnectionLimit = 32`) and `Job.Connections` (nullable override) is mapped to `MaxConnections` by the caller.
- `long MinSplitSize = 1L * 1024 * 1024` (`1 MiB`)
- `long PageAlignment = 64L * 1024` (`64 KiB`)
- `long MinLeaseBytes = 512L * 1024` (`512 KiB`)
- `long MaxLeaseBytes = 16L * 1024 * 1024` (`16 MiB`)
- `TimeSpan LeaseTargetDuration = TimeSpan.FromSeconds(2)`
- `double SlowLaneSpeedRatio = 0.30` (`30%` of median active worker speed)
- `TimeSpan SlowLaneSustainedDuration = TimeSpan.FromSeconds(10)`
- `long SlowLaneMinRemainingMultiplier = 4` (`4 * MinSplitSize = 4 MiB`)
- **[added]** `int SlowLaneMinActiveWorkers = 3`: the median is only meaningful with at least three active workers (the slow one plus two others), otherwise no takeover is attempted.
- `long MaxEndgameDuplicateBytes = 2L * 1024 * 1024` (`2 MiB`)
- `TimeSpan RampUpInterval = TimeSpan.FromMilliseconds(250)`
- `double RampUpThroughputGainThreshold = 0.05` (`5%`)

### 2.2 `LeaseAssignment` & `LeaseAdvanceResult` (`src/Kasi.Engine/LeaseAssignment.cs`)

- **`LeaseAssignment`** (`readonly record struct`):
  - `long LeaseId`: unique monotonic ID within the scheduler
  - `int WorkerId`: assigned worker lane (`0 .. MaxConnections - 1`)
  - `int SegmentIndex`: target `Segment.Index`
  - `long Start`: inclusive byte offset (`Range: bytes=Start-(End-1)`)
  - `long End`: exclusive byte offset (`Length = End - Start > 0`)
  - `bool IsEndgameDuplicate`: `true` when shadowing the tail of another worker's segment
  - **[changed]** `bool IsInitialProbeStream`: `true` for worker 0's first lease, which is the response the probe already holds open (see 2.4).
- **`LeaseAdvanceResult`** (`readonly record struct`):
  - `long AcceptedStart`, `long AcceptedLength`: contiguous bytes that newly advanced `Segment.Written` (so endgame shadow writes or post-completion bytes can be skipped or verified without double-counting)
  - `bool IsLeaseComplete`: `true` when the lease reached its `End`
  - `bool IsSuperseded`: `true` when an endgame peer already finished the segment (caller may stop reading/discard the rest of its lease)

### 2.3 `SegmentScheduler` (`src/Kasi.Engine/SegmentScheduler.cs`)

- **Construction / Initialization:**
  - `SegmentScheduler(long totalBytes, bool rangesSupported = true, SegmentSchedulerOptions? options = null, TimeProvider? timeProvider = null)` — starts a fresh download with a single segment `[0, totalBytes)` (or 0 segments with `IsComplete = true` when `totalBytes == 0`).
  - `SegmentScheduler(long totalBytes, IEnumerable<Segment> existingSegments, SegmentSchedulerOptions? options = null, TimeProvider? timeProvider = null)` — restores from persisted segments (for M1.9 resume), validating that the segments partition `[0, totalBytes)` with no overlap and no gap.
  - **[added]** Jobs of unknown size (`TotalBytes = null`, chunked) and non-resumable single-connection jobs do not use the scheduler; the engine streams them straight to the file. `rangesSupported = false` with a known size gives one segment and one worker, and no splits or ramp-up.
- **State queries:**
  - `long TotalBytes { get; }`
  - `bool RangesSupported { get; }`
  - `int AllowedConnections { get; }` (starts at `1`, ramps up to `MaxConnections`)
  - `long TotalWritten { get; }`
  - `long EndgameDuplicateBytesAllocated { get; }` (never exceeds `MaxEndgameDuplicateBytes`)
  - `bool IsComplete { get; }`
  - `IReadOnlyList<Segment> GetSegmentsSnapshot()` — returns immutable `Segment` records ordered by `Start`. **[changed]** The values are the *received* progress; see 2.5 for how they become checkpointable.
  - **[added]** `int StructureVersion { get; }`: incremented whenever the set or the ends of the segments change (a split); the engine persists the snapshot when it moves (2.5).
- **Core operations:**
  0. **[added] Segment ownership.** A segment belongs to one worker from its first lease until it completes or the lease is abandoned. Between two leases of the same segment the worker keeps it: `CompleteLease` does not make the segment available to others, so a worker's next `TryAcquireNextLease` continues its own segment first, before steps A to D. Only `AbandonLease` (failure) or a worker being removed releases a segment to the "unowned" pool. Without this rule two workers can alternate on one segment between leases and per-worker speed means nothing.
  1. **`LeaseAssignment? TryAcquireNextLease(int workerId)`**:
     - Returns `null` if `IsComplete`, `workerId >= AllowedConnections`, or the worker already holds an active lease.
     - **Step A (Unowned incomplete segment):** If an incomplete segment has no owner (segment 0 at start, or a segment released by `AbandonLease`), assigns a lease `[Cursor, min(Cursor + ComputeLeaseSize(workerSpeed), End))` to `workerId`.
     - **Step B (Slow-lane takeover, TRD 6.3):** If `RangesSupported`, at least `SlowLaneMinActiveWorkers` workers are active, and an active worker's speed has been `< 0.30 * medianActiveSpeed` continuously for >= 10 s and its segment has `Remaining > 4 * MinSplitSize` (`4 MiB`) and unleased tail `End - LeaseEnd >= MinSplitSize`, splits that victim segment early at `mid = AlignUp(victim.LeaseEnd, PageAlignment)` (falling back to unaligned `victim.LeaseEnd` if `AlignUp` would leave `< MinSplitSize`), so the slow worker only finishes its current lease while `workerId` takes the large share `[mid, End)`.
     - **Step C (Standard dynamic split — `TrySplit`, TRD 6.3):** Finds the incomplete segment with the maximum `free = End - LeaseEnd`. If `free >= 2 * MinSplitSize`:
       - Computes `mid = AlignUp(victim.LeaseEnd + free / 2, PageAlignment)` (with a guard ensuring `victim.LeaseEnd < mid < victim.End` even if custom alignment/split sizes are used).
       - Shrinks `victim` via `victim.WithEnd(mid)` (leaving `victim`'s in-flight lease `[Cursor, LeaseEnd)` untouched, `TC-ENG-011`), creates `fresh = new Segment(nextIndex, mid, oldEnd)`, and issues `workerId` its first lease on `fresh`.
     - **Step D (Endgame duplication, TRD 6.3):** When no unowned segment exists, every incomplete segment has `Remaining < MinSplitSize`, and `EndgameDuplicateBytesAllocated < MaxEndgameDuplicateBytes`:
       - Picks the unfinished segment with no existing shadow lease whose primary worker has the lowest speed (and whose `Remaining <= MaxEndgameDuplicateBytes - EndgameDuplicateBytesAllocated`).
       - Issues an endgame duplicate lease (`IsEndgameDuplicate = true`) over `[victim.Cursor, victim.End)` and adds that length to `EndgameDuplicateBytesAllocated`.
     - **[added] Tail lease shrink (optional, off by default behind an option):** near the end of the file, cap a lease at `max(MinLeaseBytes, Remaining / AllowedConnections)`. A single 16 MiB lease over the last stretch leaves the other workers idle while it finishes, because a split cannot cut into a lease in flight and endgame needs `Remaining < MinSplitSize`.
  2. **`LeaseAdvanceResult AdvanceLease(long leaseId, int bytesWritten)`**:
     - Advances the lease cursor and `Segment.Written` (if not already covered by an endgame peer), records throughput for `workerId` and aggregate ramp-up, and marks the peer lease superseded if the segment reaches `End`. **[added]** Called per received buffer (256 KiB), so it is allocation-free (`LeaseAdvanceResult` is a struct; no LINQ or closures under the lock) and gets a BenchmarkDotNet micro-benchmark (CONTRIBUTING 3.1, rule 7).
  3. **`void CompleteLease(long leaseId)` & `void AbandonLease(long leaseId)`**:
     - Complete: the lease ended normally; the worker keeps its segment (rule 0). Abandon: a transient failure; the segment is released and the next lease starts from `Segment.Cursor`.
  4. **`int EvaluateRampUp()`** (also called automatically inside `AdvanceLease` / `TryAcquireNextLease` when >= 250 ms has elapsed since the last ramp-up check):
     - Starts at `AllowedConnections = 1`.
     - After the first `250 ms` with active transfer (and splittable work remaining), steps `1 -> 2` and records baseline aggregate speed `R_1`.
     - On subsequent `250 ms` windows, if current aggregate speed `R_k >= 1.05 * R_{k-1}` (once the newly added connection has reported transfer or after the window), increments `AllowedConnections` up to `MaxConnections`.
     - **[added]** `R` is the bytes advanced over the window divided by its length, taken from `AdvanceLease` calls on the scheduler's clock. Because 250 ms windows are noisy (lease boundaries, TCP slow start), the plateau rule is tested with noisy simulated throughput and the thresholds stay in the options so M1.15's benchmark can tune them.
  5. **`void ReduceAllowedConnections(int count = 1)`**:
     - Decrements `AllowedConnections` and `MaxConnections` cap (clamped to >= 1) for `429` host throttling (`TC-RES-008` groundwork).
- **[added] Worker speed** (used by lease sizing, slow-lane and endgame): an exponential moving average with α = 0.3 of per-worker throughput sampled once a second (TRD 6.8), kept in a small internal `SpeedTracker` that the UI's speed and time-remaining display reuses. A worker with no sample yet counts as cold and gets `MinLeaseBytes`.

### 2.4 Resolving M1.4 D1 (How Segment 0's Probe Stream Becomes the First Lease) **[changed]**

Recorded in **ADR 0004**. The original text allowed an open-ended probe stream and said worker 0 would "extend its logical lease as it keeps reading". That cannot work: the HTTP response is one request, so a split of segment 0 would either leave worker 0 reading bytes it no longer owns or force it to abort the response, which closes the connection and breaks TC-ENG-011 and the connection-reuse goal (TC-ENG-010).

- **Decision:** for any download the engine intends to segment, it probes with a **bounded first range**: `ProbeAsync(url, firstRangeLength: MinLeaseBytes)` sends `Range: bytes=0-524287`. The response is exactly worker 0's first lease `[0, min(512 KiB, TotalBytes))`, flagged `IsInitialProbeStream`; when worker 0 has read it, the response ends naturally and the connection returns to the pool.
- The open-ended `Range: bytes=0-` stays the `ProbeAsync` default (TRD 6.1 and the TC-ENG-003 wording) and is used when the engine does not segment (single connection). No code path extends a lease beyond its HTTP response.
- If the server ignores `Range` and answers `200`, there is one segment and one worker (`rangesSupported = false`).

### 2.5 Persistence contract between scheduler, disk and `CheckpointWriter` **[added]**

ADR 0003 says a cursor may be recorded only after `FlushFileBuffers`, and `CheckpointWriter` silently ignores updates for segments that are not in the database. Two things follow that the original plan did not cover:

1. **Received versus flushed.** `AdvanceLease` counts bytes handed to the file. Only the disk layer knows what a flush made durable. The rule: take `GetSegmentsSnapshot()` **before** calling `FlushFileBuffers`, and record those snapshot values with `ICheckpointWriter.Record` **after** the flush returns. Bytes that arrive during the flush are simply recorded next cycle. The scheduler never reports flushed progress itself.
2. **Splits must be persisted before their progress.** A split adds a segment row and shrinks another. `CheckpointWriter` only updates existing rows, so progress of a new segment would be dropped. When `StructureVersion` changes, the engine calls `ISegmentRepository.ReplaceAsync` with the snapshot (it runs at most 31 times per download), and only then records checkpoints for the new segment. A crash before that costs at most the new segment's progress (redownload), never correctness, because persisted cursors are never ahead of the data.

M1.5 delivers the scheduler side (snapshot, `StructureVersion`) and tests of the rule against fakes; M1.6 and M1.9 wire the real flush and `ReplaceAsync`.

## 3. Verification (`tests/Kasi.Engine.Tests/`)

### 3.1 Deterministic unit tests (`SegmentSchedulerTests.cs`, using `FakeTimeProvider`)

- **Lease sizing (`TRD 6.2`):** Cold worker gets `512 KiB`; worker at `1 MiB/s` gets `2 MiB` (2 s); worker at `20 MiB/s` clamps to `16 MiB`; lease never exceeds `segment.End`.
- **`TrySplit` & 64 KiB alignment (`TRD 6.3`, `TC-ENG-011`):** Splitting while a lease is in flight shrinks `victim.End` to `mid = AlignUp(LeaseEnd + free / 2, 64 KiB)`, never cuts into `[Cursor, LeaseEnd)`, and allows the in-flight lease to complete normally; refuses to split when `free < 2 * MinSplitSize`.
- **Connection counts (`TC-ENG-006`):** Configured `MaxConnections` of `1, 2, 8, 16, 32` on a `1 GiB` file ramps up to the exact target count when throughput scales and completes the full `1 GiB` with union = `[0, 1 GiB)`.
- **Slow-lane takeover (`TC-ENG-008`):** 8 workers where worker 0 runs at `50 KB/s` and workers 1–7 run at `5 MB/s`. **[changed]** TPL says "takeover within 10 s", but the rule needs 10 s of sustained slowness, so the simulated test asserts the takeover happens when the slow state has lasted `SlowLaneSustainedDuration` (10 s from its first sample, plus one scheduler tick), and that no worker idles while more than `MinSplitSize` remains. The TPL wording is clarified accordingly when M1.5 is ticked.
- **Endgame duplication (`TC-ENG-009`):** When all remaining segments are `< 1 MiB` and a worker becomes idle, it receives an `IsEndgameDuplicate = true` lease on the slowest unfinished segment; whichever lease finishes first completes the segment and marks the other `IsSuperseded = true`; total duplicate bytes across the download never exceed `2 MiB`.
- **Ramp-up plateau (`TRD 6.3`):** Ramp-up stops adding connections when aggregate throughput rises by `< 5%` over a `250 ms` step. **[added]** Also with noisy throughput (±20% per window) it does not stop at two connections on a link that really scales.
- **[added] Ownership:** a worker's next lease continues its own segment; a lease completing does not hand the segment to an idle worker; an abandoned lease releases it and resumes at the cursor.
- **[added] Slow-lane guards:** no takeover with fewer than three active workers, or when the victim has no unleased tail.
- **[added] Persistence contract (2.5):** `StructureVersion` increases on every split and only then; the snapshot partitions the file; a test double that mimics `CheckpointWriter` (ignores unknown segment rows) shows progress of a new segment is lost if the split was not persisted first, and is kept when it was.
- **Edge cases:** `0 B` file (immediately complete), `1 B` file, exact multiples of `MinSplitSize` and `64 KiB`, `4 GiB + 1 B` and `20 GiB` files, non-ranged (`RangesSupported = false`) single-connection mode, and resume from existing `Segment` list.
- **[added] Simulation harness (`SchedulerSimulator`, test project):** virtual workers with configurable speed, a virtual clock (`FakeTimeProvider`), lease completion, failures and aborts. The unit tests and the property tests share it; it is part of step 3 of the plan, not an afterthought.

### 3.2 Property-based tests (`SegmentSchedulerPropertyTests.cs`, `FsCheck.Xunit.v3`, `TC-ENG-007`)

Random file sizes across `0 B` to `64 GiB` (including boundary values `0`, `1`, `64 KiB +- 1`, `1 MiB +- 1`, `4 GiB + 1`, `64 GiB`), random connection counts (`1..32`), random worker speeds, and random sequences of lease acquisitions, partial advances, completions, abandonments, and slow-lane/endgame triggers, all through the simulator:
- **Invariant 1 (No overlap, no gap, union = file):** After every step and at completion, segments sorted by `Start` form a contiguous partition of `[0, TotalBytes)`.
- **Invariant 2 (In-flight lease safety, `TC-ENG-011`):** No split ever sets `segment.End < lease.End` or `segment.End < segment.Cursor`.
- **Invariant 3 (Completion):** Every generated schedule terminates with `IsComplete == true` and `TotalWritten == TotalBytes`.
- **Invariant 4 (Endgame cap, `TC-ENG-009`):** `EndgameDuplicateBytesAllocated <= 2 MiB` always holds.
- **[added] Invariant 5 (Ownership):** at any time each incomplete segment has at most one primary lease holder, and a worker holds at most one lease.
- **[added]** The seed is printed on failure (CONTRIBUTING 4).
