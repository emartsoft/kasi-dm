- **Phase:** M3 ([`plan.md`](../../plan.md) section 6, tasks M3.1 to M3.9)

## 2. Decisions

1. **Our own parsers, no FFmpeg for parsing (TRD 7.2).** HLS (RFC 8216) is a hand-written line parser; DASH uses `System.Xml` with `DtdProcessing.Prohibit`, `XmlResolver = null`, and the 10 MB manifest cap from plan.md M3.1. Both emit one neutral model: `MediaPresentation` (streams, each with a variant description: bandwidth, resolution, codecs, language, estimated size, and a concrete ordered segment list with init segment, key info and durations). Hard caps on segment count and on `SegmentTimeline` repeat expansion so a hostile manifest cannot allocate without bound (TPL 7.2: no allocation over 256 MB, no hang over 2 s).
2. **One gate for DRM, in front of every segment request (`KASI-MED-005`, TRD 7.3, hard rule 4).** `Kasi.Media` exposes a single entry point, `MediaSourceLoader.LoadAsync(...)`, that fetches the manifest (and the media playlists of the chosen variants, which are manifests, not segments), parses, runs `ProtectionCheck`, and returns either `Playable(plan)` or `Protected(reason)`. The segment downloader accepts only a `Playable` plan (the type has no public constructor outside the loader), so there is no way to reach a segment without passing the check. Details:
   - HLS refused: `EXT-X-KEY` or `EXT-X-SESSION-KEY` with `METHOD=SAMPLE-AES`/`SAMPLE-AES-CTR`, any `KEYFORMAT` other than `identity` (FairPlay, Widevine, PlayReady and unknown ones), any `METHOD` we do not know. Allowed: `NONE`, `AES-128` with `KEYFORMAT=identity` and an HTTPS key URI (`KASI-MED-006`).
   - DASH refused: any `ContentProtection` element in a used `AdaptationSet` or `Representation` whose scheme is a DRM scheme (Widevine, PlayReady, FairPlay, ClearKey, and any unrecognised `urn:uuid:` scheme, fail closed). `urn:mpeg:dash:mp4protection:2011` alone (the generic `cenc` signal) also refuses, because the content is encrypted.
   - **Fail closed:** a signal we cannot classify is a refusal, never a pass.
   - **No override, by construction.** No setting, command-line flag, environment variable, registry value, protocol field, or parameter of any public `Kasi.Media` type can skip or soften the check. `Kasi.ArchitectureTests` gets a test that fails if a public type in `Kasi.Media` or `Kasi.Core` settings exposes a member whose name suggests bypassing the check (`drm`, `protect`, `bypass`, `skip`, `ignore`), and a test that the only producer of `Playable` is the loader. PR carries the `security` label and needs **two approvals** (plan.md M3.2).
   - Refusal logs the manifest host and the reason code only: no segment URLs, no query strings, no key URIs (hard rule 3).
   - User message: see question 5 (the TRD has two wordings).
3. **Direct media (`kind: direct`) is not a media job.** An `mp4`/`webm`/`mp3`/`m4a` response is a plain HTTP download and goes through the existing Add path with the cookies and referrer already carried by `captureMedia`. Only HLS and DASH use the segment pipeline. Saves a whole code path and keeps resume exact.
4. **Media job model (TRD 7.4, 11.2).** One `job` row (`kind = media`), no grid rows for segments. New tables `media_stream` (job, role video/audio/subtitle, chosen variant, codecs, container, init segment) and `media_segment` (job, stream, index, size, completed flag, offset of key/IV), migration `0006` (next free number; confirmed at PR time), ADR first. Completion writes are batched every 1 s through a single writer like the `CheckpointWriter` (TRD 11.3). `job.done_bytes` is the sum of finished segments; `job.total_bytes` is the manifest estimate (bandwidth × duration) and shown as approximate.
5. **Segment storage and resume (hard rule 2).** Each segment is written to `%LOCALAPPDATA%\Kasi\media\<job id>\<stream>\<index>.part`, flushed (`FlushFileBuffers`), renamed to `<index>`, and only then marked complete in SQLite. A resume skips marked segments and deletes stray `.part` files. Whole segments are fetched (no splitting), 6 in parallel per stream (setting 1 to 16). They reuse the engine's connection pool, retry and error classification, authentication/cookie scoping, and the shared bandwidth buckets. If the engine does not already expose a "fetch this URL whole through the pool" seam, 3c adds the smallest additive one in `Kasi.Engine` and says so in the PR; no change to the transfer hot path.
6. **Executor routing without breaking layers.** `Kasi.Media` references `Kasi.Engine`, so the engine cannot call it. `Kasi.App` composes a routing `IJobControl` (the M2.10 interface in `Kasi.Core`) that sends `http`/`ftp` jobs to `DownloadEngine` and `media` jobs to a `MediaJobRunner` in `Kasi.Media`. The queue runner needs no change. State flow is the existing one: `Downloading` → `Muxing` → `Verifying`.
7. **AES-128 (`KASI-MED-006`)** is decrypted in C# with `System.Security.Cryptography` (CBC, PKCS#7, explicit IV or media-sequence IV per RFC 8216), per segment, before the segment is marked complete. Key fetched once per key URI, held in memory only, never written to disk, logs or the DB. Key URI must be HTTPS (TRD 7.3); tests run `TestServer` in its TLS mode.
8. **Concatenate ourselves, mux with FFmpeg (TRD 7.4).** Per stream: init segment first (fMP4/CMAF), then segments in order, into one temp file; then `ffmpeg -c copy` combines streams into `.mp4` or `.mkv` (MKV when codecs do not fit MP4, decided from manifest codec strings, falling back to `ffprobe` of the joined stream). Audio only keeps the audio in a stream-copy container (`.m4a` for AAC, `.mka` otherwise). `ffprobe` checks duration against the manifest within 1 s, then the segment folder is deleted. A duration mismatch fails the job in `Verifying` and keeps the folder for diagnosis.
9. **FFmpeg boundary (TRD 13.4, hard rule 8).** LGPL build, no `--enable-gpl`, no `--enable-nonfree`; started by `Process` with `ArgumentList` (no shell), only local file inputs and `-protocol_whitelist file`, so FFmpeg never touches the network. A Win32 job object with `KILL_ON_JOB_CLOSE` (P/Invoke, no package) ends it if Kasi exits. Stderr goes to the job log **through the redaction helpers** (FFmpeg echoes full local paths; hard rule 3). It is never linked into any Kasi assembly. Packaging, licence file, source offer, notices and installer size are the owner's calls (questions 1 to 3); this plan only builds the wrapper against a path it is given.
10. **Test media (`TC-MED-004`, `TC-MED-006`).** The existing opaque kinds stay as they are and keep serving parser, DRM, download, resume and decrypt tests. For FFmpeg and playability tests 3d adds kinds that serve **real muxable segments**: a few-hundred-KB clip (about 24 s: six 4 s segments of a 160×90 test pattern with a sine tone) pre-generated once, checked in under `tests/fixtures/media/` with the generator script and command line documented, served by `/hls/muxable/...`, `/hls/muxable-aes128/...` (same bytes, AES-128 encrypted at serve time) and `/dash/muxable/...` (fMP4 init + segments). Checked-in files (not "run FFmpeg during the test") keep the segment bytes stable and the only test-time FFmpeg use is the code under test. See question 4 for where the test binary comes from.
11. **No public internet in tests (hard rule 5).** Every media test reads manifests and segments from `Kasi.TestServer` (in-process Kestrel). "Golden" manifests are text files in `tests/fixtures/media/`; no segment is ever fetched from Apple, DASH-IF or anyone else (question 6 covers the licence of the manifest files themselves). Extension Playwright tests serve their pages from `Kasi.TestServer` too. Zero-segment-requests assertions (`TC-MED-005`) use a per-path request counter on the server; 3b adds it to `TestServerMetrics` if absent.
12. **Detection in the extension (`KASI-MED-001`, TRD 7.1).** `webRequest.onResponseStarted` (read-only, non-blocking; MV3-safe) classifies `.m3u8`/`.mpd` by URL or content type, and direct media by `video/*`/`audio/*` over 1 MB. Segments (`.ts`, `.m4s`, `.cmfv`, `.cmfa`) and repeat manifests per tab are suppressed. Per-tab state lives in `chrome.storage.session` (the MV3 service worker can be unloaded at any time; nothing may depend on in-memory state). Badge on the icon, overlay button on the largest `<video>`, popup stream list. Choosing an entry sends `captureMedia`. No site-specific extractors and no hidden-URL scraping (TRD 7.6): only what the browser actually requested. Tests use test pages that `fetch()` manifests and play a direct `<video src>`, so no player library (such as hls.js) is needed.
13. **Where the quality list is shown.** The popup lists detected streams (one line each); the quality list, size, format and subtitles are the **Kasi media picker** (TRD 12), because the engine does the parsing with the page's cookies. `captureMedia` therefore leads to: loader → refuse (toast) or picker → job. Default selection is the highest video at or below the preferred maximum (setting, default 1080p) with the best matching audio.
14. **Protocol changes are additive, optional, `v` stays 1** (ADR 0016 versioning). Proposed in 3e: `captureMedia.origin` (optional string), `mediaDetected.thumbnailUrl` optional (from `video.poster` or `og:image`), `mediaDetected.contentType` optional, and a defined reply (`ok`, or the existing `error`) for both messages. A general request-header pass-through is deliberately **not** proposed (cookies, referrer, user agent and origin cover real sites; more would widen the secret surface). Schema, `IpcValidator`, C# records and TS types change together; the schema test (`Kasi.Ipc.Tests`) and the TS contract test must pass.
15. **Quota (`KASI-QUE-007`, `TC-QUE-006`).** The column `queue.quota_bytes`/`quota_reset` exists. New table `queue_usage` (queue, period start UTC, bytes) holds consumption; the engine reports bytes written per job (media segments and HTTP chunks alike) through a Core-level counter interface that `Kasi.Scheduling` consumes. When a queue's period total reaches the cap the runner stops starting jobs, pauses running ones with `pause_reason = quota`, and shows it in the queue and status bar. The period rolls over at local midnight (daily), local Monday 00:00 (weekly) or never, computed from `TimeProvider`; at rollover quota-paused jobs resume in order. Overshoot is bounded by bytes in flight (question 8).
16. **Wake from sleep (`KASI-QUE-005`, TC-QUE-005, TRD 10.2).** `IWakeTimer` in `Kasi.Core`; the Windows implementation (P/Invoke: `CreateWaitableTimerEx`, `SetWaitableTimer` with the resume flag) lives in `Kasi.Scheduling` and arms the next schedule start, re-armed whenever schedules change and on resume. "Wake timers allowed" is read from the active power plan (`PowerReadACValueIndex`/`DCValueIndex` for the RTC-wake setting) behind `IWakeTimerPolicy`; when off, the Scheduler window shows a warning with the setting named. Unit tests use fakes plus `FakeTimeProvider`; the hardware case is manual and its evidence is recorded in `docs/qa/wake-from-sleep.md` on two physical laptops (modern standby and S3 if available). `KASI-QUE-005` is not marked verified until that evidence exists, the same way the M1 gate waits for benchmark evidence.
17. **Fuzzing.** `tests/Kasi.Fuzz` gains HLS and MPD targets (5 min each per night, TPL 7.2) with seed corpora of the hand-written and golden manifests; `nightly-fuzz.yml` runs them. Findings follow the existing flow (minimise, add to `tests/fixtures/fuzz/crashes`, High defect).
18. **Out of scope for M3:** site-specific extractors (TRD 7.6), DRM of any kind, link refresh for expired signed segment URLs (a media job whose segments return 401/403 pauses with a clear reason; refresh reuse is a v1.1 candidate, question 9), muxing with burned-in subtitles, transcoding of any kind.

## 4. Tests per PR

All tests are tagged `[Trait("TC", "...")]`; anything touching the server is also `[Trait("Category", "Integration")]`. No tight timing assertions: waits are on events or on `FakeTimeProvider` time.

- **3a:** golden manifests for master/media playlists (audio groups, I-frame-only ignored, byte ranges, discontinuities), `SegmentTemplate` (`$Number$`, `$Time$`, `SegmentTimeline`), `SegmentList`, `SegmentBase`; hostile inputs (DTD/XXE, 10 MB+, 10^6 timeline repeats, nested BaseURL cycles) fail fast and bounded. Property test (FsCheck): parse never throws anything but `MediaParseException`.
- **3b:** for every kind in `StreamFixtures.HlsKinds`/`DashKinds`: loader result and reason code; server counter shows **0** requests to any segment or key path for the refused ones; `aes128`, `clear`, `segment-list` return `Playable`. Variant playlists carrying `EXT-X-KEY` that the master did not (refuse); `EXT-X-SESSION-KEY` in master (refuse); unknown `METHOD` (refuse). Architecture tests: no override member, single `Playable` producer.
- **3c:** parallelism ≤ configured (server peak connections), ordered assembly equals expected bytes (SHA-256), cancel+restart resumes with the server counter proving finished segments are not fetched again, chaos profiles (reset, 503, truncation) recover, `.part` leftovers cleaned, disk-full error is a clean failure, AES-128 plaintext equality.
- **3d:** fixtures decode with `ffprobe` (duration, stream count) for MP4 and MKV; wrapper kills FFmpeg when the host job object closes (test starts a child that sleeps, not real mux); stderr redaction test; duration-mismatch fault. Tests that need the binary skip with an explicit message when it is absent locally and **fail** in CI (question 4).
- **3e:** pipe-level tests with the existing BrowserHarness: `captureMedia` for a clear stream creates a media job; for each DRM kind the reply is a refusal and the server saw no segment; protocol schema/validator/TS contract tests for the new optional fields.
- **3f:** Avalonia.Headless tests: default selection, MP4/MKV/audio-only switching, size text, keyboard-only, automation names.
- **3g:** Vitest: classifier table (URL and content-type cases, 1 MB threshold, segment and duplicate suppression, service-worker restart keeps state); Playwright: three pages (HLS, DASH, direct) show badge and popup entry and send the expected `captureMedia` to a fake native host.
- **3h:** `FakeTimeProvider` + fake byte counter: a 2 GB cap stops the queue at the cap within the stated overshoot, daily/weekly/never rollover including month and DST boundaries, restart keeps usage, paused-by-quota jobs resume in order.
- **3i:** fake timer: armed for the next start, re-armed on edit and on resume, warning when policy is off; Win32 wrapper smoke test only checks that arming and cancelling a timer succeeds on a Windows runner. Hardware evidence on two laptops per the checklist.
- **3j:** `/hls/live/...` kind added to the test server that grows by one segment per injected clock tick; "10-minute" requirement is tested as 150 ticks of 4 s with a fake clock, plus one optional real-time nightly smoke run of a few minutes. VTT fixtures for the saved-beside-video case.
- **3k:** change of `/mutable/{id}` content triggers one re-download at the next check, unchanged triggers none.

## 5. Order and parallelism

```
3a ─ 3b ─ 3c ─ 3e ─ 3f ──┐
          3d ──┘          ├─ 3l
3g (after 3e's protocol) ─┤
3h ─ 3i (independent of media; can run alongside) ─ 3k, 3j (optional, last)
```

- Media series order: 3a, 3b, 3c; 3d can start as soon as the owner answers questions 1 to 3 and runs in parallel with 3c; 3e needs 3c (and 3d for the muxed result end to end, otherwise it stops at the concatenated file behind a flag that does not ship); 3f after 3e; 3g needs only the protocol part of 3e, so split that part out first if the extension developer is free earlier.
- Scheduler series 3h, 3i touches `Kasi.Scheduling`, `Kasi.Data`, Scheduler window; no overlap with `Kasi.Media`, so a second developer can take it.
- Two writers never touch the same files: 3c and 3h both add a migration; whoever merges second renumbers.
- Each PR updates README (layout, commands) and plan.md (task status, "Last updated") where it changes them, and says so in the PR description.

## 6. Risks

| Risk | Impact | Mitigation |
| --- | --- | --- |
| A DRM variant slips through the check | Legal, store removal | Fail closed, single gate, fixture for every kind in the test server, two approvals, architecture tests, fuzzing |
| MV3 service worker unloads mid-session | Lost detections, wrong badge | State in `storage.session`, tested by restarting the worker in Playwright |
| Hostile manifests (XXE, huge timelines, cyclic URLs) | Hang or memory blow-up | No DTD, no resolver, hard caps, fuzz targets, timeouts |
| FFmpeg build size breaks `KASI-NFR-020` (60 MB installer) | NFR miss | Minimal LGPL build (mux/copy only) is an owner decision (question 2) |
| Segment URLs expire (signed CDNs) | Capture fails midway | Pause with a clear reason; resume works if the URL still works; refresh deferred (question 9) |
| Muxable fixtures drift from real-world streams | Passing tests, failing sites | Fixtures cover TS and fMP4; manual QA list with a handful of real public streams (outside CI) before the M3 close |
| Wake timers differ across laptops and plans | `QUE-005` flaky in the field | Two physical devices, policy check and warning, evidence file; not claimed verified without it |
| Quota overshoot by in-flight bytes | Users on metered bundles exceed cap slightly | Bounded and documented; stop issuing new ranges near the cap (question 8) |
| Engine seam for whole-segment fetch needs a change | Touches M1-gated code | Smallest additive seam only, benchmark smoke before and after, called out in the PR |
| Another session edits shared files | Merge friction | This plan touches none of `tests/Kasi.App.UiTests`, `tests/Kasi.FaultInjection`, `docs/plans/m2-13.md`; M3 tests use TestServer chaos and in-process restarts instead |

## 7. Questions for the owner

Not decided here.

1. **FFmpeg licence and source offer:** confirm LGPL 2.1+ build only and that Kasi satisfies the obligations by shipping the licence text, a written source offer (or a hosted source archive for the exact build), and a replaceable `ffmpeg.exe` in a known folder. Who hosts the source archive, and under which URL?
2. **FFmpeg packaging and size:** build our own minimal LGPL binary (only demux/mux/copy, a few MB, we own the build recipe and source archive) or ship a stock LGPL build from a third party (bigger, faster to start)? `KASI-NFR-020` is 60 MB for the installer. Same question for `ffprobe`.
3. **Download-or-bundle for development:** bundled in the installer from the first M3 beta, or fetched at first use? (TRD 7.4 and NFR-020 say bundled; confirming, since a download would be a new network behaviour.)
4. **FFmpeg in CI and tests:** where does CI get the binary without the public internet at test time (a pinned release asset in this repo's storage, a CI cache, or `tools/ffmpeg` produced by question 2)? Which version do we pin and who updates it?
5. **Refusal wording:** TRD 7.3 says "This video is protected and can't be saved"; the `KASI-MED-005` acceptance criterion says "Protected content can't be saved". Which string is exact? Tests will assert it.
6. **Fixture licences:** plan.md M3.1 says golden fixtures from public test streams (Apple, DASH-IF). Their manifest files carry their own terms. Is checking in verbatim copies acceptable (with attribution), or should we hand-write manifests modelled on them?
