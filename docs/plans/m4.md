## 2. Decisions

1. **Torrents stay out.** `Kasi.Torrent` remains an empty placeholder, nothing here depends on MonoTorrent, the installer budget (`KASI-NFR-020`, 60 MB) is easier without it, and the beta gate treats `TC-TOR-001` to `006` as an approved deferral (plan.md 7.1).
2. **Speed profiles (`BWL-003`, `BWL-001`).** A profile is a named limit (bytes per second, or unlimited). The existing global bucket stays the only throttle: a profile just sets its rate. A schedule may name a profile for its window (TRD 10.2); the scheduler applies the change at the boundary and persists the active profile, so a restart inside a window starts under the right profile. The tray gets presets (profiles plus "Unlimited") that apply within one second (`TC-BWL-001`). Data: a `speed_profile` table and a `profile_id` on `queue_schedule`; migration numbers are taken when the PR is written.
3. **Start with Windows (`SYS-003`).** One toggle in Settings adds or removes a value under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` that starts Kasi with `--tray`; the value points at the installed executable, is replaced rather than duplicated, and the portable build writes it only after the person turns the toggle on (`TC-SYS-002`, `TC-SYS-004`). Uninstall removes it.
4. **Portable mode.** `portable.marker` next to `Kasi.exe` moves data and settings to `.\data`. A portable run writes no registry key, no host manifest and no startup entry until the person consents in Settings (TRD 14.2). Browser integration needs the HKCU host registration (browsers read it from the registry), so it is a Settings action in portable mode and an install step in the installer.
5. **Registration in one place.** The registry and manifest writes that `Register-NativeHost.ps1` does today move into a small tested class used by the installer hook, the Settings action and uninstall; the script stays as the developer tool and its tests keep running.
6. **Velopack packaging (`SYS-001`).** Self-contained, ReadyToRun, x64 and ARM64. The installer is per user (no UAC) under `%LOCALAPPDATA%\Kasi`, with Start menu entry, toast AUMID, uninstall entry that asks whether to keep history and settings, and host manifests under HKCU. Artefacts are those of TRD 14.1. FFmpeg and ffprobe come from the verified minimal LGPL build as a release asset (`Fetch-FFmpeg.ps1`, SHA-256 pinned); **an ARM64 FFmpeg build is needed** and the existing workflow only builds x64 (question 8).
7. **Signing (`NFR-012`).** Every executable, DLL built by MartSoft, installer and package is signed and timestamped in CI; an unsigned or wrongly signed artefact fails the release job. Which service signs is the owner's decision (question 1); the pipeline is written against a signing step that can be swapped. No key or token is ever read or handled by me or committed: they live in the repository's protected environment secrets, set up by the owner.
8. **Release pipeline (TRD 14.5).** Pull requests: unchanged. Merge to `main`: build, test, fuzz as today, then a signed **beta** build published to the `beta` channel. Version tag: signed **stable** build, release notes from merged pull requests, artefacts to the update feed and download page. Version numbers come from the existing MinVer tags (`1.0.0-beta.N`, `1.0.0`).
9. **Self-update (`SYS-002`, `NFR-012`).** Daily, and at start-up when the last check is older than 24 hours, over HTTPS only, `releases.<channel>.json`. Velopack verifies the package signature and hash before anything is replaced; a tampered or unsigned package leaves the old version untouched. The update applies on exit or by "Restart to update", after the engine has checkpointed active jobs. Channels `stable` (default) and `beta` (opt-in). Tests run against a local feed (a folder or the test server), never the public internet. Whether the download uses Velopack's own downloader or the Kasi engine at low priority (TRD 14.3) is question 4.
10. **Export and import (`SYS-004`).** A single versioned JSON file with settings, categories and rules, queues and schedules, speed profiles and the job list. **Secrets (cookies, credentials, proxy passwords) are never exported** (`TC-SYS-005`: "secrets are not exported in plain text"); imported jobs that need them ask for them again. Import validates a schema version and runs older versions through a migration, rejects unknown future versions with a clear message, and never overwrites without a confirmation.
11. **Opt-in crash reporting (`SYS-006`, `NFR-013`).** Off by default; a first-run choice and a Settings toggle. The payload is the exception, stack trace, OS and Kasi version only; a scrubber removes URLs, query strings, file paths, user names, cookies and header values before anything leaves the machine, using the existing redaction helpers plus a final allow-list check on the payload, and a test feeds it canary strings. A fresh install's only network request is the update check (`TC-SYS-007`). Backend is question 2.
12. **Notices (`TRD 13.4`).** `THIRD-PARTY-NOTICES.txt` is generated in CI from the package manifests and checked against the committed file (a changed dependency fails the build until the file is regenerated); Settings, About shows it.
13. **Compatibility matrix (`NFR-014`, `NFR-015`).** A manual-trigger workflow and a documented procedure run the install, start, download, tray, scheduler and update check on each OS image, and the browser smoke on each browser, and write results to `docs/qa/compatibility.md`. Hosted runners cover Windows 11 x64 and ARM64; older Windows 10 and the 23H2/24H2/25H2 images need the owner's VMs (question 7).
14. **Beta programme (`NFR-008`).** Process, not code: the `beta` channel, an install guide, a feedback channel, a triage cadence, and 7 days with 50 or more users including people on metered and unstable connections. Crash data is opt-in and starts accruing only from beta users who choose it.

## 4. Tests per PR

All tests are tagged `[Trait("TC", "...")]`; anything that touches the network, the registry or a real process is also `[Trait("Category", "Integration")]`. No public internet; no tight timing assertions (the 1 second tray rule is checked with a fake clock and an event, plus one measured run on hardware).

- **4a:** fake clock across a schedule boundary (the profile flips, persists, and is right after a restart inside a window); the tray preset changes the live limit within one second of the call and a second change while running also takes effect; measured rate within 5% over a 10 s window on the test server.
- **4b:** registry round trip against a private test hive (as the registration script tests do): add, remove, repeat toggles leave one value; the command line has `--tray`; portable writes nothing before consent.
- **4c:** the generator output equals the committed file; adding a package changes it; the About page shows it (headless).
- **4d:** round trip of every exported kind through a temporary database; secrets absent from the file (canary strings); older schema through the migration; unknown newer version refused; confirmation required.
- **4e:** publish smoke on x64 and ARM64 (hosted runners): the app starts, finds FFmpeg, reads `portable.marker`; the registration class against a private registry root; size budget assertion.
- **4f:** installer and uninstaller on a clean VM or hosted runner: no UAC, expected files, host manifests, uninstall removes them and asks about data; portable run writes no registry keys (compared before and after).
- **4g:** a workflow dry run on a branch; the signature check fails on an unsigned file; no secret in logs. The first real signed run is the owner's.
- **4h:** a local feed with 1.0.0 and 1.0.1: delta applies and restarts on the new version; a tampered package and a badly signed one are rejected before any file is replaced and the old version still starts; update check is the only request; channel switch.
- **4i:** canary URL, cookie, header and user path in an exception are absent from the payload; opt-in off means no request; the only request of a fresh install is the update check; the scrubber has a property test (random strings never survive when they look like URLs or paths).
- **4j:** the matrix runs and their evidence, plus the smoke suite on each image.
- **4k:** the gate checklist is filled from the evidence files.

## 7. Risks

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Code-signing service not available or slow to set up | No signed beta; SmartScreen warnings | Decide question 1 now; the pipeline is written against a swappable signing step; first run is a dry run |
| A brand-new certificate has no SmartScreen reputation | First users see a warning | Say so in the beta guide; reputation builds with downloads; EV certificates start with it |
| ARM64 FFmpeg or Velopack ARM64 packaging problems | ARM64 users cannot install | Hosted ARM64 runner builds it early (4e); ARM64 can ship after x64 in the beta if the owner agrees |
| Registry writes from the portable build | Breaks the "portable" promise (`TC-SYS-002`) | Registration class with a private-root test; a before/after registry comparison in the installer test |
| A crash report leaks a URL, path or cookie | Privacy breach, High defect | Allow-list check on the payload, canary tests, property test, security review before the PR merges (two approvals and the `security` label) |
| Update applied to a damaged install | Users cannot start Kasi | Verify before replace, keep the old version, tamper tests, beta channel first |
| Update feed outage | Update checks fail | Failure is silent and retried; downloads and the app never depend on it |
| Beta users fewer than 50 | Release criteria (TRD 15.3) not met | Owner recruits early (question 6); gate waits for the numbers |
| Old Windows VMs unavailable | Compatibility claims unproven | Question 7; do not claim a version that has no evidence |

## 8. Questions for the owner

Not decided here. Recommendations are marked.

1. **Code signing:** Azure Trusted Signing, or an EV (or OV) certificate in a cloud HSM service? Trusted Signing availability depends on the organisation's country and registration, so please check eligibility for MartSoft Solutions first. *Recommendation:* use Trusted Signing if it accepts the company, otherwise a cloud-HSM EV certificate. Who sets up the account and the GitHub environment secrets, and by when (4g is blocked until then)?
2. **Crash reporting backend (Appendix B #6):** Sentry hosted (which region), Sentry self-hosted, or a small endpoint of your own? *Recommendation:* Sentry hosted, EU region, with the scrubber enforced in the client so the server never sees personal data. This also needs the privacy policy and store data-usage pages updated, which 4i does.
3. **Update feed hosting:** GitHub Releases, Cloudflare R2 behind a CDN, or Azure Blob with Front Door? Which domain? *Recommendation:* GitHub Releases for the beta (Velopack supports it, no extra service), object storage plus CDN for stable. Is the repository public?
4. **Update download:** Velopack's own downloader, or the Kasi engine at low priority as TRD 14.3 says? *Recommendation:* Velopack's downloader first (simplest and already verified), the engine route only if you want the bandwidth-limiter integration.
5. **Export contents:** confirm that secrets are never exported and that imported jobs ask for credentials again. *Recommendation:* yes.
6. **Beta users:** who are the 50 (including people on metered and unstable connections), how are they recruited, what is the feedback channel and the triage cadence, and how long (at least 7 days)?
7. **Compatibility VMs:** where do the Windows 10 22H2, Windows 11 23H2, 24H2, 25H2 and ARM64 machines run (your Hyper-V host, Azure VMs, a cloud service)? Which Windows 11 ARM64 device or VM?
8. **ARM64 FFmpeg:** build the minimal LGPL FFmpeg for ARM64 as well (a second job in the existing workflow on an ARM64 runner), or ship x64 first and ARM64 later?
9. **Installer details:** publisher and product names as shown, icon, whether the installer shows a licence page, and the licence itself: Appendix B #2 says free and open source, #5 (source availability) is still open. Which licence applies to the repository and the installer?
10. **Store links:** the installer opens each browser's store page; the Chrome, Edge and Firefox listings must exist (the M2 store submissions are your steps). Is it acceptable to ship the beta with links that open the listing only once approved?
11. **Version names:** `1.0.0-beta.N` for beta builds and `1.0.0` for stable, with the first beta tag cut by you?
12. **M3 close-out:** the wake-from-sleep hardware runs and a short real-stream smoke test are still owner items before M3 is called closed; shall I prepare a one-page checklist for them as a separate docs PR?
