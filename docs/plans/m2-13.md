## 1. What exists

- `Kasi.App` has stable automation names on its controls (a Definition of Done item since M2.8), and `Kasi.App.Tests` drives views headlessly with Avalonia.Headless.
- `KASI_DATA_DIR` moves the data folder, and `KASI_ENDPOINT_SUFFIX` appends to the instance mutex, the browser pipe and the hand-off pipe, so a test instance never meets a real Kasi. Both are read by the app today.
- `Kasi.BrowserHarness` plays Kasi on the real named pipe and also runs as `Kasi.exe --tray` for the native host to start. `extension-e2e.yml` runs it in Chromium on pull requests and in Chromium and Firefox nightly.
- `Kasi.TestServer` serves files and a login-protected path (cookie check) on loopback.
- The native host connects to `KasiPipeNames.ForCurrentUser()` and does **not** read `KASI_ENDPOINT_SUFFIX` (see decision 7).
- There is no FlaUI project, no UI workflow, and the browser suite cannot yet run against the real app.

## 2. Decisions

1. **UI Automation, not pixels.** Tests find controls by `AutomationId` and name and act through UIA patterns (`Invoke`, `Value`, `Toggle`, `SelectionItem`), never by screen coordinates or simulated mouse movement. The window need not be in front, which is what makes a CI desktop dependable. A text lookup retries for up to 10 s; nothing else retries.
2. **A new project, `tests/Kasi.App.UiTests`,** on the same TFM as `Kasi.App.Tests`. It starts the **built** `Kasi.App.exe` as a child process, so the real start-up path, the single-instance lock and the shutdown are exercised. It is not part of `dotnet test` on a developer machine unless `KASI_UI=1` is set (same opt-in idea as `KASI_E2E`), because it needs an interactive desktop and takes over nothing else.
3. **Isolation per test.** Each test gets a temp data folder (`KASI_DATA_DIR`), a unique endpoint suffix (`KASI_ENDPOINT_SUFFIX`), and its own `Kasi.TestServer` on a free loopback port. Tests never run in parallel against the same suffix. No public internet (CLAUDE.md rule 5); every completed download is checked by SHA-256.
4. **Test seam for the browser side.** The UI tests do not need a browser. Where a flow starts from one (the link picker, the refresh window), the test plays the browser: it connects to the app's pipe with `KasiPipeClient` and sends the real `addBatch` or `refreshLink` message. This reuses `Kasi.Ipc` and needs no new app code.
5. **Scope of the smoke suite (13a and 13b).** It proves the main flows work through the real window; the finer behaviour stays in the headless tests.

   | Flow | Test case | PR |
   | --- | --- | --- |
   | Start, main window visible with the toolbar, sidebar and list, then Quit | `TC-UI-001` | 13a |
   | Add dialog: fill the URL and folder, Add, the row appears and completes with the right SHA-256 | `TC-UI-001` | 13a |
   | Pause and resume from the toolbar; state text changes | `TC-UI-001` | 13a |
   | Delete with the confirmation dialog | `TC-UI-001` | 13b |
   | Details window opens on Enter and shows the map and the log | `TC-UI-002` (the window, not the update rate) | 13b |
   | Link picker from a browser `addBatch`: filter, select shown, Add | `TC-BRW-005` Kasi half | 13b |
   | Refresh-link window from a browser `refreshLink` | M2.8d-4 | 13b |
   | Scheduler window: opens, saves a schedule and a post-action | KASI-QUE-003, 004 | 13b |
   | Tray: close the window, the process stays; Pause all and Quit from the menu | `TC-UI-003` | 13b |

   The tray menu is a native shell menu; if UIA cannot reach it reliably on the runner, the test falls back to the view-model path already covered headlessly and the gap is written in the ADR (decision 9). The tray icon itself and the toasts are not driven (see the closing note above).
6. **CI.**
   - **Pull requests (13a):** job `UI smoke` runs the three 13a tests (about 2 minutes), on pull requests that touch `src/Kasi.App/**`, `src/Kasi.Core/**`, `tests/Kasi.App.UiTests/**` or the workflow. It does not block on a path it does not cover.
   - **Nightly (13b):** `nightly-ui.yml` at 03:15 UTC runs the full suite and uploads screenshots of the failing window and the app log. A failure artefact never contains URLs with query strings or user paths (CLAUDE.md rule 3); the screenshot is of the app window only (`PrintWindow`), as in M2.9.
   - Runner: `windows-latest` has an interactive desktop session for the job. If a run finds none, the suite skips with a clear reason rather than failing, and the nightly report says so.
7. **Real Kasi in the browser tests (13c).**
   - `HarnessOptions` gains `RealApp`: the harness serves pages and the test server only, and the native host's `AppLauncher` finds the real `Kasi.exe` next to the host, built from `Kasi.App` and copied there by the test fixture. The browser, the extension, the host and the pipe are unchanged; only the far end changes.
   - Cases: `TC-BRW-001` to `004` (intercept, ack, bypass, exclusions) against the real `addDownload` handler, `TC-BRW-005` (menu, batch, picker), `TC-BRW-008` (clipboard on and off), and the refresh-link round trip.
   - **M2.12:** a page behind the test server's login sets a cookie; the extension adds the download with the cookies; the real app downloads the file and its SHA-256 matches; afterwards `job_secret` holds nothing for the job and the app log has no cookie or header text.
   - **Endpoint isolation:** the host must reach the test instance, not a Kasi a developer is running. The host (Native AOT) will read `KASI_ENDPOINT_SUFFIX` the same way the app does and pass it to `KasiPipeNames`. This is a small change in `Kasi.NativeHost` with its own test, and it stays inert when the variable is absent. On CI no other Kasi exists, so the suffix is a developer-machine safety.
   - Schedule: the existing PR job (Chromium, stub) is unchanged; the real-app mode runs **nightly** in Chromium and Firefox, in the job of `extension-e2e.yml` that already runs then, so the pull request time does not grow.
8. **Dependencies.** FlaUI (MIT) is added to `Directory.Packages.props` with the other test packages. Nothing else is new. The licence check in CI stays green.
9. **Known limits, written down not hidden.** UIA cannot always reach the shell's tray menu, toasts and the Mica backdrop. Those stay in the manual list (`docs/qa/browser-interception.md` and the M4 installer checks). The ADR records exactly which of them each test covers.

## 3. Tests per PR

- **13a:** `Kasi.App.UiTests` with the launcher (`AppProcess`: start, wait for the main window, close, kill on timeout and collect the log), the `TestServer` fixture, and the three flows above. A unit test for the launcher's timeout and clean-up so a hung child never leaks into the next test. Mutation check: break the Add dialog's Add command (no job created) and the Add flow must fail; make Pause a no-op and the pause flow must fail.
- **13b:** the remaining flows. Mutation checks: the link picker hands the batch over without the filter, the scheduler window does not save, Quit does not end the process.
- **13c:** the host's suffix test; the real-app mode of the browser suite with the cases above. Mutation checks: the real handler acks without creating the job, the cookie is not stored, the cookie is not deleted on completion.

## 5. Risks

| Risk | Handling |
| --- | --- |
| The runner has no usable desktop, or focus changes break a test | UIA patterns instead of input simulation; one probe test first (13a) so the question is answered before more is built; a skip with a reason rather than a red build |
| Slow or flaky start-up on a loaded runner | wait on the window appearing, not on time; a 30 s ceiling; the app log attached on failure |
| A test leaves `Kasi.App.exe` running | every start is wrapped so the process tree is killed in `DisposeAsync`; the suite fails if a stray process remains |
| Tests find a developer's own running Kasi | per-test endpoint suffix and data folder (decision 3), and the host change of decision 7 |
| FlaUI cannot see an Avalonia control | the app already sets `AutomationProperties.Name` on interactive controls; a missing one is a bug in the app and is fixed there, which is also an accessibility gain (TC-UI-007) |
