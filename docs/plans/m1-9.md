# M1.9 Plan — Checkpoint and resume (`Kasi.Engine` + `Kasi.Data`)

- **Phase:** M1 — Download engine, resume, bandwidth (`plan.md` section 4.1)
- **Requirements:** `KASI-RES-001`, `KASI-RES-002`, `KASI-RES-003`, `KASI-RES-006` (TRD 6.5, 11.3; ADR 0003, ADR 0004)
- **Test cases:** `TC-RES-001` to `TC-RES-006`, `TC-RES-011` (fault-injection halves remain M1.14)
- **Status:** implemented on `feature/m1-9-checkpoint-resume`; integration evidence is in review.

## 1. Scope

The M1.7 runner can resume when a caller already has a `Segment` list; M1.9 makes that state durable during a live transfer:

- every 2 s, and on pause/shutdown/failure, snapshot the scheduler, flush the part file, persist a changed segment structure, then record the flushed cursors;
- never record a cursor when the part-file flush failed;
- persist the probe's final URL, filename, size, ETag and Last-Modified so a restart has everything `ResumeAsync` needs;
- reload the segment rows and resume with `If-Range`; a changed file returns `FileChanged` and the caller restarts;
- preserve the `.kasipart` file and a durable snapshot on pause, cancellation, disk full and checkpoint failure.

Single-stream (`/norange`, `/chunked`) downloads are not checkpointed; they have no resumable segment cursors.

## 2. Design

**`SegmentCheckpointCoordinator`** (internal, Engine):

1. Take an atomic `(segments, StructureVersion)` snapshot from the scheduler.
2. Call `PartFileWriter.FlushAsync`; if it fails, return/throw without recording anything.
3. If the structure version changed, call `ISegmentRepository.ReplaceAsync` with that snapshot.
4. Call `ICheckpointWriter.Record` for every segment, then `FlushAsync` to commit.

The snapshot is taken **before** the flush and the records are written **after** it. `SegmentScheduler.GetCheckpointSnapshot()` reads the list and version under one lock, so a split cannot land between the two reads and leave the new segment unpersisted.

**Runner integration:** `HttpTransferOptions` gains `CheckpointJobId`, `CheckpointWriter`, `SegmentRepository`, `JobRepository` and `CheckpointInterval` (2 s by default). The runner persists the initial structure before workers start, runs the coordinator alongside the workers, stops it before the final checkpoint, and takes the final snapshot/flush on every failure or cancellation path. A checkpoint failure is returned as `TransferErrorKind.CheckpointError`; a part-flush failure stays a `DiskError`/`DiskNotEnoughSpace`.

**Job metadata:** after a successful probe, the runner updates the job row with the final URL, resolved filename, total bytes, ETag, Last-Modified and resumability. `CheckpointWriter` and `SegmentRepository` continue to own `done_bytes`.

**Ownership:** the caller starts `CheckpointWriter` before the runner (its contract already requires `Start`); the runner only records and flushes. Job-state transitions remain the engine facade's job (M1.13).

## 3. Verification

- `TC-RES-002`: checkpointed download, cancel/pause, reload segment rows from SQLite, `ResumeAsync` completes with the expected SHA-256; job row carries the validators.
- `TC-RES-001`/`TC-RES-005`: `/mutable` changed between sessions returns `FileChanged`, preserves the part, then a fresh download matches the new content.
- `TC-RES-006`: `/mutable` changed mid-session returns `FileChanged` and leaves the part file.
- `TC-RES-011` (smoke): a failed `FlushFileBuffers` never records a cursor.
- Structure split rows are persisted before their progress.
- Kill-loop/power-cut (TC-RES-001/003/011 full) and the reboot VM case remain M1.14.
