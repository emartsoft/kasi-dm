## 1. Scope and decisions

The harness proves the TRD's central promise: no finished byte is ever lost and no corrupt file is ever reported as complete (TPL 7). The suites and pass conditions are TPL 7.1; this plan decides how they are built and where they run.

- **The project already exists.** `tests/Kasi.FaultInjection` was created in M1.13c as the kill-loop child (command line: database, job id, bytes per second) and `KillLoopSmokeTests` already kills it three times. 14a grows that project into the harness (a `--suite` command router, shared helpers, the report) and turns the smoke test into a thin caller of the same code with a few iterations. No second child and no second smoke test.
- **Seeds reproduce the schedule, not the outcome.** Every suite takes `--seed` (or picks one and prints it first). The seed fixes kill delays, mutation points and toxic schedules; timing and the OS still vary, so a failure report carries the seed, the schedule and the logs, and "reproducible" is promised only for the schedule.
- **Three places to run.** PR CI runs only fast smoke versions (a few iterations, small files). The full nightly suites run as separate jobs of one scheduled workflow on `main` (a matrix, one suite per job, so no job nears the 6 h limit). The Hyper-V suites run on the dedicated host only (2.7).
- **No secrets and no URLs in output** (CLAUDE.md rule 3): reports and logs carry job ids, suite names, seeds, counters and hashes, never URLs with queries or paths of the user.
- **No production behaviour change except one test-only hook** (2.2).

## 2. Design

### 2.1 14a — Project, report and shared pieces

- `Kasi.FaultInjection` references `Kasi.Core`, `Kasi.Data`, `Kasi.Engine` and `Kasi.TestServer`. `Program.cs` becomes a router: `--suite kill-loop|commit-kill|server-mutation|disk-pressure|storage-stall|network-soak`, `--iterations`, `--seed`, `--output <dir>`, plus the existing `--worker` mode for the child (arguments extended compatibly).
- **Report** (`Reporting/FaultReport.cs`, `ReportWriter.cs`): `fault-report.json` and `summary.md` with suite, seed, iterations, failures with their logs, duration and the SHA-256 results (TPL 7.3). The process exit code is non-zero when any iteration fails.
- Unit tests: report serialisation and the Markdown table, the seeded schedule (same seed, same delays).

### 2.2 14a — Kill loop and commit kill (`TC-RES-001`, `TC-RES-011`)

- **Iteration = one kill.** The orchestrator starts the child on a throttled download (so it lasts minutes, not seconds), kills it with `Process.Kill(entireProcessTree: true)` at a seeded random time between 1 and 30 s, restarts it (the engine recovers and resumes) and repeats; when a download completes it is verified and a new one starts. 200 kills is therefore about 60 complete 4 GiB downloads a night, written to the D: drive of the runner.
- **Refetch bound (`KASI-RES-001`).** Per iteration the test server's `BytesServed` (reset at the start of the iteration) minus the checkpointed progress gained must be at most `2 s × connections × per-connection rate` plus an allowance for bytes already in socket buffers (1 MiB per connection; the server counts bytes it handed to the kernel that the throttled child had not read). A resume that starts over fails this bound by a wide margin.
- **Commit kill.** A test-only hook on `CheckpointWriter` (`internal Action? BeforeCommit`, null in production, visible to the child through `InternalsVisibleTo`) runs inside the open transaction: it creates a marker file and blocks, and the orchestrator kills the child when the marker appears, so the kill lands during a commit. 100 iterations.
- After **every** kill: the database opens, `PRAGMA integrity_check` returns `ok`, recovery runs, and the finished file's SHA-256 matches. Otherwise the iteration fails.

### 2.3 14b — Server mutation (`TC-RES-005`, `TC-RES-006`)

- 50 iterations, each its own job on `/mutable/{id}`. Between sessions: download part, pause, mutate, resume. Mid-session: mutate at a seeded point while leases stream. At most two mutations per job, because the engine's restart cap is two (the third change fails the job by design, covered by an engine test).
- Pass: every change detected (`JobRestarted`), and the finished file's SHA-256 equals one complete version of the content, never a mix.

### 2.4 14b — Disk pressure (`TC-ENG-015` resilience)

- 20 iterations on a 2 GiB VHD (`New-VHD`, `Mount-VHD`, format, mount). The download is larger than the free space; the job must pause with `NotEnoughSpace` without damaging the part file or the checkpoints; space is freed after 30 s; resume completes and verifies.
- Mounting needs elevation: the suite skips with a clear message when it is not elevated (and in PR CI), and runs in the nightly job, where the existing VHD integration test already works.

### 2.5 14b — Storage stall

- 10 iterations. The existing `WriteFaultInjector` is used to delay writes by 5 s. The test sets `ReadStallTimeout` to about 1 s, so it **fails if the stall guard runs while the engine writes** (M1.11 arms it only around the network read). Pass: no `TransientNetworkError`, the download completes and verifies.

### 2.6 14c — Network chaos soak (`TC-RES-004`)

- `ToxiproxyClient` (`HttpClient` against the Toxiproxy REST API: create and delete proxies, add and remove toxics, reset) with unit tests against a fake `HttpMessageHandler`, so PR CI never needs the daemon.
- **Daemon source.** The soak workflow downloads the pinned Windows Toxiproxy release and verifies its SHA-256 before running it; the Ubuntu/Testcontainers route stays an option for M1.16.
- 50 jobs over up to 2 hours with seeded toxics: latency jitter 100 to 500 ms, throttling down to 64 KB/s, resets, and 30 s partitions. Pass: all 50 verify; no job stays in `Downloading` with zero throughput for more than 2 minutes (sampled from the progress events); jobs paused by the engine because of the partition resume after it.

### 2.7 14d — Hyper-V power cut and the nightly workflows

- `scripts/fault-injection/Invoke-HyperVPowerCut.ps1` for the dedicated host (TPL 3.4): start the guest, run the worker in it through PowerShell Direct, read progress from the guest's database, `Stop-VM -TurnOff` at about 40% and also during a commit (using the hook from 2.2), power on, check `PRAGMA integrity_check`, resume, verify. 20 iterations for `TC-RES-003`; `TC-RES-002` (clean pause, exit and reboot, then resume) is covered by the engine's pause and resume tests and the weekly checklist, not scripted. The guest side is `--scenario power-guest` (phases run, progress and verify), so it also runs on a developer machine with a process kill standing in for the power cut. The set-up (guest, checkpoint, account, runner labels, secrets) is in `docs/fault-injection.md`.
- **These runs are owner evidence.** They cannot be dry-run on a GitHub-hosted runner. The workflow for them is `workflow_dispatch` and `schedule` on `main` only, on a self-hosted runner label, and **never on `pull_request`** (a self-hosted runner on a public repository must not run code from pull requests).
- `.github/workflows/nightly-faults.yml` on GitHub-hosted Windows: a matrix with one job per suite (kill loop, commit kill, server mutation, disk pressure, storage stall, and the soak from 14c), each uploading `fault-report.json` and `summary.md`. `plan.md`'s M1.16 keeps only the "three consecutive nights" gate check.
- **Sleep/hibernate** (TPL 7.1, manual, weekly, 5 iterations) is a documented checklist in the runbook, not automation.

## 3. Verification

- **PR CI (fast):** `FaultReportTests`, seeded-schedule test, `ToxiproxyClientTests` (fake handler), the three-kill smoke test through the shared harness code, a 3-iteration server-mutation run, a 2-iteration storage-stall run.
- **Nightly:** kill loop 200, commit kill 100, server mutation 50, disk pressure 20, storage stall 10, soak 1 run of 50 jobs; reports published as artifacts; three green nights for the engine gate.
- **Owner:** power cut 20 (+ the clean reboot mode), sleep/hibernate weekly.
- Mutation checks for the harness itself: a resume that restarts from byte 0 fails the refetch bound; skipping the hook makes the commit-kill timing test fail; a stall guard armed around writes fails the storage-stall suite.
- Build, full tests and `dotnet format --verify-no-changes` for each PR.
