## 1. Scope

M1.11 shapes the download rate with a two-level token bucket (TRD 6.7): one global bucket shared by every job and one optional bucket per job. A worker takes tokens from both before each 16 KiB network read.

- **Capacity is a quarter second of the rate** (at least 16 KiB), so speed stays smooth instead of bursty after an idle spell.
- **A bucket starts empty.** A full start bucket would let the first quarter second through at once and add 2.5% to a 10 s measurement, half of the 5% tolerance.
- **Rate changes apply at once, including to workers that are already waiting** (`KASI-BWL-001`, `TC-BWL-001`).
- **Nothing is lost when a read does not complete:** unread tokens are refunded after a short read, an exception or a cancellation.
- **Throttling must not weaken resume safety** (`KASI-NFR-007`): a long limiter wait never leaves received bytes unflushed for longer than the write-buffer age budget.
- **Torrent groundwork** (`KASI-TOR-005`): the global bucket offers a non-blocking, all-or-nothing `TryAcquire` so the M4 MonoTorrent adapter can draw from the same limit.

Out of scope: where the limits are stored and changed (the `speed_limit_bps` columns already exist; the engine facade, M1.13, and the tray, M2, wire them), scheduled speed profiles (`KASI-BWL-003`, M3), fairness between jobs (see 2.3).

## 2. Design

### 2.1 `TokenBucket` (`src/Kasi.Engine/TokenBucket.cs`)

One thread-safe bucket, driven by `TimeProvider.GetTimestamp()`.

- `long? BytesPerSecond { get; set; }`: null or zero or less means unlimited (a synchronous fast path with no lock and no allocation). Setting a rate sets the capacity to `max(16 KiB, rate / 4)`; going from unlimited to limited starts the bucket empty.
- **The balance can go negative** (debt). `Reserve(bytes)` debits the balance at once and returns the point in cumulative-refill terms at which the debit has been paid back. Cumulative refill is a monotone counter that grows by `elapsed × current rate`, so a rate change re-times every waiter on its next look.
- `WaitAsync` waits in slices of at most 250 ms and re-reads the rate each time. A waiter therefore finishes within one slice of a change to unlimited or to a faster rate (`TC-BWL-001`).
- A requested size larger than the capacity is allowed (it simply creates more debt).
- `Refund(bytes)` adds tokens back, never above the capacity. A reservation cancelled while waiting is refunded by `WaitAsync` itself; waiters queued behind it may wait one slice longer, which is accepted.
- `bool TryAcquire(int bytes)`: takes tokens only if the whole amount is available, never goes negative.

### 2.2 `BandwidthLimiter` (`src/Kasi.Engine/BandwidthLimiter.cs`)

`BandwidthLimiter(TokenBucket? global, TokenBucket? job)`; `IsLimited` is true when either bucket is limited (read on every read, so a limit set mid-transfer takes effect).

- `BandwidthTicket Reserve(int bytes)`: debits **both** buckets (allowing debt) and returns a small struct holding both completion points and `ExpectedDelay`, the larger of the two waits.
- `ValueTask WaitAsync(BandwidthTicket, CancellationToken)`: waits until both buckets have paid back their debit; refunds both on cancellation.
- `ValueTask AcquireAsync(int bytes, CancellationToken)`: `Reserve` + `WaitAsync` (for tests and the torrent adapter).
- `void Refund(int bytes)`: returns tokens to both buckets.
- **The global bucket is first come, first served** with no fairness between jobs. A job's share of the global rate follows its number of waiting workers, so the live tests give competing jobs the same connection count. Per-job fair queuing is not promised.

### 2.3 Runner integration (11b: `HttpTransferRunner`, `HttpTransferOptions`)

`HttpTransferOptions` gains `BandwidthLimiter? BandwidthLimiter`. In `ReadLeaseAsync` and in the probe-stream and single-stream loop (`ReadBodyAsync` path), when the limiter is limited, each read is:

1. `n = min(window.Length, 16 KiB)`; `ticket = limiter.Reserve(n)`.
2. **Flush before a long wait:** if `ticket.ExpectedDelay` is longer than half of `WriteBufferMaxAge` and the buffer holds bytes, call `FlushPendingAsync` first. `PooledPartWriteBuffer` checks the age limit only when the next read arrives ([PooledPartWriteBuffer.cs](../../src/Kasi.Engine/PooledPartWriteBuffer.cs)), so without this rule a wait of seconds leaves up to 256 KiB per worker unwritten and unrecorded, beyond the 2 s loss budget.
3. `await limiter.WaitAsync(ticket, cancellationToken)`.
4. **Only then** `stallGuard.Reset()`, so the 30 s read-stall timer measures the network and never the limiter wait.
5. `read = await body.ReadAsync(window[..n], stallGuard.Token)`; if the read throws, `limiter.Refund(n)` and rethrow; if `read < n`, `limiter.Refund(n - read)`.

When the limiter is null or unlimited the loop reads the whole window exactly as today (no extra allocation, no pacing).

**Endgame duplicates cost real bandwidth under a cap** (2 MiB at 200 KB/s is 10 s). When the limiter is limited at the start of a transfer, the runner sets `MaxEndgameDuplicateBytes` to 0 for that run; a limit set later does not change it.

## 3. Verification

### 3.1 Unit tests with `FakeTimeProvider` (11a: `TokenBucketTests`, `BandwidthLimiterTests`)

- Pacing: acquiring past the balance waits exactly `shortfall / rate`; a bucket starts empty; an idle bucket never holds more than the quarter-second capacity.
- Rate change reaches a waiter: a worker waiting 16 s at 1 KB/s finishes within one 250 ms slice after the rate becomes unlimited, and finishes sooner after a rise to 500 KB/s (`TC-BWL-001`).
- Refund: a refund brings the next acquire forward and never lifts the balance above the capacity; a cancelled `WaitAsync` returns what it reserved (a following acquire is not delayed by it).
- Two levels: the slower bucket sets the pace; an unlimited bucket adds no delay; a request larger than the capacity completes (debt).
- `TryAcquire`: all-or-nothing, never negative, and a failed attempt takes nothing.
- Concurrency: eight tasks drawing together move the aggregate bytes at the configured rate, with no lost or duplicated tokens.
- Mutation checks: no slicing (the waiter test fails), refund on cancellation removed, empty start replaced by a full start.

### 3.2 Integration tests (11b: `HttpTransferBandwidthTests`, `Category=Integration`, `TC-ENG-024`)

Measured at the server with `TestServerMetrics.BytesServed`, between 2 s and 12 s after the start, so the flush lag of the write buffers (up to 8 × 256 KiB) and the initial socket buffers do not enter the result.

- **A — global 500 KB/s, 8 connections:** 475 to 525 KB/s.
- **B — per-job 200 KB/s next to an unlimited job on the same server:** the limited job holds 190 to 210 KB/s and the unlimited one is at least 10 times faster (relative, not an absolute MB/s bound, so a slow runner cannot fail it).
- **C — two jobs, 4 connections each, global 500 KB/s, job A capped at 200 KB/s:** A within 10% of 200 KB/s, total within 5% of 500 KB/s.
- **Dynamic change:** start at 200 KB/s, raise to 500 KB/s after 4 s; the following window (after a 1 s settle) holds 475 to 525 KB/s.
- **Flush before a long wait (`KASI-NFR-007`):** global 16 KB/s, 4 connections, 6 s; the flushed total (`TotalWritten` via the scheduler tick) is at least 70% of what the cap allows. Without the flush rule up to 64 KiB of the 96 KB stays unwritten.
- **Stall guard:** global 8 KB/s with 8 connections (a worker waits longer than a 1 s `ReadStallTimeout`): no stall failure, no retry, SHA-256 of a small file matches.
- **Endgame under a cap:** a capped run of a small file serves at most the file size plus one lease of re-requested bytes (no duplicate tail); an uncapped run is unchanged.
- **Refund:** a cancelled capped download frees its tokens (a second job started at once reaches its rate without a delay from the first).
- Every download test checks SHA-256. Mutation checks: stall reset before the wait, flush rule removed, endgame rule removed, refund on exception removed.

### 3.3 Micro-benchmarks (11a: `bench/Kasi.Bench/BandwidthLimiterBenchmarks.cs`)

- Unlimited fast path: a few nanoseconds and 0 B.
- Limited, tokens available (no wait), 1, 8, 16 and 32 threads: 0 B per acquire.
- Limited, waiting path: reported per wait. `Task.Delay` allocates, so this path is **not** claimed to be allocation-free; the rule (no per-chunk allocation) is held for the unlimited and the token-available paths.
