## 1. Scope and decisions

Four P2 capabilities from `plan.md` section 4.1, split so each can merge and be reviewed alone. FTP is the largest and riskiest part and does not hold up the other two.

- **Tests run on in-process servers on the Windows CI leg.** GitHub Windows runners cannot run Linux containers, and the Ubuntu leg with Squid, Dante and vsftpd conformance tests is M1.16 ("CI growth"). The M1.12 gate is therefore the in-process proxy and FTP servers in `Kasi.TestServer`; container conformance moves to M1.16 and the `plan.md` rows for M1.12 and M1.16 are updated to say so.
- **Secrets stay out of URLs, options dumps and logs** (`KASI-NFR-013`, CLAUDE.md rule 3): FTP and proxy credentials live in the job's `JobSecret` (DPAPI, M1.10), never in `job.url` or a `ProxyUri`. A failure text never contains a credential.
- **TLS validation stays on** (M1.7 rule): no accept-any, no bypass setting. Tests pin the generated test root only.
- **One transfer engine.** FTP does not get its own runner; it plugs into the segmented transfer loop through a transport seam (12c), so checkpoint ordering, retry, stall guard, bandwidth limiting and checksums are written once.

## 2. Design

### 2.1 12a — Checksum verification (`KASI-ENG-012`, `TC-ENG-020`)

- **`ExpectedChecksum`** (`src/Kasi.Engine/ExpectedChecksum.cs`): `Algorithm` (`Md5`, `Sha1`, `Sha256`) and a normalised lower-case hex string. `TryParse(string? algo, string? hex)` accepts `md5`, `sha1`/`sha-1`, `sha256`/`sha-256` in any case and the matching job columns (`checksum_algo`, `checksum`). `HttpTransferOptions.ExpectedChecksum` carries it. **`Validate()` rejects a hex string of the wrong length or with non-hex characters up front**, so a typo never costs a 4 GB download.
- **`ChecksumVerifier.ComputeAsync(path, algorithm, ct)`** returns the lower-case hex hash, reading the sealed part file through `IncrementalHash` in 256 KiB reads (no whole-file buffer), cancellable. MD5 and SHA-1 need justified CA5350/CA5351 suppressions: they are used only to compare a published checksum, never to protect anything. No constant-time comparison (a published hash is not a secret).
- **One finalisation helper** used at **every** commit site (empty file, single stream, segmented; FTP in 12c): after `SealAsync` succeeds and **before** `CommitAsync`, compute and compare (TRD 6.5: seal, verify length and checksum, then rename). Cancellation during verification returns `Cancelled` with the part file kept.
- **Mismatch policy.** The transfer returns `TransferFailed { ErrorKind = TransferErrorKind.VerificationFailed }` with `Detail = "Checksum mismatch: expected <hex>, computed <hex>"`, no final file, and the sealed part file kept for inspection. The part file is complete, so a plain resume would only fail the same way: the **retry is a fresh download** after the caller deletes the part file and calls `IJobRepository.ResetProgressAsync` (the job-state side, "Verification failed", is the engine facade's, M1.13; 12a proves the engine side with a retry test).

### 2.2 12a — Duplicate detection (`KASI-ENG-013`, `TC-ENG-021` engine half)

- **`DuplicateDetector.CheckAsync(IJobRepository jobs, Uri url, string folder, string fileName, ct)`** uses the existing `IJobRepository.ListAsync` (no new repository member) and returns `DuplicateCheckResult { ExistingJob, TargetFileExistsOnDisk, SuggestedFileName, AvailableActions }`. The UI prompt is M2; the engine returns which of **Resume** (an unfinished, resumable job with this URL), **Overwrite** and **AutoRename** are legal.
- **URL normalisation** is spelled out: scheme and host lower-cased, default port dropped, fragment dropped; path and query compared as given (a signed URL with a new `exp` is a different URL, so a job is **also** matched on the same folder plus file name).
- **Name conflicts** consider another job's target path and its `<name>.kasipart`, and a file already on disk.
- **AutoRename** gives `name (1).ext`, `name (2).ext`, keeps multi-part extensions together (`archive (1).tar.gz`) and stays within `FileNameSanitiser.MaxLength` (200).
- **Overwrite** is not a deletion: it sets the existing `HttpTransferOptions.OverwriteDestination`, so the old file is replaced only at commit.
- The check and the add are two steps; serialising them is the facade's job (M1.13) and is noted in the ADR. Nothing is logged with a URL query.

### 2.3 12b — Proxies (`KASI-ENG-011`, `TC-ENG-019`)

- **First test is a spike:** which proxy forms `SocketsHttpHandler` supports. "HTTPS proxy" is defined as an HTTP proxy used with a `CONNECT` tunnel for an HTTPS origin, plus a TLS connection **to** the proxy only if the spike shows the handler supports it; the plan and ADR record the outcome.
- **`ProxySettings`** on `HttpTransferOptions` (per transfer; `HttpHostPoolOptions` is runner-wide): `Mode` (`System` default, `None`, `Custom`), `Uri` (`http://`, `https://`, `socks5://`; no userinfo) and a bypass list. Credentials are `JobSecret.ProxyCredentials` (new `HttpCredentials?`, redacted `ToString` like the others). `HttpHostPool` applies the proxy to every lane; `System` is what the handler already does today and `None` forces a direct connection. The HTTPS proxy spike passed with the .NET 10 handler and an in-process TLS proxy.
- Proxy credentials are answered by the handler and are never sent to the origin; the origin-scoped credential rules from M1.10 are unchanged.
- **Test proxy (`tests/Kasi.TestServer/Proxy/`):** in-process HTTP forward proxy, `CONNECT` tunnel and SOCKS5 (RFC 1928, username/password RFC 1929), optional Basic proxy auth, with counters (connections, `CONNECT`s, SOCKS handshakes, bytes relayed, auth failures). "Direct connection blocked" (TPL) is shown with a host name **only the proxy resolves** (`kasi-origin.test` mapped to the test server; the generated test certificate gains that name), so a direct attempt cannot succeed.

### 2.4 12c — FTP and FTPS (`KASI-ENG-002`, `TC-ENG-022`)

- **Transport seam first (refactor-only commit, all existing tests green and untouched).** The parts of `HttpTransferRunner`'s segmented loop that are HTTP-specific (probe, open a lease's stream and check it, map errors to a `TransferFailure`) go behind a small internal interface with the HTTP implementation moved as is. FTP is the second implementation. FTP does **not** copy checkpointing, retry, stall guard, bandwidth limiting or finalisation. Reads use `ReadLimitedAsync`, so reads are the whole window without a cap and 16 KiB slices under one.
- **FTP implementation (`FluentFTP` 55.1.0):** passive data connection (EPSV then PASV, no `AutoConnect`), `TYPE I`, `SIZE`, `MDTM`, `REST <offset>`, one connection and one segment (`MaxConnections = 1`; FTP has no end-of-range, so the lease stream is closed at its end).
- **URL and credentials.** `FtpUrl.StripUserInfo(Uri)` returns the clean URL and the credentials, which go to `JobSecret.Credentials`; anonymous login is the default. The engine rejects an `ftp://user:pass@…` URL that reaches it unstripped, with a message that does not repeat the password.
- **Security modes.** `ftp://` is plain text and is never upgraded silently. `ftps://` is **explicit** TLS (`AUTH TLS` on port 21); `ftps://host:990` is implicit. A requested TLS session never falls back to clear text. Certificate validation uses the OS store; tests pin the generated root through FluentFTP's `ValidateCertificate` event with a chain build against that root, never "accept any".
- **Resume validity.** FTP has no ETag: identity is **size (`SIZE`) plus `MDTM`** (stored as `last_modified`). A change in either returns `FileChanged`. A server without `REST STREAM` or without `MDTM` makes the job non-resumable (restart from byte 0, like `/norange`).
- **Errors** map onto the existing classification: authentication failure is `AuthRequired` (no retry), `550` is permanent (like 404), `421`/`426`, resets and timeouts are transient.
- **Test server (`tests/Kasi.TestServer/Ftp/`):** in-process FTP serving `GeneratedContent` (`USER/PASS`, `FEAT`, `TYPE`, `SIZE`, `MDTM`, `EPSV/PASV`, `REST`, `RETR`, `QUIT`, and `AUTH TLS`/`PBSZ`/`PROT P` for FTPS), with counters (bytes sent, `REST` offsets seen) and a chaos hook that drops the data connection after N bytes. **FTPS data-channel TLS is spiked first**; if it is not workable in process, FTP ships with plain-FTP integration tests and FTPS is covered by vsftpd in M1.16, recorded in the ADR.

## 3. Verification

**12a**
- `ChecksumVerifierTests`: MD5, SHA-1 and SHA-256 of known `GeneratedContent`; case-insensitive hex; `Validate()` rejects wrong length and non-hex; unsupported algorithm names.
- `ChecksumIntegrationTests` (`TC-ENG-020`): correct SHA-256, MD5 and SHA-1 complete and commit (single stream, segmented, empty file); a wrong hash returns `VerificationFailed`, keeps the part file and creates no final file; cancelling during verification keeps the part file; after `ResetProgressAsync` and deleting the part, a fresh download with the right hash completes.
- `DuplicateDetectorTests`: URL normalisation cases; same folder and name with a different signed query; another job's target and `.kasipart`; a file on disk; `AutoRename` counters, `.tar.gz`, the 200-character cap; legal actions per case; `Overwrite` replaces only at commit.
- Mutation checks: skip the verification at one commit site; skip the up-front hex check; compare before `SealAsync`.

**12b** — `ProxyIntegrationTests` (`TC-ENG-019`): HTTP origin through the HTTP proxy, HTTPS origin through `CONNECT`, HTTP origin through SOCKS5, Basic proxy auth good and bad (no retry loop on bad), all with SHA-256; the virtual host cannot be reached directly; proxy counters prove the traffic; `Mode.None` bypasses a proxy; proxy credentials never reach the origin and never appear in a failure text.

**12c** — `FtpTransferIntegrationTests` (`TC-ENG-022`): 16 MiB passive download with SHA-256; FTPS explicit if the spike allows; data connection dropped mid-way then resumed with `REST` from the saved cursor (the server's `REST` offsets and bytes sent prove nothing was fetched again); changed size or `MDTM` returns `FileChanged`; no `REST`/`MDTM` support means non-resumable; bad login is `AuthRequired` without retries; checksum verification, bandwidth cap and the stall guard work for FTP through the shared loop; an unstripped `ftp://user:pass@` URL is rejected. The HTTP suite passes unchanged after the seam commit. The TPL's 1 GiB runs (passive and FTPS) are nightly/M1.16 evidence.

All download tests verify SHA-256; unit tests use `FakeTimeProvider` where time matters. Build, full tests and `dotnet format --verify-no-changes` for each PR.
