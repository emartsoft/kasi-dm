# M1.8 Plan — Errors and retry (`Kasi.Engine`)

- **Phase:** M1 — Download engine, resume, bandwidth (`plan.md` section 4.1)
- **Requirements:** `KASI-RES-004`, `KASI-RES-002`, `KASI-ENG-007`, `KASI-ENG-008`, `KASI-ENG-009`, `KASI-RES-005` (TRD 3.2, 6.6; ADR 0006)
- **Test cases:** `TC-RES-007`, `TC-RES-008`, `TC-RES-009`, `TC-RES-012`, `TC-ENG-015` (job-level pause/resume half)
- **Status:** merged in PR #23; job-level disk-full pause and offline pause/resume moved to M1.13.

## 1. Scope

The M1.7 runner deliberately stops the whole transfer on the first lease failure. M1.8 adds a retry policy and wires it around the probe and each lease while keeping the part file and scheduler alive:

- classify a failure as transient, throttled, auth/expired, permanent, file changed, offline or disk-space;
- exponential backoff with full jitter, base 1 s, cap 60 s, 10 attempts;
- honour `Retry-After` on `429`/`503` and reduce the host connection count by one;
- retry truncated/reset leases and 5xx bursts without losing flushed bytes;
- return permanent `404`/`410` and auth `401`/`403` without retrying;
- preserve `DiskNotEnoughSpace` with a durable snapshot so the caller can pause and later `ResumeAsync` (job state-machine/facade work remains M1.13);
- classify offline separately; the NLM pause-all controller belongs to the engine facade (M1.13), so the runner returns the classified outcome instead of owning global job state.

Single-stream (`/norange`, `/chunked`) downloads are not resumed by a retry: their body has no saved segment cursors. Probe retries still apply, and a failed single stream is returned to the caller to restart.

## 2. Design

**`TransferRetryPolicy`** (public, `src/Kasi.Engine/`): immutable policy with `MaxAttempts` 10, `BaseDelay` 1 s, `MaxDelay` 60 s, and a test-only deterministic jitter hook. `Decide` returns `TransferRetryDecision { Retry, Delay, ReduceConnections }`.

- Classification: `TransientNetworkError`/5xx/reset/truncation → transient; `429` and `503` with `Retry-After` → throttled; `401`/`403` → auth; `404`/`410` → permanent; `FileChanged`, certificate, disk target and `Cancelled` → no retry; `DiskNotEnoughSpace` → disk-space pause.
- Delay: `min(MaxDelay, BaseDelay * 2^(attempt-1))`, then full jitter in `[0, cap]`; a server `Retry-After` raises the delay to at least the stated value, capped at `MaxRetryAfter` (15 minutes) so a rogue multi-hour value cannot block the transfer.
- **Progress resets the budget:** a failed attempt that flushed at least `MinProgressBytes` (16 KiB) of new bytes starts the attempt count again, so a connection that dies every few hundred KiB still completes; ten failures *without* progress end the transfer. Bytes already received are written before the lease is given up (`SalvageAsync`), so the retry starts at the last byte that arrived.
- **Read-stall timeout:** a lease whose connection delivers nothing for `ReadStallTimeout` (30 s) is abandoned and retried (ADR 0004); one `StallGuard` per lease, restarted before each read.
- **Throttle window (`ThrottleGate`):** a throttling server pauses *every* worker for the Retry-After window, and only the first throttle of a window lowers the scheduler limit, so eight simultaneous 429s reduce the pool by one.

**Probe path:** `DownloadAsync` retries the initial probe (and the open-ended re-probe for an unknown total) through the same policy. A throttled probe reduces the effective `SegmentSchedulerOptions` before the scheduler is created.

**Lease path:** each worker keeps a consecutive-failure counter, resets it after a successful lease or after progress, and on a retryable failure waits the decision delay and acquires a fresh lease. The failed lease was already abandoned, so its flushed cursor remains in the scheduler and the next lease resumes from it. Non-retryable failures still cancel siblings and return a typed `TransferFailed`.

## 3. Test server additions

`ChaosProfile` gains `StatusAfterRequests`, `StatusCount`, `ResetOnRequest`, `TruncateOnRequest` and `StallOnRequest`, so a test can let the probe succeed and inject one deterministic fault into the first lease. The existing all-requests modes remain the default.

## 4. Verification

- Unit: `TransferRetryPolicyTests` with a deterministic jitter hook; classification, backoff bounds, `Retry-After`, max attempts.
- Integration (`HttpTransferRetryTests`):
  - `TC-RES-007`: a short `503` burst after the probe completes; the TPL profile (30% `503` plus a reset every 5 MiB, 32 MiB, 8 connections); and a connection that dies every 128 KiB (32 resets on one connection, more than the ten attempts) completes because progress resets the budget. SHA-256 matches in each.
  - `TC-RES-008`: a `429` with `Retry-After: 5` on the probe (elapsed ≥ 5 s, the scheduler starts with one fewer connection); and three simultaneous lease-level `429`s: no request reaches the server during the window, and the pool is reduced by exactly one (`FinalAllowedConnections`).
  - `TC-RES-009`: `404` on the first lease; `HttpStatusError` with 404 and no retry loop.
  - `TC-RES-012`: a one-request truncated lease; the next attempt completes with SHA-256.
  - reset-once variant: a one-request connection reset; the next attempt completes.
  - read-stall: a 10 s stall on one request with `ReadStallTimeout = 500 ms` completes in well under 10 s.
  - Unit: `ThrottleGateTests` (one reduction per window, window extension), the `Retry-After` cap and the progress threshold in `TransferRetryPolicyTests`.
  - Mutation checks (disable the progress reset, the stall guard, the window wait, or reduce on every throttle) each make one of these tests fail.
  - Existing `TC-ENG-015` disk-full test remains the pause/resume evidence.
- Build, full tests and `dotnet format --verify-no-changes`.
