## 2. Design

### 2.1 Start-up order (2.8a)

`Program.Main` does, in this order and nothing else before the first three: (1) take the per-user instance lock; (2) if another instance holds it, send the hand-off (2.3) and exit 0 at once, without building a host or a UI; (3) in `--tray` mode or normal mode alike, create and **start the `KasiPipeServer`** with the handler of 2.2; (4) build the generic host and the engine; (5) start Avalonia, show the main window unless `--tray`. A test starts the real `Program` path with a fake UI and asserts the pipe accepts a `hello` before the engine finished starting. `Kasi.exe` must not be a console flash: it stays a `WinExe`.

Reconcile with `src/Kasi.App/CompositionRoot.cs` (`Host.CreateApplicationBuilder`, `MainWindowViewModel`): the hosted services are added there; `Program.cs` keeps `[STAThread]` and `StartWithClassicDesktopLifetime`.

### 2.2 Browser protocol handlers (2.8b, `Kasi.App/Browser`)

A `BrowserMessageHandler` (an `IpcMessageHandler`) is the only place that knows the protocol; it calls small interfaces the engine/UI side implements, so it is testable without Avalonia:

| Message | Behaviour |
| --- | --- |
| `hello` | Reply `rules` built from settings: enabled, extension and MIME lists (a populated default: common archive, installer, document, media types, because an empty list intercepts nothing), excluded sites, bypass key, `ackTimeoutMs` 2000, and `minSizeBytes` **only** when `hello.extensionVersion` ≥ `IpcProtocol.MinSizeExtensionVersion`. A settings change broadcasts `rules` (`BroadcastAsync`). |
| `addDownload` | Create the job or queue the Add dialog (decision 5), then ack **when the request is durably accepted** (job row written, or dialog queued), never after the user's answer (TRD 9.2). The request id makes it idempotent: the same id twice gives one job and the same ack. Cookies go to `job_secret` (M1.10), never to a log. An invalid or unsupported request gets an `error`. |
| `addBatch` | Queue the picker (2.7) with the links, referrer, cookies and user agent; ack when queued. |
| `openSettings` | Show the Settings window (a skeleton: General, Browser) on the section asked; ack. |
| `mediaDetected`, `captureMedia` | `error INTERNAL` until M3 (a clear reply, not silence). |
| `refreshLink` / `linkRefreshed` | Kasi sends `refreshLink` when the refresh dialog (2.7) is confirmed; a `linkRefreshed` updates the job's URL and secrets. |
| Unknown or out-of-order | `error INVALID_MESSAGE` (the server already does this for non-`hello` first frames). |

Hosts that connect while no UI exists (`--tray` at logon) are served the same way; a message that needs a window queues it and shows the tray notification "N downloads waiting" instead of stealing focus.

### 2.3 Single instance and argument hand-off (2.8a)

- **Lock:** `Local\Kasi-<SID>` mutex (per user session). Not `Global\`.
- **Hand-off (decision 1):** a second per-user pipe `kasi-<SID>-open`, separate from the browser pipe, same ACL rules as `PipeSecurityFactory` (it is internal to `Kasi.Ipc`, so the hand-off server lives there or the factory is made public), one JSON line per launch: `{ "args": [...] }`. The first instance parses it with the same argument parser as `Program` (URLs to add, `--tray`, nothing else) and opens the Add dialog or raises the window. The second process exits 0 within a generous bound whether or not it got an answer. URLs are validated by scheme and length before use and never written to a log.
- `TC-SYS-006`: the second launch with a URL reaches the first (a real second process in an integration test), the first instance's view model has the URL, exit code 0.

### 2.4 `UiBatchDispatcher` (2.8a)

Coalesces by job id (the latest progress per job wins) and applies the set to the view models every 250 ms on the UI thread. It takes a `TimeProvider` (`PeriodicTimer(period, timeProvider)`), so the test uses `FakeTimeProvider` (already a dependency): ten thousand updates for 50 jobs between two ticks produce one apply of 50 items; no tick means no apply; disposal stops it; an exception in an apply is logged (type only) and the loop continues. No assertion on wall-clock time.

### 2.5 Settings skeleton (2.8b)

A window with General and Browser sections backed by the settings store, enough for `openSettings`, the rules (extension and MIME lists, excluded sites, bypass key, minimum size) and the clipboard switch (2.8e). Every control has an automation name (UI-010).

### 2.6 Tray and toasts (2.8c)

- **Tray:** Avalonia `TrayIcon` with total speed, Pause all, Resume all, speed-limit presets, Open Kasi, Quit; the menu is driven by a `TrayIconViewModel` so the actions are unit-tested without a native icon (G7); `TC-UI-003` checks the actions with the main window closed, against the engine facade.
- **Close-to-tray:** closing the main window hides it when a tray exists and jobs run or the setting says so.
- **Toasts:** a `NotificationService` behind an interface; a router maps activation arguments (`open-file`, `open-folder` with a job id) to commands. The unit tests cover the router and the paths (the file is opened with the default handler, the folder with Explorer selecting the file); the real toast is a manual row in `docs/qa` until the M4 installer provides the shortcut and app ID. The notification text never contains the URL, only the file name.
- **Quit (decision 4):** exits the process and closes the pipe; with `m2-5.md` decision 3 the browser will not relaunch it on a timer.

### 2.7 Dialogs and the picker (2.8d)

- **Add Download** (UI-002, TC-UI-001): URL pre-filled, file name, folder, category, queue, connections, start now or add to queue, checksum, "remember for this site" (TRD 12.1). Fields map one to one onto the created job (a test per field).
- **Duplicate prompt** (ENG-013, TC-ENG-021 UI half): `DuplicateDetector` (exists in `Kasi.Engine`) decides; the dialog offers Rename (auto), Overwrite, Resume; each path is a view-model test against a fake engine.
- **Link picker** (BRW-005, TC-BRW-005 Kasi half): a window opened from a queued `addBatch`; filters by extension and by text (matching the URL and the file-name hint, `m2-5.md` decision 1), select all or none, destination; "Add" creates one job per selected link in one batch, sharing the batch's cookies. A test selects 12 of 40 and asserts 12 jobs with the right URLs; the window stays responsive with 100,000 links (virtualised list; a test with 100,000 rows checks the view model builds in a bounded time with a generous limit).
- **Refresh-link dialog:** shown when the engine reports an expired link (the engine has `DownloadEngine.RefreshLinkAsync` for a paused job, M1.10), asks to open the referrer in the browser, sends `refreshLink` over the connected host for that browser, and cancels after a timeout.

### 2.8 Clipboard capture (2.8e, P3, decision 2 of `m2-5.md`)

Off by default. A hidden window registers `AddClipboardFormatListener`; on a text change the text is checked for a single http, https or ftp URL whose extension is on the user's list; a match opens the Add dialog pre-filled. Nothing is read when the setting is off, and the clipboard text is never logged. `TC-BRW-008`: with the setting on, copying a `.iso` link opens the dialog; off, it does not (a fake clipboard source in tests; one FlaUI check on a real clipboard).

## 3. Verification

- **Unit (xUnit, Avalonia.Headless where a control is needed):** handler table of 2.2 (rules content including the version gate and an empty-list guard, ack timing relative to acceptance, idempotent request id, error replies, cookies not logged); `UiBatchDispatcher` with `FakeTimeProvider`; argument parser; tray and notification view models; Add dialog field mapping; duplicate paths; picker filters and the 12-of-40 case.
- **Integration (`Category=Integration`):** `TC-SYS-006` with a real second process; the pipe accepts a `hello` before the engine is up (2.1); a real `KasiPipeServer` plus the real `Kasi.NativeHost` and the stub extension messages from `Kasi.BrowserHarness`'s client side answer `addDownload` with an ack and create the job in a temporary database.
- **End to end:** once 2.8b lands, the 2.4c browser suites can run against the real `Kasi.App --tray` (an additional nightly leg) instead of the stub; this replaces the stub only for the "Kasi running" group.
- **FlaUI smoke (nightly):** start `Kasi.App`, tray menu actions, Add dialog, picker; automation names present.
- **Mutation checks, each must fail a named test:** ack sent before the job exists; `minSizeBytes` sent to an old extension; an empty default list; a duplicate request id creating two jobs; the pipe started after the engine; the hand-off pipe open to another user; the dispatcher applying every event; a URL in a notification or a log line.
- `dotnet build -c Release` (warnings as errors), `dotnet test --filter "Category!=Integration"`, `dotnet format --verify-no-changes`; `Kasi.ArchitectureTests` (no Avalonia in the engine) must stay green.

## 5. Security and privacy

- Both pipes are per-user with an explicit access list (current user only, network denied); the hand-off pipe accepts arguments only and validates every URL before use.
- Cookies from the browser go to `job_secret` and are deleted with the job; no URL with a query, cookie, header or full user path in any log, toast or crash report.
- The handler treats everything on the browser pipe as untrusted input (it is already schema-validated by `Kasi.Ipc`), caps what it queues per connection (links, pending dialogs) and never acts on a message by opening anything but its own windows.
- Quit and the tray never start a browser or a process other than Kasi's own windows and the shell open for a completed file or folder.

## 6. Decisions (approved: the recommended option, the first of each, was chosen for all)

**Dependency approval:** decision 3 approves adding `CommunityToolkit.WinUI.Notifications` (MIT) and a Windows target framework for `Kasi.App` in PR 2.8c; its licence goes into the comment at the top of `Directory.Packages.props` with the others.


1. **Argument hand-off.** A second per-user pipe `kasi-<SID>-open` with its own one-line contract (**recommended**: protocol v1 and the extension stay untouched, the browser pipe keeps one purpose). **Or** a new `openUrl` message on the browser pipe (a schema and `Kasi.Ipc` change, and a registered host would be needed to send it). **Or** `WM_COPYDATA` to the main window (no window exists in `--tray` mode).
2. **Where clipboard capture lives.** In Kasi, PR 2.8e, P3 and droppable (**recommended**, see `m2-5.md` decision 2). **Or** drop `BRW-007` from M2 and keep it for M5.
3. **Toast implementation.** `CommunityToolkit.WinUI.Notifications` (MIT) with a Windows target framework for `Kasi.App` only, activation through its COM activator (**recommended**; needs your approval to add the package and the TFM change). **Or** Windows Runtime toast APIs directly from the Windows TFM, writing the activator by hand (no package, more code and risk). **Or** no toasts in M2: a tray balloon-style message only, and `UI-005` moves to M4 with the installer that provides the shortcut.
4. **What Quit does with browsers connected.** Exit completely and, with `m2-5.md` decision 3, the extension reconnects only on a download or a click (**recommended**). **Or** Quit means "close to tray" (the process stays), so the browser can always reach Kasi, and a separate "Exit Kasi" item ends it.
5. **Browser downloads: dialog or straight to the queue.** A setting "Show the Add dialog for browser downloads", on by default, off adds the job at once with the default category and queue (**recommended**; BRW-002's acceptance says Kasi's dialog opens). **Or** always the dialog (no setting).
6. **Real Kasi in the browser e2e.** After 2.8b the nightly runs the "Kasi running" browser group against `Kasi.App --tray` as a second leg, keeping the stub for the fault cases (**recommended**). **Or** keep the stub only until M5.
