## 2. Design

### 2.1 What stays and what changes

- **Single source of truth** for the manifest text stays `src/Kasi.NativeHost/Registration/com.martsoft.kasi.json` (already used by the script and by the e2e helper). The M4 installer takes the same template; a test pins that the template and the script produce the same JSON for a given set of IDs.
- **IDs live in one file**, `extension/store-ids.json` (new): `{ "chrome": ["<id>"], "edge": ["<id>"], "firefox": ["extension@kasi.martsoft.com"] }`. The script, the M2.7 packager and the allow-list test read it. Until the owner has the real IDs, the file holds the unpacked-build IDs and the script still accepts parameters.
- **Per-user keys only** (no UAC), unchanged: Chrome, Edge, Chromium, Firefox under HKCU.

### 2.2 Script changes (`Register-NativeHost.ps1`)

- `-ChromeExtensionId` and `-EdgeExtensionId` become lists (`string[]`); Chrome and Chromium use the Chrome list, Edge uses the Edge list; each manifest's `allowed_origins` carries every ID given for that browser (a store ID plus the developer ID).
- `-RegistryRoot` (default `HKCU:\Software`, decision 4) and `-ManifestDirectory` (default `%LOCALAPPDATA%\Kasi\NativeHost`) so a test can register under a private root.
- `-Unregister` removes the keys it wrote and the manifests, and nothing else. Idempotent.
- IDs are validated (`^[a-p]{32}$` for Chromium, `^[A-Za-z0-9@._-]+$` for Firefox); an empty list for a browser skips it, as today.

### 2.3 Registry tests (`tests/Kasi.NativeHost.Tests`, `Category=Integration`, Windows)

xUnit runs the script with `-RegistryRoot HKCU:\Software\KasiTest\<guid>` and a temp manifest folder, then checks: the keys exist with the right default value, the manifest has exactly the given IDs under the right property, a second run changes nothing, `-Unregister` removes everything it made and leaves a pre-existing foreign key in the test root alone. The test root is removed in `finally`. Nothing touches the real browser keys.

## 3. `TC-BRW-007` end to end

In the M2.4c harness, per browser family, with the host registered for **one** allowed extension ID:

- **Chromium:** `prepareChromiumExtension()` is called twice, producing an allowed copy and a rogue copy with different keys. The browser loads the **rogue** copy only. Its background connects to the host. Expected: the port disconnects with an error and the stub Kasi receives **no `hello`** within a generous wait, and no `Kasi.NativeHost.exe` process was started by the browser (the test counts host processes before and after by image path of the temp copy). Control: the same browser with the allowed copy connects and the stub sees its `hello`.
- **Firefox (nightly):** the add-on is installed temporarily with a different `browser_specific_settings.gecko.id` in a temp copy; the registration allows only `extension@kasi.martsoft.com`. Same assertions. The exact refusal wording is **not** asserted (it differs per browser).
- The assertion is on observable effects (no `hello`, no host process, port closed), never on an error string.

## 4. Verification

- Script tests of 2.3; a template-equality test (script output equals the template with the IDs filled in).
- `TC-BRW-007` e2e in `extension/tests/e2e/allowlist.e2e.test.ts` for both browsers, skipped locally with a reason like the other e2e suites, run in `extension-e2e.yml` (Chromium on PRs, both nightly).
- **Mutation checks, each must fail a named test:** an extra ID in `allowed_origins`; the Chromium list used for Edge; `-Unregister` leaving a key; the manifest written with a wildcard origin; the rogue copy's ID added to the allow-list.
- `dotnet build`, `dotnet test --filter "Category!=Integration"`, `dotnet format --verify-no-changes`, the extension checks.

## 5. Decisions (open: the first option of each is recommended)

1. **Where the real store IDs come from.** The owner creates the three store items as **drafts now** (a Chrome Web Store item gives its ID and a public key at once; Edge Add-ons and AMO give theirs), and the IDs go into `extension/store-ids.json` (**recommended**; the IDs are public and the allow-list is then final before M2.7). **Or** register with unpacked IDs only for M2 and revisit in M4 (the installer would then carry an unfinished allow-list).
2. **Allowed IDs per browser.** Each browser allows its own store ID plus the developer ID of the unpacked build (**recommended**: development and the nightly keep working). **Or** the store ID only, with the e2e tests registering their per-run ID through the existing helper (stricter, and the script then cannot register an unpacked build by hand).
3. **The Firefox ID and the domain.** Keep `extension@kasi.martsoft.com`, which is in the shipped manifest and ADR 0018 (**recommended**). **Or** change to the draft's `kasi@martsoft.co.ke`, which needs a manifest change, a new AMO listing and a check that the domain is the one MartSoft Solutions owns. Please confirm which domain is real either way.
4. **Registry test isolation.** A `-RegistryRoot` parameter on the script so tests use a private root (**recommended**). **Or** keep the script unchanged and have the test save and restore the real keys, as the e2e helper does (it works, but a crashed test can leave a developer's registration replaced).
5. **Firefox in `TC-BRW-007`.** Include it in the nightly (**recommended**). **Or** Chromium only and a manual row for Firefox (cheaper; the TPL says all three browsers).
