## 1. Scope and decisions

`Kasi.NativeHost.exe` is the bridge between the browser and Kasi: it speaks the browser's native messaging framing on stdin and stdout and Kasi's framing on the named pipe, and it forwards nothing it has not validated.

- **Two concurrent pumps, one writer.** The protocol is not request/response: Kasi pushes `rules` and `refreshLink` whenever it likes. The host therefore runs a stdin→pipe pump and a pipe→stdout pump at the same time, with a single serialised writer on stdout so frames never interleave. It exits when stdin closes (the browser went away), and when the pipe closes it tries to reconnect once through the launcher and otherwise exits.
- **Validation is the strict parse of `Kasi.Ipc`.** A frame is parsed into an `IpcMessage` through `IpcJsonContext`; anything the contract rejects is rejected here. The host never forwards raw bytes it did not parse.
- **Failure policy (the fuzz test's contract).**
  - A frame that cannot be trusted to be a frame (length 0, over the cap, truncated, EOF mid-frame) cannot be resynchronised: the host writes nothing it cannot frame, logs a redacted reason to stderr and **exits with a non-zero code**.
  - A well-framed message that is invalid (bad JSON, unknown type or field, wrong version, over a field cap) gets an `error` reply (`INVALID_MESSAGE` or `UNSUPPORTED_VERSION`) with a fixed text that never echoes the input, and the host **keeps running**.
  - Kasi not reachable after the retry window: `error` `APP_NOT_RUNNING`; Kasi's executable not found next to the host: `error` `APP_NOT_INSTALLED`. In both cases the extension resumes the browser's own download (TC-BRW-002).
- **Size limits (`TRD 9.3`).** browser → host 64 MiB, host → browser 1 MiB (Chrome's limit); a pipe message that would exceed 1 MiB is replaced by an `INTERNAL` error instead of a broken frame.
- **Memory.** The "under 15 MB" figure is the idle and typical private working set. A 64 MiB link-picker batch needs a buffer of that size, so large buffers are rented per message and released afterwards, and a test records the peak and the return to baseline.
- **Stdout belongs to the protocol.** Nothing else ever writes to stdout; diagnostics go to stderr or a log file under the user's profile, with the redaction helpers (no query strings, cookies or full user paths).

## 2. Design

```text
src/Kasi.NativeHost/
├── Program.cs                 entry point: wires the pieces, maps the exit code
├── Framing/
│   ├── NativeFrameReader.cs   4-byte little-endian length + payload; exact reads over partial reads; the caps
│   └── NativeFrameWriter.cs   one lock, one flush per frame
├── Relay/
│   ├── HostRelay.cs           the two pumps, the failure policy, the error replies
│   └── AppLauncher.cs         finds the sibling Kasi.exe, starts "--tray", retries the pipe with backoff for 5 s
└── Registration/
    └── com.martsoft.kasi.json host manifest template (allowed_origins / allowed_extensions placeholders)
scripts/native-host/Register-NativeHost.ps1   per-user HKCU registration for Chrome, Edge and Firefox (development; the installer does this in M4)
```

- **`AppLauncher`:** the executable is `Kasi.exe` in the host's own directory (`AppContext.BaseDirectory`), never looked up on `PATH`. If the pipe is absent it starts the process with `--tray`, then retries the pipe with exponential backoff (50 ms doubling to 500 ms) until 5 seconds have passed. It does not start a second instance while one is starting (Kasi itself is single-instance; the host only avoids hammering). `--tray` is implemented by the main app in a later M2 task; until then the launcher is exercised with a fake executable and this plan names that dependency instead of hiding it.
- **`HostRelay`** takes `Stream`s and a pipe-client abstraction, so the whole relay runs in a test process without a browser.
- **Native AOT:** `PublishAot`, single file, invariant globalization, trimming warnings as errors (`TreatWarningsAsErrors` already covers them).

## 3. Verification

- **2.2a:** `NativeFrameTests` (round trips, partial reads one byte at a time, EOF at a frame boundary versus mid-frame, the 64 MiB and 1 MiB caps); `HostRelayTests` (both directions at once, a pushed `rules` arrives while a request is in flight, the writer never interleaves two frames under concurrency, the exit and error policy above, the pipe closing mid-session); `AppLauncherTests` for **TC-BRW-002** (absent pipe → the fake executable is started with `--tray` and the message is relayed once the pipe appears; an executable that never opens the pipe → `APP_NOT_RUNNING` within 5 s plus a small margin; no executable → `APP_NOT_INSTALLED` at once; the path is the sibling file, never a PATH lookup); a test that nothing but frames reaches stdout.
- **2.2b, `TC-BRW-006`:** `NativeHostFuzzTests` feeds **100,000 seeded malformed frames in one session** (invalid JSON, truncated JSON, wrong types, unknown types and fields, duplicate properties, deep nesting, huge strings, embedded NUL and control characters, bad UTF-8, `v` values) through `HostRelay`: every one is answered with an `error` and the host is still serving at the end; a separate table-driven test covers the framing-level cases (each must end the host with a non-zero code and no partial frame). The seed is printed on failure. Memory is sampled before and after (the delta stays small) and the run is deterministic. A smaller sample (about 1,000) also runs against the **published AOT executable** over real pipes so the process boundary is covered too.
- **Nightly fuzzing (TPL 7.2):** a `HostMessageFuzz` target in `tests/Kasi.Fuzz` (the strict parser and the error mapping, 5 minutes a night in `nightly-fuzz.yml`), with its saved findings replayed as unit tests like the filename parser's.
- **Native AOT in CI:** a `ci.yml` step publishes `Kasi.NativeHost` for `win-x64` with zero warnings, asserts the single file is under 5 MB, and records the cold start (median of 20 launches) in the job summary without gating on it (the 50 ms target of the TRD is checked on the benchmark machine).
- Mutation checks: let a frame over the cap through, let a message skip the strict parse, write a log line to stdout: each must fail a named test.
- Build, full tests, `dotnet format --verify-no-changes`.
