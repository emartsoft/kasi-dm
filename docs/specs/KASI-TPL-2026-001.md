## 1. Introduction

### 1.1 Purpose

This plan states what is tested, how, where, by whom and when, and what evidence each phase gate needs. Developers use it to know which tests their code must pass; the QA lead uses it to run gate reviews.

### 1.2 Scope

In scope: every functional requirement (KASI-ENG, RES, BRW, MED, TOR, QUE, CAT, BWL, UI, SYS) and non-functional requirement (KASI-NFR) in the TRD, the browser extension, the native messaging host, the installer, portable build and update pipeline.

Out of scope: third-party libraries' own correctness (MonoTorrent, FluentFTP, FFmpeg, Avalonia) beyond the behaviour Kasi depends on, browser store review processes, and P4 requirements.

## 2. Test approach

Every P1 requirement is verified by an automated test that runs in CI; manual testing is reserved for exploratory sessions, hardware-dependent cases (wake from sleep, power loss on real disks) and usability. A requirement counts as verified only when its acceptance criterion from the TRD passes in the gate build.

### 2.1 Test levels

| Level | What it proves | Tools | Owner | Trigger |
| --- | --- | --- | --- | --- |
| Unit | Algorithms are correct in isolation: segment splitting, lease sizing, token bucket, filename sanitising, rule matching, state machine, parsers | xUnit, FluentAssertions, FsCheck | Developers | Every PR |
| Integration | Components work against real protocols and storage: HTTP/1.1, HTTP/2, FTP, SQLite, FFmpeg, MonoTorrent | Kasi.TestServer, Testcontainers | Developers | Every PR |
| Fault injection | No data loss and correct recovery under resets, throttling, server changes, disk full, kills, power loss | Chaos middleware, kill harness, Hyper-V | QA + developers | Merge to `main` |
| Fuzz | Parsers and the host survive malformed input without crash or hang | SharpFuzz + libFuzzer | Developers | Merge to `main`, 20 min budget |
| Extension | Interception, media detection, native port behaviour | Vitest; Playwright (Chromium) and geckodriver (Firefox) for the end-to-end cases | Extension developer | Unit: every PR; end to end: Chromium on PRs that touch the extension or host, both browsers nightly |
| UI | Views and view models behave; end-to-end flows work through the real window | Avalonia.Headless, FlaUI | QA | Nightly |
| Performance | Throughput, start time, memory, CPU, grid responsiveness meet KASI-NFR targets | BenchmarkDotNet, Kasi.Bench, PerfView | QA | Weekly + release candidates |
| Compatibility | Works across Windows and browser versions | Hyper-V / Azure VM matrix | QA | Each release candidate |
| Acceptance | Gate criteria met; usability targets met | Manual scripts, moderated sessions | CTO + QA | Each phase gate |

### 2.2 Techniques

- **Property-based testing** for the segmentation engine: for any file size, connection count and sequence of splits and worker completions, segments never overlap, never leave gaps, and their union equals the file (FsCheck generators in `Kasi.Engine.Tests`).
- **Checksum oracle**: every download test compares SHA-256 of the result with the source; a passing progress bar is never accepted as evidence.
- **Deterministic chaos**: fault-injection runs use a seeded random generator so a failing run can be replayed exactly from its seed.
- **Boundary values** for sizes (0 bytes, 1 byte, exactly `minSplit`, 2 × `minSplit` − 1, 4 GiB + 1, 50 GiB) and connection counts (1, 2, 32).
- **Golden files** for parsers: real-world HLS and DASH manifests (anonymised) checked into `tests/fixtures`.

### 2.3 Automation policy

- A PR cannot merge if any unit, integration or extension test fails, or if engine line coverage drops below 80% (KASI-NFR-018).
- Flaky tests are quarantined within one working day, tagged `[Trait("Quarantine", "true")]`, and fixed or deleted within one sprint.
- Tests must not reach the public internet. The only exception is the benchmark suite (section 6), which runs on a dedicated machine.

## 3. Test environments and infrastructure

All functional tests run against `Kasi.TestServer`, an in-repo ASP.NET Core server whose behaviour each test controls through a chaos profile. This makes network faults reproducible and keeps CI independent of the internet.

### 3.1 Kasi.TestServer

A Kestrel server started in-process by integration tests (and as a container for extension tests). It serves deterministic generated files, so content can be verified without storing large fixtures: byte `i` of file `seed` is `hash(seed, i / 4096)[i % 32]`.

| Endpoint | Behaviour |
| --- | --- |
| `/files/{seed}/{size}` | Range-capable file with ETag and Last-Modified |
| `/norange/{seed}/{size}` | Ignores `Range`, always returns `200` |
| `/chunked/{seed}/{size}` | No `Content-Length`, chunked transfer |
| `/redirect/{hops}/...` | Redirect chain before the file |
| `/auth/basic/...`, `/auth/cookie/...` | Requires credentials or a session cookie |
| `/signed/...?exp=` | Returns `403` after the expiry time (link refresh tests) |
| `/mutable/{id}` | File whose content and ETag can be changed mid-test |
| `/hls/...`, `/dash/...` | Generated manifests and segments, including AES-128, SAMPLE-AES and ContentProtection variants |
| `/disposition/...` | Edge-case `Content-Disposition` values (RFC 5987 `filename*`, path traversal attempts, reserved names) |

### 3.2 Chaos middleware

A test sets a profile through the `X-Kasi-Chaos` header or the control API. Profiles combine:

| Fault | Parameters |
| --- | --- |
| Connection reset | After N bytes, or probability per 64 KiB |
| Stall | Hold the connection open, send nothing, for N seconds |
| Per-connection throttle | Bytes per second for a given connection index |
| Status injection | `429` with `Retry-After`, `500`, `502`, `503`, `504` at a given rate |
| Max connections per client IP | Reject beyond N with `503` |
| Content change | Swap content and ETag after N requests |
| Truncation | Send fewer bytes than `Content-Range` declares |
| Latency | Fixed or jittered delay before first byte |

Every profile takes a `seed` so a failing run can be replayed exactly.

### 3.3 Other test services

### 3.5 Test data

Generated files cover 0 B, 1 B, 1 MiB, 100 MiB, 1 GiB, 4 GiB + 1 B and 20 GiB (sparse on the server). Real-world manifest fixtures are collected from public test streams (Apple and DASH-IF reference streams), never from commercial services.

## 4. Entry and exit criteria

Each roadmap gate in the TRD (section 16) passes only when its exit criteria below are met in a single signed build; the gate review records the build number and evidence links.

| Gate | Entry criteria | Exit criteria |

| End of M0 | Repository, CI and signing set up; Kasi.TestServer and chaos middleware merged | CI runs unit and integration stages green on an empty engine; defect tracker configured; this plan approved |
| Engine gate (end of M1) | All KASI-ENG and KASI-RES P1 cases automated | 100% of section 5.1 and 5.2 P1 cases pass; fault-injection suite (section 7) passes 3 consecutive nightly runs; benchmark median within 10% of IDM (section 6); engine coverage ≥ 80%; no open Critical or High defects in the engine |
| Internal alpha (end of M2) | Extension builds for Chromium and Firefox; UI main flows automated | All BRW, QUE, CAT, UI P1 cases pass; browser hand-off end-to-end passes in Chrome, Edge and Firefox; FlaUI smoke suite green; no open Critical defects |
| Public beta (end of M4) | MED, TOR, BWL, SYS cases automated; signed installer and portable builds produced | All P1 cases pass; at least 90% of P2 cases pass, with deferrals approved; update from previous beta build verified; DRM refusal cases pass; compatibility matrix smoke run green; no open Critical or High defects |
| v1.0 release (end of M5) | Beta ran at least 7 days with 50+ users | All P1 pass; P2 deferrals approved; all KASI-NFR targets met (section 6); crash-free sessions ≥ 99.5%; full compatibility matrix passed; extension approved in all three stores; release sign-off by CTO and QA lead |

### 4.1 Suspension and resumption

Testing of a build is suspended if the build fails to install, the engine cannot complete a basic 100 MiB download, or more than 20% of a suite fails for one root cause. It resumes on a new build that fixes the blocking defect, and the suspended suite is rerun in full.

## 6. Performance and benchmark plan

Kasi's headline claim is speed parity with IDM, so throughput is measured head-to-head on the same machine, line, file and time window, with the median of 5 alternating runs deciding the result. The engine gate needs Kasi within 10% of IDM; release needs within 5% (KASI-NFR-001).

### 6.1 Throughput benchmark protocol

1. Use the dedicated benchmark machine (section 3.4) on a wired connection with no other traffic. Record line speed with a reference speed test before each session.
2. For each source, run IDM then Kasi, alternating, 5 times each, with the same connection count (8 by default, then 16). Clear DNS cache between runs.
3. Record wall-clock time from first request to verified file, average throughput, and peak connections.
4. Run sessions at two times of day (business hours and night) to capture congestion differences on local and international links.
5. Result per source = median Kasi time ÷ median IDM time. The suite passes if the median of all sources is ≤ 1.10 (gate) or ≤ 1.05 (release), and no single source is worse than 1.25.

### 6.2 Benchmark sources

| Source type | Example | Why |
| --- | --- | --- |
| Linux ISO mirror, East Africa | KENET or other regional university mirror (Ubuntu, Debian ISO) | Local high-bandwidth path |
| Linux ISO mirror, Europe | A major European university or ISP mirror | International transit typical for Kenyan users |
| Global CDN | Large public file on a commercial CDN (for example, a GPU driver or SDK download) | HTTP/2 and CDN edge behaviour |
| Cloud object storage | 2 GiB test object on S3 or Azure Blob, signed URL | Signed URLs and per-connection throttling |
| Single-server origin with per-connection cap | Self-hosted VPS with 2 MB/s per connection limit | Shows segmentation gains most clearly |
| Range-less server | Self-hosted, ranges disabled | Confirms no regression in single-connection mode |

Exact URLs are maintained in `bench/sources.json` and reviewed monthly, because public mirrors change.

### 6.3 Resource targets

| Metric | Target | Method | Requirement |
| --- | --- | --- | --- |
| Aggregate throughput, one job, 16 connections, local 10 GbE server | ≥ 1 Gbit/s sustained | Kasi.Bench against TestServer | NFR-002 |
| Cold start to visible window | < 1.5 s | ETW trace, median of 20 starts, ReadyToRun build | NFR-003 |
| Idle private working set after 10 min | < 80 MB | PerfView / Process Explorer | NFR-004 |
| Working set with 20 active jobs | < 250 MB | Same | NFR-004 |
| CPU at 100 MB/s aggregate | < 5% of one core | Windows Performance Recorder | NFR-005 |
| UI frame time, 10,000 history rows, 20 jobs updating | < 16 ms | Avalonia render timing overlay + automated scroll | NFR-006 |
| Installer size | < 60 MB | CI artefact size check | NFR-020 |

### 6.4 Regression tracking

Kasi.Bench runs weekly against TestServer on the benchmark machine and stores results in `bench/results/*.json`. A throughput drop of more than 5% or a memory increase of more than 10% against the previous week's median opens a High defect automatically. Micro-benchmarks for hot paths (lease scheduling, token bucket, checkpoint batching) run under BenchmarkDotNet on every merge to `main`.

## 7. Fault-injection and resilience plan

The resilience suite proves the TRD's central promise: no finished byte is ever lost and no corrupt file is ever reported as complete. It runs nightly on `main` and must pass 3 consecutive nights for the engine gate.

### 7.1 Suites

| Suite | Method | Iterations per night | Pass condition |
| --- | --- | --- | --- |
| Kill loop | Start a 4 GiB, 16-connection download; `TerminateProcess` at a random time between 1 and 30 s; restart; repeat until complete | 200 kills | Every file verified; re-downloaded bytes per kill ≤ 2 s × connections × speed |
| Power cut | Hyper-V VM hard-off (`Stop-VM -TurnOff`) during download and during checkpoint commit | 20 | Database opens; `PRAGMA integrity_check` = ok; resume verifies |
| Network chaos soak | 50 jobs over 2 hours through Toxiproxy with resets, stalls, latency spikes and 30 s partitions | 1 run | All 50 verified; no job stuck in Downloading with zero throughput for more than 2 minutes |
| Server mutation | Content swapped at random points on `/mutable/` | 50 | Every change detected; no file contains bytes from two versions |
| Disk pressure | Download to a 2 GiB VHD that fills during transfer; space freed after 30 s | 20 | Job pauses, then completes and verifies |
| Storage stall | Writes delayed 5 s via a filter (slow USB simulation) | 10 | No timeouts misreported as network errors; completes and verifies |
| Sleep/hibernate | Laptop sleeps for 5 minutes mid-download | 5 (manual, weekly) | Resumes automatically after wake; verified |

### 7.2 Fuzzing targets

| Target | Corpus seed | Budget per night |
| --- | --- | --- |
| Native host message parser and schema validator | Valid protocol messages from section 9.4 of the TRD | 5 min |
| HLS playlist parser | Apple reference streams, generated edge cases | 5 min |
| DASH MPD parser | DASH-IF reference MPDs | 5 min |
| `Content-Disposition` and URL filename parser | RFC 6266 examples, traversal strings | 3 min |
| Torrent metadata (bencode) | Public-domain .torrent files | 2 min |

Any crash, hang over 2 s, or unbounded allocation over 256 MB is filed as a High defect with the minimised input added to the regression corpus.

### 7.3 Evidence

Each nightly run publishes a report artefact: suite, seed, iterations, failures with logs, and checksum results. Gate reviews link the last three reports.

## 8. Defect management

Defects are tracked as GitHub Issues with the `bug` label, a severity label and the test case ID that found them. Severity describes impact on users; priority describes when it gets fixed, and the triage owner sets both.

### 8.1 Severity

| Severity | Definition | Examples | Fix target |
| --- | --- | --- | --- |
| Critical | Data loss, corrupt file reported as complete, security flaw, crash on start, DRM check bypassed | Resume writes bytes from a changed file; host accepts messages from any extension | Before the next build; blocks every gate |
| High | Core feature broken with no workaround, or an NFR target missed by more than 20% | Dynamic segmentation stops splitting; throughput 30% below IDM | Within the current sprint; blocks the next gate |
| Medium | Feature broken with a workaround, or a minor NFR miss | Toast action does not open folder; start time 1.7 s | Before release |
| Low | Cosmetic or minor inconvenience | Misaligned column header; typo | When convenient |

### 8.2 Workflow

1. **New**: filed with build number, steps, expected and actual results, logs, and the TC ID or "exploratory".
2. **Triaged**: severity and priority set within 1 working day; duplicates closed.
3. **In progress**: assigned developer adds a failing automated test first, wherever the defect can be automated.
4. **In review**: fix and test in one PR.
5. **Ready for test**: merged; QA verifies in the next nightly build.
6. **Closed**: verified, or rejected with a reason. A defect that recurs is reopened, not refiled.

### 8.3 Required issue fields

| Field | Content |
| --- | --- |
| Build | Version and commit, from Kasi's About box or CI artefact |
| Environment | Windows version and architecture; browser and version if relevant |
| Steps to reproduce | Numbered; include chaos seed for fault-injection failures |
| Expected / actual | One line each |
| Evidence | Kasi log (`%LOCALAPPDATA%\Kasi\logs`), screenshot or recording, checksum mismatch details |
| Linked | TC ID, requirement ID |

Logs attached to issues must have URLs, cookies and personal paths redacted; Kasi's "Export logs for support" action does this automatically.
