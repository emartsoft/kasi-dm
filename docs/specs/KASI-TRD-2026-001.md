## 1. Introduction

### 1.1 Purpose

This document specifies what Kasi must do and how it will be built. It is the single reference for developers, QA and reviewers, and the baseline for estimating and sprint planning.

### 1.2 Scope

In scope for v1.0:

- A Windows desktop application (Windows 10 22H2 and Windows 11, x64 and ARM64).
- A multi-connection HTTP/HTTPS/FTP download engine with dynamic segmentation and byte-exact resume.
- Browser integration for Chrome, Edge and Firefox through a WebExtension and a native messaging host.
- Capture of unencrypted HLS, DASH and direct media streams.
- A BitTorrent client (magnet links and .torrent files) sharing the same queue and bandwidth limits.
- Queues, a scheduler, auto-categorisation, a bandwidth limiter, a light/dark UI, an installer, a portable build and self-update.

Out of scope for v1.0: macOS and Linux builds, mobile apps, cloud sync of download lists, a site-specific video extractor library (for example yt-dlp-style site parsers), and any handling of DRM-protected content.

### 1.3 Definitions

| Term | Meaning |
| --- | --- |
| Segment | A contiguous byte range of a file fetched by one connection |
| Dynamic segmentation | Splitting the largest unfinished segment during a download so a freed connection can take half of it |
| Probe | The initial request that discovers size, range support and validators (ETag, Last-Modified) |
| Validator | A server value (ETag or Last-Modified) used to confirm a file has not changed before resuming |
| Native messaging host | A small executable the browser launches and talks to over stdin/stdout with length-prefixed JSON |
| HLS / DASH | HTTP Live Streaming (.m3u8) and MPEG-DASH (.mpd) adaptive streaming formats |
| Muxing | Combining separate audio and video streams into one container file, without re-encoding |
| Job | One item in the queue: an HTTP download, a stream capture or a torrent |

### 1.4 Requirement conventions

## 2. Product overview

### 2.1 Vision

Kasi takes over downloads from the browser and finishes them as fast as the connection allows, survives any interruption without losing finished bytes, and puts HTTP files, captured streams and torrents in one queue with one set of limits.

### 2.3 Users

| User | Need |
| --- | --- |
| Everyday user | One-click capture from the browser, fast large files, no lost progress |
| Media saver | Pick a quality from a playing stream and get one playable file |
| Power user | Queues, schedules, bandwidth caps, torrents, per-site rules |
| Low or metered bandwidth user | Night-time scheduling, strict speed caps, resume over unstable lines |

The last group matters in the East African market: unstable connections and off-peak data bundles make scheduling and reliable resume more valuable than raw speed.

### 2.4 Constraints

- Windows only; .NET 10 LTS runtime (supported to November 2028), self-contained in the installer so users need no separate runtime.
- Browser extensions must comply with Manifest V3 (Chromium) and Mozilla Add-on policies, including the bans on circumventing DRM.
- No server-side component is required to download; the update feed is the only network dependency on MartSoft infrastructure.
- FFmpeg is bundled as an external process under its LGPL build to avoid GPL obligations on Kasi's own code.

### 2.5 Assumptions

- Most target servers support HTTP range requests; where they do not, Kasi falls back to a single connection.
- Users install the browser extension; without it, Kasi still accepts pasted links and clipboard capture.
- Code-signing certificates (EV preferred) are procured before the first public build to avoid SmartScreen warnings.

## 5. System architecture

Kasi runs as one long-lived desktop process that hosts a UI-free engine, plus a tiny native messaging host the browser launches. The engine owns every job; the Avalonia UI only observes and sends commands, so closing the window to the tray never interrupts a download.

### 5.1 Process model

| Process | Started by | Role | Lifetime |
| --- | --- | --- | --- |
| `Kasi.exe` | User, Windows startup, or the native host | Engine, scheduler, persistence, UI, tray | Until the user quits |
| `Kasi.NativeHost.exe` | The browser, on first extension message | Relays extension messages to `Kasi.exe` over a named pipe; starts `Kasi.exe` if it is not running | While the browser keeps the port open |
| `ffmpeg.exe` (bundled, LGPL) | Media subsystem | Muxes captured audio and video streams | One per mux task, seconds to minutes |
| `Kasi.Updater` (Velopack) | `Kasi.exe` on exit after an update is staged | Swaps binaries and restarts | Seconds |

The named pipe `\\.\pipe\kasi-<user SID>` has an ACL that admits only the current user, so other users and sandboxed processes cannot inject jobs.

## 6. Download engine design

The engine fetches files in bounded byte-range leases over pooled connections, so it can rebalance work between connections at any moment without aborting a request or opening a new handshake. This is how Kasi matches IDM's dynamic segmentation (KASI-ENG-004 to 006).

### 6.1 Probe without a wasted request

The first connection sends `GET` with `Range: bytes=0-` instead of a separate `HEAD`. The response decides the mode:

| Response | Meaning | Action |
| --- | --- | --- |
| `206` with `Content-Range: bytes 0-N/Total` | Ranges supported, size known | Keep streaming as segment 0; start splitting immediately |
| `200` with `Content-Length` | No range support | Single connection; mark non-resumable (KASI-RES-005) |
| `200` without length (chunked) | Size unknown | Single connection; progress shown as bytes only |
| `3xx` | Redirect | Follow, up to 10 hops; store the final URL for later leases |
| `401`, `403` | Auth required or link expired | Ask the browser for fresh cookies or a refreshed link (6.6) |
| `416` | Range not satisfiable | Re-probe without a range |

The probe also records `ETag`, `Last-Modified`, `Accept-Ranges`, the filename from `Content-Disposition` (RFC 6266, including `filename*`), and the MIME type for categorisation.

### 6.2 Segments and leases

A **segment** is a byte range `[Start, End)` owned by one worker, with a `Written` cursor. A worker never requests its whole segment at once. It requests a **lease**: `Range: bytes=Written-(Written+LeaseSize-1)`, capped at the segment's current `End`.

- Lease size adapts to the worker's speed: two seconds of transfer at its current rate, clamped between 512 KiB and 16 MiB.
- Because every request is bounded, the response ends naturally and the keep-alive connection returns to the pool. The next lease reuses it with no new TCP or TLS handshake.
- A split can shrink a segment's `End` but never cuts into the lease in flight, so no request is ever aborted mid-stream.
- For HTTP/2 hosts, `EnableMultipleHttp2Connections` is on, so parallel segments get separate TCP connections instead of competing on one.

### 6.3 Dynamic segmentation algorithm

When a worker finishes its segment, it splits the largest remaining segment and takes the second half. New workers are added the same way until the configured connection count is reached.

```csharp
// Called under the download's lock when a worker becomes free.
Segment? TrySplit(Download d, long minSplit /* default 1 MiB */)
{
    // Largest amount of work not yet covered by an in-flight lease.
    var victim = d.Segments
        .Where(s => !s.IsComplete)
        .MaxBy(s => s.End - s.LeaseEnd);

    if (victim is null) return null;

    long free = victim.End - victim.LeaseEnd;
    if (free < 2 * minSplit) return null;           // too small to be worth a connection

    long mid = victim.LeaseEnd + free / 2;
    mid = AlignUp(mid, 64 * 1024);                  // keep writes page-aligned

    var fresh = new Segment(start: mid, end: victim.End);
    victim.End = mid;                               // shrink; current lease is untouched
    d.Segments.Add(fresh);
    return fresh;                                   // caller assigns it to the free worker
}
```

Two refinements keep slow connections from holding up the end of a download:

1. **Slow-lane takeover.** If a worker runs below 30% of the median worker speed for 10 seconds and its segment has more than 4 × `minSplit` left, the scheduler splits it early so a faster connection takes the larger share.
2. **Endgame duplication.** When every remaining segment is smaller than `minSplit` and a connection is idle, it may fetch the tail of the slowest segment in parallel. Whichever finishes first wins; the other lease is discarded. This is capped at 2 MiB of duplicate traffic per download.

The connection count ramps up rather than starting all at once: one connection at probe, then one more every 250 ms while throughput keeps rising by at least 5%. This avoids tripping per-IP limits on servers that ban aggressive clients.

### 6.4 Disk I/O

- The target is opened once as `<name>.kasipart` with `File.OpenHandle(..., FileOptions.Asynchronous)` and marked sparse (`FSCTL_SET_SPARSE`), then sized with `SetLength`. Sparse allocation avoids NTFS zero-filling gaps when a far offset is written first.
- Each worker writes through `RandomAccess.WriteAsync(handle, buffer, offset)`. Buffers are 256 KiB, rented from `ArrayPool<byte>.Shared`.
- On completion the sparse flag is cleared, the file is verified (length, optional checksum), Mark-of-the-Web is written to the `Zone.Identifier` stream, and the file is renamed to its final name.
- Free-space check: before starting, and again if a write fails with `ERROR_DISK_FULL`, the job pauses with a "Not enough space" status instead of failing.

### 6.5 Checkpoints and resume

Resume correctness depends on never recording bytes as written before they are on disk.

1. Every 2 seconds, and on pause or shutdown, the engine calls `FlushFileBuffers` on the part file.
2. Only after the flush returns does it write each segment's `Written` cursor to SQLite in one transaction.
3. On resume it reloads the segments, sends a lease request with `If-Range: <ETag or Last-Modified>`, and checks the response. A `206` continues; a `200` means the file changed, so the job restarts and the user is warned (KASI-RES-003).

With a 2-second interval, a power cut costs at most 2 seconds of re-download per connection (KASI-RES-001).

### 6.6 Errors and retry

| Error | Class | Handling |
| --- | --- | --- |
| Timeout, connection reset, DNS failure | Transient | Retry the lease with exponential backoff and full jitter: 1 s, 2 s, 4 s … capped at 60 s, 10 attempts |
| `429`, `503` with `Retry-After` | Throttled | Wait the stated time; reduce this host's connection count by one |
| `500`, `502`, `504` | Transient | Same as timeout |
| `401`, `403` | Auth or expired link | Ask the extension for fresh cookies; if that fails, prompt "Refresh link" (below) |
| `404`, `410` | Permanent | Fail the job with the server message |
| `Content-Range` total differs from the probe | File changed | Restart the job |
| Network offline (NLM event) | Environmental | Pause all jobs; resume automatically when connectivity returns |

**Refresh link.** Signed URLs (cloud storage, file hosts) expire. Kasi stores the referrer page with each job. The "Refresh link" action opens that page in the browser; the extension watches for the next download whose filename and size match, and hands its fresh URL to the paused job, which then continues from its saved bytes.

### 6.7 Bandwidth limiting

Bandwidth is shaped with a two-level token bucket: one global bucket and one optional bucket per job. A worker must take tokens from both before each 16 KiB network read. Bucket capacity is a quarter of a second of the rate, which keeps speed smooth instead of bursty. Torrent traffic draws from the same global bucket through a MonoTorrent rate-limiter adapter (KASI-TOR-005).

### 6.8 Speed and time remaining

Speed is sampled once per second per worker and smoothed with an exponential moving average (α = 0.3). Time remaining is remaining bytes divided by the smoothed total speed, shown only after 3 samples to avoid wild early estimates.

### 6.9 Job lifecycle

&#91;embedded content: Job state machine · 9 states\]

Media jobs pass through Muxing before Verifying; HTTP and torrent jobs go straight to Verifying. A permanent error during Probing (404, 410) also moves the job to Failed. Every transition is persisted before the UI is notified, so the grid never shows a state the database does not hold.

## 7. Media capture subsystem

Media capture turns a playing stream into one playable file: the extension detects the manifest, the user picks a quality, the engine fetches segments in parallel, and FFmpeg joins them without re-encoding. Protected content is detected and refused before any segment is fetched.

### 7.1 Detection

The extension's background service worker observes requests in each tab with `webRequest.onResponseStarted` (read-only; no blocking) and classifies them:

| Signal | Classified as |
| --- | --- |
| URL ends `.m3u8` or `Content-Type: application/vnd.apple.mpegurl` / `application/x-mpegURL` | HLS manifest |
| URL ends `.mpd` or `Content-Type: application/dash+xml` | DASH manifest |
| `Content-Type: video/*` or `audio/*` with `Content-Length` over 1 MB | Direct media |

For each detection the extension sends the manifest URL, the page URL, the page title, request headers (cookies, referrer, origin, user agent) and the tab ID to Kasi. A badge appears on the extension icon and a small overlay button appears over the largest `<video>` element on the page.

Segment requests (`.ts`, `.m4s`) and duplicate manifests from the same tab are suppressed so the panel shows one entry per stream.

### 7.2 Manifest parsing and quality list

`Kasi.Media` parses manifests itself rather than through FFmpeg, so it can show qualities and sizes instantly and control downloading:

- **HLS (RFC 8216).** From the master playlist, read each `EXT-X-STREAM-INF` (bandwidth, resolution, codecs) and `EXT-X-MEDIA` audio and subtitle groups. Estimated size = declared bandwidth × duration from the media playlist.
- **DASH.** From the MPD, read each `AdaptationSet` and `Representation` (bandwidth, width, height, codecs), resolving `SegmentTemplate`, `SegmentList` and `SegmentBase` addressing into a concrete segment URL list.

The panel lists video qualities highest first, each paired with the best matching audio track, plus audio-only options. The default selection is the highest quality at or below the user's "preferred maximum" setting (default 1080p).

### 7.3 Protected content check (KASI-MED-005)

Before any segment is requested, the parser checks for DRM:

| Format | DRM signal | Result |
| --- | --- | --- |
| HLS | `EXT-X-KEY` with `METHOD=SAMPLE-AES` or `SAMPLE-AES-CTR`, or `KEYFORMAT` naming FairPlay, Widevine or PlayReady | Refuse |
| HLS | `EXT-X-KEY` with `METHOD=AES-128` and a plain HTTPS key URI | Allowed: standard transport encryption, decrypted with the served key (KASI-MED-006) |
| DASH | Any `ContentProtection` element with a DRM scheme ID (Widevine, PlayReady, FairPlay, ClearKey) | Refuse |

A refused capture shows "This video is protected and can't be saved" and logs no segment URLs. There is no setting to override this check.

### 7.4 Segment download and assembly

A media job is a parent job whose children are segment fetches. Children reuse the HTTP engine (connection pool, retry, throttling) but each segment is small, so they are fetched whole rather than split.

1. Fetch up to 6 segments in parallel per stream (configurable 1–16), video and audio streams side by side.
2. Write each segment to `%LOCALAPPDATA%\Kasi\media\<job id>\<stream>\<index>`; record completion per segment in SQLite so a resume skips finished ones (KASI-MED-003).
3. When all segments are present, concatenate each stream in order. For fragmented MP4 (DASH, CMAF) the init segment is written first.
4. Run FFmpeg to mux: `ffmpeg -i video -i audio -c copy -map 0:v -map 1:a -movflags +faststart out.mp4`. MKV is used instead when codecs do not fit MP4 (for example VP9 with Opus).
5. Verify the output duration with `ffprobe` against the manifest duration (tolerance 1 second), then delete the segment folder.

FFmpeg runs with a job object that kills it if Kasi exits, and its stderr is captured into the job log.

### 7.5 Live streams (KASI-MED-007)

For HLS without `EXT-X-ENDLIST`, the media playlist is re-polled every target duration. New segments are appended until the user presses Stop or the playlist ends. Muxing runs once at the end.

### 7.6 Limits

Kasi v1.0 does not include site-specific extractors (code that parses a particular site's player to find hidden stream URLs). It captures only what the browser actually requests. This keeps maintenance low and avoids the legal exposure of targeting specific platforms; see section 13.

## 8. BitTorrent subsystem

Torrents run on one embedded MonoTorrent `ClientEngine` and appear in the same grid, queues and bandwidth limits as HTTP jobs. `Kasi.Torrent` is a thin adapter: it maps each `TorrentManager` to a Kasi job and translates engine events into job state changes.

### 8.1 Engine configuration

| Setting | Default | Notes |
| --- | --- | --- |
| Listen port | Random in 49152–65535, chosen at first run | UPnP and NAT-PMP port mapping on; user can fix the port |
| DHT | On | DHT state persisted between sessions for fast bootstrap |
| PEX, local peer discovery | On |  |
| Protocol encryption | Prefer encrypted, allow plain | User can require encryption |
| uTP | On |  |
| Max connections | 200 global, 50 per torrent |  |
| Seeding | Stop at ratio 1.0 or after 24 hours, whichever comes first | KASI-TOR-004 |
| Disk cache | 32 MB | Reduces write amplification on HDDs |

### 8.2 Adding a torrent

1. A magnet link, .torrent file or browser hand-off reaches the orchestrator.
2. For magnets, Kasi fetches metadata (BEP 9) and shows "Fetching file list" until it arrives (timeout 5 minutes, then the job waits in Queued and keeps trying).
3. The add dialog shows the file tree with sizes; the user ticks files to download (KASI-TOR-002). Unticked files get priority `DoNotDownload`.
4. The job joins its queue and starts when the queue allows.

### 8.3 Queue and state mapping

| Kasi state | MonoTorrent state |
| --- | --- |
| Probing | `Metadata` / `Hashing` |
| Downloading | `Downloading` |
| Paused | `Paused` or `Stopped` |
| Verifying | `Hashing` after completion |
| Completed (seeding shown as a sub-status) | `Seeding` |
| Failed | `Error` |

A seeding torrent does not count toward its queue's parallel job limit, so finished torrents never block new downloads.

### 8.4 Bandwidth and resume

MonoTorrent's upload and download rate limiters are replaced with adapters that draw from Kasi's global token bucket (6.7), so a 1 MB/s cap holds across HTTP and torrent traffic together. Fast-resume data is saved on pause and on exit, so restarting Kasi does not re-hash completed torrents.

### 8.5 File associations

On first add of a magnet or .torrent, Kasi asks whether to become the default handler. If the user agrees, it registers the `magnet:` protocol and `.torrent` extension under `HKCU\Software\Classes` (per-user, no admin) and opens the Windows Default Apps page so the user can confirm, as Windows 10 and 11 require (KASI-TOR-006).

## 9. Browser integration

One TypeScript Manifest V3 extension, built separately for Chromium and Firefox, catches downloads and media and sends them to Kasi through the native messaging host. A browser download is cancelled only after Kasi confirms it has taken the job, so a missing or crashed Kasi never loses a download.

### 9.1 Extension structure

| Part | Responsibility |
| --- | --- |
| Background (service worker on Chromium, event page on Firefox) | Download interception, media detection, native port, context menus |
| Content script | Overlay button on `<video>` elements, "Download selected links" floating button, link collection for the picker |
| Popup | Connection status, media found in this tab, quick toggle for interception |
| Options page | Opens Kasi's settings; the extension stores no settings of its own beyond a cache of the rules Kasi pushes |

Permissions: `downloads`, `cookies`, `webRequest`, `contextMenus`, `nativeMessaging`, `storage`, `scripting`, and host permission `<all_urls>`. Each is justified in the store listing; `<all_urls>` is required to read cookies for and observe requests on any site.

### 9.2 Download interception (KASI-BRW-002)

1. `downloads.onCreated` fires. The extension checks the rules Kasi pushed: file extensions, MIME types, excluded sites, and whether the bypass key was held (KASI-BRW-003).
2. If the download matches, the extension **pauses** it (`downloads.pause`) and sends an `addDownload` message with URL, final URL, referrer, filename, MIME type, cookies for the URL (`cookies.getAll`) and the user agent.
3. If Kasi acknowledges within 2 seconds, the extension cancels and erases the browser download.
4. If there is no acknowledgement, or Kasi is not installed, the extension resumes the browser download and shows the status as disconnected (KASI-BRW-006).

Never intercepted: `blob:` and `data:` URLs (they exist only inside the page), downloads triggered by a POST form (the request body cannot be replayed), and incognito windows unless the user enables the extension there.

### 9.3 Native messaging host

`Kasi.NativeHost.exe` is a Native AOT console app (about 3 MB, starts in under 50 ms). The installer registers its manifest per user:

| Browser | Registry key (HKCU) | Allow-list field |
| --- | --- | --- |
| Chrome | `Software\Google\Chrome\NativeMessagingHosts\com.martsoft.kasi` | `allowed_origins`: the Chrome Web Store extension ID |
| Edge | `Software\Microsoft\Edge\NativeMessagingHosts\com.martsoft.kasi` | `allowed_origins`: the Edge Add-ons extension ID |
| Firefox | `Software\Mozilla\NativeMessagingHosts\com.martsoft.kasi` | `allowed_extensions`: the AMO add-on ID |

The host reads 4-byte length-prefixed JSON from stdin, validates it against the schema, and forwards it over the named pipe. If the pipe is absent, it starts `Kasi.exe --tray` and retries for up to 5 seconds. Messages from host to browser stay under Chrome's 1 MB limit; large payloads such as link lists travel only browser-to-host, where the limit is 64 MiB.

### 9.4 Message protocol

Every message has `v` (protocol version), `id` (correlation ID) and `type`. Unknown types and fields are rejected (KASI-NFR-010). The JSON Schema in `docs/protocol/kasi-messages.schema.json` is the single definition of the eleven messages, their fields and their size caps; `Kasi.Ipc` and the extension both validate against it.

| Type | Direction | Purpose |
| --- | --- | --- |
| `hello` | Extension → Kasi | Version handshake; Kasi replies with current rules |
| `rules` | Kasi → extension | Interception rules, bypass key, enabled flag |
| `addDownload` | Extension → Kasi | One intercepted or context-menu download |
| `addBatch` | Extension → Kasi | Links chosen in the picker (KASI-BRW-005) |
| `mediaDetected` | Extension → Kasi | Manifest or direct media found in a tab |
| `captureMedia` | Extension → Kasi | User chose a stream from the popup or overlay |
| `refreshLink` | Kasi → extension | Open the referrer page and watch for a matching download (6.6) |
| `linkRefreshed` | Extension → Kasi | Fresh URL and cookies for a paused job |
| `openSettings` | Extension → Kasi | Show Kasi's settings window (the options page, 9.1); answered with `ack` |
| `ack` / `error` | Both | Result for a correlation ID |

Example `addDownload`:

```json
{
  "v": 1,
  "id": "8f1c2a",
  "type": "addDownload",
  "url": "https://mirror.example.com/files/setup.exe",
  "finalUrl": "https://cdn.example.com/a1b2/setup.exe",
  "referrer": "https://example.com/download",
  "filename": "setup.exe",
  "mime": "application/x-msdownload",
  "userAgent": "Mozilla/5.0 ...",
  "cookies": [{ "name": "session", "value": "...", "domain": ".example.com", "path": "/", "secure": true, "httpOnly": true }]
}
```

Cookies and auth headers are stored with the job, encrypted with Windows DPAPI (current-user scope), so a paused job can resume after a restart. They are deleted when the job completes or is removed, and never written to logs.

### 9.5 Context menus and link picker (KASI-BRW-004, 005)

Right-click offers "Download with Kasi" on links, media and images, plus "Download all links" and "Download selected links" on pages. The link picker opens in Kasi (not in the browser), with filters by extension and a text filter, so large pages with thousands of links stay responsive.

### 9.6 Distribution

The extension is published to the Chrome Web Store, Microsoft Edge Add-ons and Mozilla Add-ons (AMO). Unlike Hamax, Kasi does not ask users to load an unpacked extension in Developer mode; store listings give automatic updates and avoid the browser's developer-mode warnings. The installer opens the right store page for each detected browser at the end of setup.

## 10. Queues, scheduler and categories

Every job belongs to exactly one queue, and a queue decides when its jobs run; categories decide only where files are saved. Keeping the two separate means a user can put Video files in a night-time queue without the category and schedule fighting each other.

### 10.1 Queues (KASI-QUE-001, 002)

| Property | Default (Main queue) | Notes |
| --- | --- | --- |
| Max parallel jobs | 4 | 1–20 |
| Connections per job | 8 | Overrides the global default for this queue's jobs |
| Speed limit | None | Drawn from the global bucket |
| Data quota | None | Stops the queue at the cap and resets daily, weekly or never (KASI-QUE-007) |
| Schedule | None (runs whenever jobs are present) |  |
| Post-completion action | None | Runs when the queue becomes empty |

The runner picks the next job in queue order whenever a slot is free. A job that fails moves to the end of the queue after its retries are used, so one bad link does not block the rest.

### 10.2 Schedules (KASI-QUE-003, 005)

A schedule has a start time, an optional stop time, and days of the week. At start, the queue starts; at stop, its running jobs pause and stay in order.

Wake-from-sleep uses a Win32 waitable timer (`CreateWaitableTimerEx` with `SetWaitableTimer`, resume flag set) armed for the next scheduled start. The setting depends on Windows "Allow wake timers" being on for the active power plan; Kasi checks it and tells the user if it is off.

Missed schedules: if the PC was off at a start time and comes on within the schedule window, the queue starts at once. If the window has passed, it waits for the next one.

A bandwidth profile can be attached to a schedule (KASI-BWL-003), for example 200 KB/s from 07:00 to 23:00 and unlimited overnight, matching off-peak data bundles.

### 10.3 Post-completion actions (KASI-QUE-004)

| Action | Implementation |
| --- | --- |
| Sleep / Hibernate | `SetSuspendState` |
| Shut down | `InitiateShutdown` with `SHUTDOWN_POWEROFF` |
| Exit Kasi | Graceful shutdown with final checkpoint |
| Run a program | User-chosen executable with optional arguments; Kasi passes the completed file path as `%1` |

Power actions show a 60-second countdown toast with Cancel. They are skipped if another queue still has running jobs, unless the user ticks "even if other downloads are running".

### 10.4 Categories (KASI-CAT-001, 002)

When a job is created, rules are checked in order and the first match sets the category and save folder:

1. User rules by domain or URL pattern (for example `*.github.com` → `Downloads\Code`).
2. User and default rules by extension.
3. MIME type from the probe, if the extension is missing.
4. Fallback: "General" in the user's Downloads folder.

| Default category | Extensions | Folder |
| --- | --- | --- |
| Compressed | zip, rar, 7z, tar, gz, xz | Downloads\\Compressed |
| Documents | pdf, doc(x), xls(x), ppt(x), txt, epub | Downloads\\Documents |
| Music | mp3, m4a, flac, wav, ogg, opus | Downloads\\Music |
| Video | mp4, mkv, webm, mov, avi | Downloads\\Video |
| Programs | exe, msi, msix, appx, iso, img | Downloads\\Programs |
| Images | jpg, png, webp, gif, svg | Downloads\\Images |
| Torrents | Torrent jobs | Downloads\\Torrents |

The category sidebar in the UI filters by these, plus status filters (All, Active, Finished, Unfinished).

## 11. Data model and persistence

All state lives in one SQLite database at `%LOCALAPPDATA%\Kasi\kasi.db` (portable build: `.\data\kasi.db`), opened in WAL mode with `synchronous=NORMAL` and `foreign_keys=ON`. Settings live in the same database, so export and import (KASI-SYS-004) is one file.

### 11.1 Tables

| Table | Holds | Write frequency |
| --- | --- | --- |
| `job` | One row per download, capture or torrent: URL, paths, size, state, queue, category | On create and each state change |
| `segment` | Byte ranges and `written` cursors for HTTP jobs | Every 2 s per active job (checkpoint) |
| `media_stream` / `media_segment` | Chosen variants and per-segment completion for captures | On each segment completion, batched every 1 s |
| `job_secret` | DPAPI-encrypted cookies and auth headers | On create and on link refresh; deleted on completion |
| `queue` / `schedule` | Queues, limits, quotas, schedules, post-actions | On user edit |
| `category` / `category_rule` | Categories and matching rules | On user edit |
| `torrent_state` | MonoTorrent fast-resume blobs | On pause and exit |
| `setting` | Key–value settings | On user edit |
| `schema_version` | Migration version | On upgrade |

### 11.2 Schema (core tables)

```sql
CREATE TABLE queue (
    id              INTEGER PRIMARY KEY,
    name            TEXT    NOT NULL UNIQUE,
    max_parallel    INTEGER NOT NULL DEFAULT 4,
    connections     INTEGER,                    -- NULL = global default
    speed_limit_bps INTEGER,                    -- NULL = unlimited
    quota_bytes     INTEGER,
    quota_reset     TEXT CHECK (quota_reset IN ('daily','weekly','never')),
    post_action     TEXT NOT NULL DEFAULT 'none',
    sort_order      INTEGER NOT NULL
);

CREATE TABLE category (
    id          INTEGER PRIMARY KEY,
    name        TEXT NOT NULL UNIQUE,
    folder      TEXT NOT NULL,
    is_builtin  INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE job (
    id              TEXT PRIMARY KEY,           -- UUIDv7, sortable by creation time
    kind            TEXT NOT NULL CHECK (kind IN ('http','ftp','media','torrent')),
    url             TEXT NOT NULL,
    final_url       TEXT,
    referrer        TEXT,
    file_name       TEXT NOT NULL,
    folder          TEXT NOT NULL,
    total_bytes     INTEGER,                    -- NULL = unknown
    done_bytes      INTEGER NOT NULL DEFAULT 0,
    state           TEXT NOT NULL,              -- see section 6.9
    error           TEXT,
    etag            TEXT,
    last_modified   TEXT,
    resumable       INTEGER NOT NULL DEFAULT 1,
    connections     INTEGER,
    speed_limit_bps INTEGER,
    checksum_algo   TEXT,
    checksum        TEXT,
    queue_id        INTEGER NOT NULL REFERENCES queue(id),
    queue_pos       REAL    NOT NULL,           -- fractional index for cheap reordering
    category_id     INTEGER REFERENCES category(id),
    created_utc     TEXT NOT NULL,
    completed_utc   TEXT
);
CREATE INDEX ix_job_queue ON job(queue_id, state, queue_pos);
CREATE INDEX ix_job_created ON job(created_utc DESC);

CREATE TABLE segment (
    job_id   TEXT    NOT NULL REFERENCES job(id) ON DELETE CASCADE,
    idx      INTEGER NOT NULL,
    start    INTEGER NOT NULL,
    "end"    INTEGER NOT NULL,                  -- exclusive
    written  INTEGER NOT NULL,                  -- bytes flushed to disk from start
    PRIMARY KEY (job_id, idx)
) WITHOUT ROWID;

CREATE TABLE job_secret (
    job_id   TEXT PRIMARY KEY REFERENCES job(id) ON DELETE CASCADE,
    payload  BLOB NOT NULL                      -- DPAPI-protected JSON: cookies, headers
);
```

### 11.3 Write path

Checkpoints are the hottest writes. A single `CheckpointWriter` background task collects segment updates from all workers through a `Channel<T>` and commits them in one transaction every 2 seconds, after the matching `FlushFileBuffers` calls (6.5). This keeps SQLite to one writer and well under 1 ms of commit time per cycle at 20 active jobs.

### 11.4 Migrations and retention

- Migrations are numbered SQL scripts embedded in `Kasi.Data`, applied in one transaction at startup; the database is copied to `kasi.db.bak` first.
- Completed jobs stay in history until the user clears them or the optional auto-clean (off by default) removes entries older than N days.
- `VACUUM` runs at most monthly, on exit, when more than 25% of pages are free.

Grid columns (default): File name, Size, Progress, Speed, Time left, Status, Date added, Category. Columns can be shown, hidden, resized and reordered, and the layout is saved (KASI-UI-007).

The job list uses Avalonia's open-source `DataGrid` with row virtualisation, and job view models update through a 250 ms batched dispatcher tick rather than per-byte events, keeping the UI under 16 ms per frame at 10,000 rows (KASI-NFR-006). The window uses FluentAvalonia's `AppWindow` with Mica on Windows 11 (acrylic fallback on Windows 10), and Avalonia's `TrayIcon` for the tray menu.

### 12.3 Interaction rules

- Closing the main window minimises to the tray; downloads continue. Quit is explicit, from the tray or File menu.
- A browser hand-off shows the Add dialog only if "Ask before each download" is on (default on); otherwise the job starts silently with a toast.
- Double-clicking a completed job opens the file; a running job opens its details.
- Every destructive action (Delete with file) asks for confirmation and offers "Don't ask again".
- Keyboard: Ctrl+N add, Space pause/resume, Delete remove, Ctrl+F search, F5 refresh link. Every control has an automation name for screen readers (KASI-UI-010).

### 12.4 Notifications

Windows toast notifications through the WinRT notification API (app targets net10.0-windows10.0.19041.0), with actions: Completed (Open, Open folder), Failed (Retry, Details), Queue finished (summary of files and total size), and the power-action countdown (Cancel). Users can mute each type. The AUMID is registered by the installer so toasts persist in Action Center.

## 13. Security, privacy and legal compliance

Kasi handles cookies, runs downloaded content near the user and accepts input from browsers, so its main risks are job injection, credential leakage and unsafe files. Each threat below has a control and a requirement that tests it.

### 13.1 Threat model

| Threat | Control | Requirement |
| --- | --- | --- |
| A malicious web page or extension injects jobs | Host manifest allow-lists only Kasi's store extension IDs; pipe ACL limits to the current user; schema validation rejects unknown messages | KASI-NFR-010 |
| Another local process reads the pipe or database | Pipe and `%LOCALAPPDATA%\Kasi` are user-scoped; secrets DPAPI-encrypted | KASI-NFR-010 |
| Cookie or token leakage | Cookies sent only to the domain and path they belong to, never across redirects to other hosts; redacted from logs and crash reports | KASI-NFR-013 |
| Path traversal in filenames (`..\`, reserved names like `CON`) | Filenames sanitised: strip path separators and control characters, map reserved names, cap at 200 characters | KASI-ENG-003 |
| Downloaded malware | Mark-of-the-Web on every file; optional AMSI scan; Kasi never auto-runs a downloaded file | KASI-CAT-003, 004 |
| Man-in-the-middle | TLS validation always on; certificate errors shown per job with no global bypass | KASI-NFR-011 |
| Tampered update | Velopack packages signed; signature and SHA-256 checked before applying; update feed over HTTPS only | KASI-NFR-012 |
| Malformed manifests or torrents (parser attacks) | Parsers fuzzed in CI; size limits on manifests (10 MB) and torrent metadata (50 MB) | Section 15 |
| Decompression or disk-fill abuse | Free-space check before and during writes; job pauses rather than filling the disk | KASI-ENG-008 |

### 13.2 Privacy

Kasi collects nothing by default. The only outbound call MartSoft receives is the daily update check, which sends the current version and architecture. Opt-in crash reports contain the exception, stack trace, OS version and Kasi version, and are scrubbed of URLs, file paths, usernames and cookies before sending (KASI-SYS-006). This keeps Kasi outside the scope of personal-data processing under Kenya's Data Protection Act 2019 and GDPR, provided crash reports stay anonymous.

### 13.3 Content and copyright

- Kasi refuses DRM-protected streams with no override (section 7.3). Circumventing DRM is prohibited under the Kenyan Copyright Act, 2001 (technological protection measures), the US DMCA section 1201 and the EU Copyright Directive, and would get the extension removed from browser stores.
- No site-specific extractors ship in v1.0 (section 7.6).
- The licence agreement and first-run screen state that users are responsible for having the right to download content and for complying with sites' terms.
- The torrent client includes no search or index of content.

## 14. Packaging, updates and deployment

One CI pipeline produces a signed per-user installer, a portable zip and delta update packages for x64 and ARM64 from the same commit. Users never need admin rights to install or update.

### 14.1 Release artefacts

| Artefact | Contents | Target size |
| --- | --- | --- |
| `Kasi-Setup-x64.exe`, `Kasi-Setup-arm64.exe` | Velopack installer: self-contained .NET 10 app, native host, FFmpeg, extension store links | Under 60 MB (KASI-NFR-020) |
| `Kasi-Portable-x64.zip`, `Kasi-Portable-arm64.zip` | Same binaries plus a `portable.marker` file; settings and database in `.\data` | Under 70 MB |
| `*-delta.nupkg` | Binary diff from the previous release | Typically 2–10 MB |
| `*-full.nupkg` | Full package for users more than one version behind | Matches installer |
| `kasi-extension-chromium.zip`, `kasi-extension-firefox.zip` | Store submission builds | Under 1 MB |

### 14.2 Installer behaviour

- Installs per user to `%LOCALAPPDATA%\Kasi` with no UAC prompt.
- Registers native messaging host manifests for Chrome, Edge and Firefox (9.3), the toast AUMID, Start menu shortcut and uninstall entry.
- Offers optional startup with Windows (KASI-SYS-003) and file associations (8.5).
- Opens the extension store page for each browser it detects.
- Uninstall removes binaries, registry entries and host manifests, and asks whether to keep the download history and settings.

The portable build detects `portable.marker`, skips all registry writes except native messaging (which the user can register from Settings, since browsers require registry entries to find the host), and updates itself in its own folder.

### 14.3 Self-update (KASI-SYS-002)

1. Daily, and at startup if the last check was over 24 hours ago, Kasi fetches `releases.<channel>.json` from the update feed over HTTPS.
2. If a newer version exists, it downloads the delta (or full) package in the background using its own engine at low priority.
3. Velopack verifies the package signature and hash, stages it, and applies it on next exit or when the user clicks "Restart to update". Active downloads checkpoint first.
4. Channels: `stable` (default) and `beta` (opt-in).

### 14.4 Code signing

All executables, DLLs built by MartSoft, installers and packages are signed with an EV code-signing certificate (or Azure Trusted Signing) and timestamped. This is required to avoid SmartScreen "unrecognised app" warnings on first release.

### 14.5 CI/CD pipeline

1. On pull request: build, unit tests, integration tests against local test servers, extension lint and tests, coverage gate (80% engine).
2. On merge to `main`: everything above plus fault-injection and fuzz runs (time-boxed to 20 minutes), then a signed beta build published to the `beta` channel.
3. On a version tag: signed stable build, release notes generated from merged pull requests, artefacts uploaded to the update feed and the MartSoft download page, extension packages submitted to the three stores.

### 14.6 Hosting

The update feed and installers are static files on object storage behind a CDN (for example Cloudflare R2 or Azure Blob with Azure Front Door). No application server or database is needed on the MartSoft side.

## 15. Testing strategy

The engine is tested against controllable local servers that inject failures on demand, because public mirrors cannot reproduce dropped connections, changed files or throttling reliably. Every P1 requirement maps to at least one automated test (Appendix A).

### 15.1 Test levels

| Level | Scope | Tools | Runs |
| --- | --- | --- | --- |
| Unit | Segmentation and split logic, lease sizing, token bucket, filename sanitising, manifest parsers, rule matching, state machine | xUnit, FluentAssertions, FsCheck (property tests) | Every PR |
| Integration | Engine against local HTTP/1.1, HTTP/2, FTP and range-less servers; SQLite checkpoints; FFmpeg muxing on sample streams; MonoTorrent with a local tracker and seeders | Kestrel test server, Testcontainers (vsftpd, opentracker) | Every PR |
| Fault injection | Connection resets mid-lease, 503 bursts, slow lanes, file changed on server, disk full, process kill, simulated power loss | Custom "chaos" middleware in the test server; process-kill harness | On merge |
| Fuzz | Native host message parser, HLS and DASH parsers, `Content-Disposition` parser, torrent metadata | SharpFuzz | On merge, time-boxed |
| Extension | Interception, rule matching, media detection, native port reconnect | Vitest (unit), Playwright with Chromium and Firefox (end-to-end) | Every PR |
| UI | Main flows: add, pause, resume, delete, queue scheduling, settings | Avalonia.Headless for view-model and view tests; FlaUI (via UI Automation) on Windows runners | Nightly |
| Performance | Throughput vs IDM, 1 Gbit/s aggregate, start time, memory, 10,000-row grid | BenchmarkDotNet, custom harness, PerfView | Weekly and before release |
| Compatibility | Windows 10 22H2, Windows 11 x64 and ARM64; Chrome, Edge, Firefox, Firefox ESR | Hyper-V and Azure VM matrix | Before release |

### 15.2 Key test scenarios

| Scenario | Expected result | Requirements |
| --- | --- | --- |
| 4 GB file, 16 connections, one connection killed every 10 s | Completes; checksum matches; idle connections near zero | KASI-ENG-005, RES-004 |
| Process killed at 60% | Resumes at 58–60% | KASI-RES-001, 002 |
| VM hard power-off at 40% | Database opens; resumes from last checkpoint; checksum matches | KASI-RES-002, NFR-009 |
| Server file replaced between sessions | Detected via `If-Range`; job restarts with warning | KASI-RES-003 |
| One connection throttled to 50 KB/s, others 10 MB/s | Slow-lane takeover splits its segment within 10 s | KASI-ENG-005 |
| Signed URL expires at 50% | Refresh link continues from saved bytes | KASI-ENG-010 |
| SAMPLE-AES and Widevine test streams | Refused; zero segments fetched | KASI-MED-005 |
| Global limit 1 MB/s with 2 HTTP jobs and 1 torrent | Combined rate within 5% of 1 MB/s | KASI-BWL-001, TOR-005 |
| Queue scheduled 02:00–05:00 with PC asleep | PC wakes, queue starts, stops at 05:00 | KASI-QUE-003, 005 |
| Kasi not running when browser download starts | Host launches Kasi; download taken within 5 s; if Kasi fails, browser resumes its own download | KASI-BRW-002, 006 |

### 15.3 Release criteria

- All P1 requirements pass; no open Critical or High defects.
- Throughput within 5% of IDM on the benchmark suite (KASI-NFR-001).
- 7-day beta with at least 50 users and a crash-free session rate of 99.5% or more.
- Extension approved in all three stores.
