# 0023. Desktop shell, browser handlers and single instance

- Status: Proposed (start-up order, single instance and the UI batch dispatcher in M2.8a; the browser protocol handlers and the Settings skeleton in M2.8b; tray, dialogs and picker follow in 2.8c to 2.8e, which finish this ADR)
- Date: 2026-10-22
- Requirements: KASI-SYS-005, KASI-NFR-003, KASI-NFR-006, KASI-NFR-010
- Related: `docs/plans/m2-8.md` (sections 2.1, 2.3, 2.4, decision 1); ADR 0016, ADR 0017, ADR 0019

## Context

The native messaging host starts `Kasi.exe --tray` and gives up on the pipe after 5 s (ADR 0017), and it does so again on every reconnect. The pipe therefore has to be open before the engine and the UI exist, a second launch has to be silent and instant, and a URL given to a second launch has to reach the running one. The browser pipe cannot carry that: it demands a `hello` from a registered host and has no "open this URL" message.

## Decision

**Start-up order** (`Kasi.App/Startup/AppStartup.cs`, called by `Program.Main`, which stays `[STAThread]` and a `WinExe`): (1) parse the arguments; (2) take the per-user lock, the mutex `Local\Kasi-<SID>` (session namespace, not `Global\`); (3) if another instance holds it, send the hand-off and exit 0 at once, building nothing; (4) start the `KasiPipeServer`, then the hand-off server; (5) only then build and start the generic host and the engine; (6) start Avalonia, with no window when `--tray`. A failed pipe start (the name is owned by something else) exits 1; `FirstPipeInstance` makes a squatter fail loudly. Until PR 2.8b the browser handler answers `hello` with `rules` that intercept nothing (`enabled: false`, empty lists) and everything else with `error INTERNAL`, so a browser falls back to its own download instead of waiting for an ack. A test holds the host build and checks that the pipe answers `hello` meanwhile.

**Hand-off** (plan decision 1, the recommended option): a second per-user pipe `kasi-<SID>-open`, one JSON line `{"args":[...]}` per launch, so protocol v1, the extension and the host stay untouched and the browser pipe keeps one purpose. The second process connects (waiting up to 5 s for a first instance that is still starting), checks that the pipe is served by a process of the same user, writes the line, waits for the pipe to drain and exits 0 whether or not that worked. The server accepts at most 64 KiB and 64 arguments, cuts a client off after 5 s and drops anything that is not the contract without an answer.

**Where it lives.** `HandOffServer` and `HandOffClient` are in `Kasi.Ipc`, not in `Kasi.App`. `PipeSecurityFactory` (current user allow, NETWORK deny, nothing else, owner set to the user) stays `internal`, so there is one place that decides pipe access, one test project that reads the access list back and creates a second Windows user to prove the denial (`CrossUserPipeTests` now covers both pipes), and `Kasi.App` cannot create a pipe with a different list by accident. The alternative, making the factory public, widens the library's surface for one caller.

**Arguments** (`AppArguments`): URLs to add and `--tray`, nothing else. A URL is taken only when it is absolute, http, https or ftp, at most `IpcLimits.UrlLength` (8,192) characters and free of control characters; everything else is counted, not kept. The same parser reads `Main`'s arguments and the hand-off. URLs may hold tokens: logs carry counts only.

**Delivery to the UI.** Requests go through `LaunchRelay`, which holds them until the UI attaches (they arrive before it exists) and then hands them to the UI thread. A request with URLs goes to an `IAddDownloadService` and raises the window; a bare `--tray` does nothing (the host sends it on every reconnect); a bare launch raises the window. The interface is what the Add dialog (PR 2.8d) will implement; until then `MainWindowViewModel` keeps the URLs in `PendingAddUrls`.

**`UiBatchDispatcher`** coalesces updates by key and applies the set once per period (250 ms in the app) through `PeriodicTimer(period, TimeProvider)`, so tests drive it with `FakeTimeProvider` and assert no wall-clock time. A failing apply is logged by exception type only and the loop continues.

**Test seam.** The environment variable `KASI_ENDPOINT_SUFFIX` appends to the lock and both pipe names so a test instance never meets a Kasi the developer has open. It cannot redirect the browser host (which uses the fixed names), so it adds no attack surface worth a build switch.

**Browser protocol handlers** (M2.8b, `Kasi.App/Browser`). `BrowserMessageHandler` is the only place that knows the browser messages. It answers `hello` with `rules` built from `BrowserSettings` (a populated default, because an empty list intercepts nothing; every list is cleaned to the protocol caps by `Normalized()` on the way to the pipe and to the disk) and sends `minSizeBytes` only to an extension whose `hello.extensionVersion` is at least `IpcProtocol.MinSizeExtensionVersion`, remembered per connection. A settings save pushes fresh `rules` to every connected host, each with its own minimum-size decision. `addDownload` and `addBatch` are acknowledged when they are **queued** in `BrowserIntake`, which is the "add dialog queued" case of TRD 9.2 and ADR 0019: the ack never waits for a person, and the pipe, which opens before the UI exists, can accept at once. The queues are bounded (100 downloads, 8 batches); a full queue answers `error INTERNAL`, which makes the extension leave the file to the browser. A request id is idempotent for ten minutes (a bounded map of 1,024 ids): the same id again gets the same ack and is not queued twice; a refused request is not remembered, so a retry can succeed. `openSettings` shows the Settings window on the asked section (default Browser). `mediaDetected`, `captureMedia` and `linkRefreshed` get `error INTERNAL` until M3 and the refresh dialog; `rules` and `refreshLink` sent by a browser are `INVALID_MESSAGE`. Held downloads and batches are classes that print only their type, since they carry URLs and cookie values; nothing in the handler logs more than the message type names.

**What 2.8b leaves for 2.8d, on purpose.** There is no engine in the composition root yet, so a queued download waits in `MainWindowViewModel.PendingBrowserDownloads` for the Add dialog and nothing creates a job: cookies therefore stay in memory with the pending request and reach `job_secret` when the dialog creates the job (the engine already stores them there, M1.10). The plan's setting "Show the Add dialog for browser downloads" (decision 5) comes with the direct path in 2.8d, since until then the dialog is the only path. `refreshLink` sending belongs with the refresh dialog (2.8d). The Settings window is a skeleton: General has a placeholder, Browser edits the rules; settings live in one JSON file (`%LOCALAPPDATA%\Kasi\browser-settings.json`, written through a temporary file and a replace, defaults on a missing or unreadable file) until the general settings store exists.

**Engine hosting** (M2.8d-1, `Kasi.App/Engine`). The composition root registers the connection factory, the repositories, the checkpoint writer, the bandwidth limiter, the `DownloadEngine` and `JobService` as singletons; building the container touches no disk. `EngineLifetime` is the one hosted service: when `host.Start()` runs (after both pipes are open) it migrates the database, starts the checkpoint writer and the engine, and on stop stops the engine and flushes the writer. `IJobService` is the UI's only way into the engine (list, categories, queues, add with a duplicate resolution, pause, resume, cancel, and the engine's events); dialogs and the job list depend on it, so they are tested against a fake. An add without a resolution reports a duplicate and adds nothing (the engine's own check, serialised with the add); `AutoRename` adds under the suggested name; `Resume` continues the existing job. The folder is the category's folder under the user's Downloads folder unless the caller names one; the queue position is the last one plus one. Only http, https, ftp and ftps links are accepted. The data folder is `%LOCALAPPDATA%\Kasi` (`KASI_DATA_DIR` moves it; `CompositionRoot.Build(args, dataFolder)` is the seam tests use so parallel hosts never share a database file).
- *The job list* (`JobListViewModel`, `JobRowViewModel`). It loads the stored jobs, then follows the engine: added, removed and state events are applied at once on the UI thread; progress goes through `UiBatchDispatcher` (latest per job, every 250 ms). A row shows the file name, never the URL. The window is a plain `Avalonia.Controls.DataGrid` (MIT, in the stack list) with four columns; sorting, selection actions and the full layout of the wireframes belong to the main-UI work after M2.8.

**Add dialog and duplicate prompt** (M2.8d-2). `AddCoordinator` is where a link becomes a job: a second launch with URLs and a browser download both arrive there (the pipe's intake delivers to it, on any thread), and one Add window is open at a time, the rest in the order asked. A browser download opens the window pre-filled (final URL, the extension's file name, referrer, cookies and user agent) unless the Settings box "Show the Add download window" is off (decision 5 of the plan, on by default), in which case it is added at once to the first queue and the General category, or the site's remembered one, and a duplicate gets a new name. `AddDownloadViewModel` holds the TRD 12.1 fields and maps them one to one onto `NewDownload` (a test sets every field and reads it back); it validates the link (http, https, ftp, ftps), the file name (what `FileNameSanitiser` would leave unchanged), the connection count (1 to 32) and the checksum (an algorithm and a hex value of the right length, or neither). On an add the engine's own duplicate check decides: a conflict is shown in the prompt (`DuplicatePromptViewModel`, which offers exactly the engine's `AvailableActions` and names the file a rename would use) and the answer is sent with the same request; backing out leaves the Add window open. The cookies and user agent go to `job_secret` right after the job row exists and before it starts, and the request and draft print only their type name. "Remember category and folder for this site" writes `site-defaults.json` next to the database (host to category and folder, matched case-insensitively; an unreadable file is an empty memory) and pre-selects them the next time.

**Link picker** (M2.8d-3, KASI-BRW-005). A queued `addBatch` opens `LinkPickerWindow` through the same coordinator and the same one-window-at-a-time chain as the Add dialog, so the main window is no longer raised for it. `LinkPickerViewModel` builds one row per link (file name from the extension's hint, else from the address) and offers a text filter (matches the address and the file name, any case), a file-type filter (the most frequent types first, at most 50), Select shown, Select none (which clears hidden links too), a destination (category, queue, folder) and Start now. The shown list is replaced as a whole on each filter change and the window uses a `ListBox`, which virtualises rows, so a page of 100,000 links costs one list rebuild per change and only the visible rows as controls; a test builds, filters and selects 100,000 links against a generous bound. Add creates one job per ticked link in page order, each with the batch's referrer, cookies and user agent (stored as the job secret by `JobService`); a duplicate gets a new name rather than a prompt per link, and a link that cannot be added is counted and shown while the rest still go in, leaving the window open. Rows and the view model print only their type, since an address can carry a token.

## Consequences

- A second launch costs one process start plus one pipe write; it never builds a host or a UI.
- With `--tray` and no tray icon yet (PR 2.8c), a hidden Kasi can be ended only from Task Manager; 2.8c adds the tray and Quit before this ships to users.
- The synchronous hand-off client and the pipe start keep `Main` on the STA thread without an `await`. The pipes are closed by process exit (tests dispose the `AppSession`).
- Start-up now runs the migrations before the first window (the pipes are already open, so the browser host is not kept waiting). A database newer than this build, or one that fails its integrity check, stops the host: the app then exits instead of showing a list that cannot be trusted. A friendlier error window is part of the main-UI work.
- Still to decide in this ADR when the rest lands: what Quit does with browsers connected, toasts, (2.8c) and the refresh-link dialog (2.8d-4).
