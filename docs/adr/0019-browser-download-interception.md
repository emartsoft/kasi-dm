# 0019. Browser download interception

- Status: Accepted (rule semantics in M2.4a; the hand-off budget and bypass detection in M2.4b; the end-to-end harness in M2.4c)
- Date: 2026-10-21
- Requirements: KASI-BRW-002, KASI-BRW-003, KASI-NFR-010
- Related: TRD 9.2 and 9.4; `docs/plans/m2-4.md`; ADR 0016, ADR 0018

## Context

`rules` carried extension, MIME and site lists with no stated semantics, and no size field although BRW-002 names a minimum size. Kasi and the extension must decide alike, and the strict parsers on both sides reject any field the other side does not know.

## Decision

**Rule semantics** are written into TRD 9.2 and `docs/protocol/README.md` and implemented as pure functions in `extension/src/shared/rules-match.ts`: a download is taken when rules exist and are enabled, it is not excluded, and its extension or its MIME type matches. Extensions are lowercase without a dot and match the end of the file name; MIME types are exact or `type/*`; an empty list matches nothing (never take what was not asked for); an excluded site covers its subdomains and is tested against the URL, the final URL and the referrer. `blob:`, `data:`, other schemes, URLs over 8,192 characters, another extension's downloads and private windows (unless allowed) are never taken.

**Minimum size** is an optional `minSizeBytes` (integer, 0 to 2^53-1) on `rules`. Because a strict parser rejects the whole message, Kasi sends it only when `hello.extensionVersion` is 0.2.0 or later (`IpcProtocol.MinSizeExtensionVersion`), and `v` stays 1. The extension is released as 0.2.0 with the field. A download of unknown size is intercepted; Kasi learns the size itself and the user can decline in its dialog.

**Acknowledgement** of `addDownload` means durable acceptance (the job exists or the add dialog is queued), not the user's answer in a dialog, so the 2 s window is not tripped by a slow click.

**Hand-off budget** (M2.4b, KASI-BRW-002, BRW-006). A matching download is paused first and then handed to Kasi in two phases. The *ready* phase applies only when the native port is not connected: the extension asks the port to reconnect now and waits at most 6 s (the host's 5 s launch window plus the `hello`/`rules` round trip) for Kasi's `rules`. The *ack* phase waits `rules.ackTimeoutMs` (default 2 s), counted from posting `addDownload`. A port is *connected* only after `rules`; the host's `APP_NOT_RUNNING` and `APP_NOT_INSTALLED` errors, and a port that dies before saying anything (no host registered), mean unreachable, and the last two skip the wait entirely so a machine without Kasi never slows a download. On an ack the extension cancels, removes the part file where the browser leaves one (Firefox) and erases the browser download; in every other case it resumes it (unless the user cancelled it meanwhile) and shows a red `!` badge until `rules` arrive again.

**Late ack.** An ack that arrives after the timeout, within 30 s, cancels and erases the browser download if it is still in progress, so the file is not downloaded twice; if its bytes are already complete nothing is done and Kasi's duplicate prompt (ENG-013) handles it. A request id is never retried.

**Bypass key.** `downloads.onCreated` cannot see the keyboard, so a content script (all frames, `document_start`) reports trusted pointer and Enter events with Alt, Ctrl or Shift held; the background keeps the last one with the SHA-256 of the link (never the link) and, after pausing, honours it when the key equals `rules.bypassKey` and it is fresh: 15 s when the link equals the download's URL, final URL or a redirect hop, otherwise 3 s, after a 100 ms grace when no record exists yet. Downloads that start outside a page cannot be bypassed by key; this is documented, not worked around (a native key-state query in the host was rejected: the key is usually released before `onCreated`).

**Exclusions** are decided before the pause: non-web schemes, over-long URLs, other extensions' downloads, private windows unless allowed, a missing host permission, and POST-form downloads, which `webRequest` marks because a `DownloadItem` has no method (the mark follows redirects, lasts 30 s, and is stored as hashes).

**Cookies** are read only after a match, for the URL and the final URL, with the cookie's domain passed unchanged (the leading dot is the only host-only signal), values over 4,096 characters dropped and at most 200 sent. They are held for one hand-off and never logged or stored.

**End-to-end harness** (M2.4c). `tests/Kasi.BrowserHarness` runs the real `KasiPipeServer` on the real per-user pipe as a stub Kasi (rules on `hello`; `addDownload` answered with an ack, an error or silence), the test pages, `Kasi.TestServer` in process and a small admin API the Node side reads. The real Native AOT host sits between browser and pipe. Vitest (`npm run test:e2e`, `vitest.e2e.config.ts`) drives Playwright's Chromium and, through a small WebDriver client over `fetch`, Firefox with geckodriver; both run the same scenarios (`tests/e2e/scenarios.ts`) and assert on what the stub received, the files the browser kept (SHA-256) and the popup and badge text. No dependency was added.

- *Registration.* The browsers read only their own HKCU key, so it cannot be test-private: the run saves the key's previous default value, points it at a manifest in a temp folder and restores it in `afterAll` and on process exit. It runs only with `KASI_E2E=1`; a Kasi or harness that already owns the pipe makes the harness refuse to start (`FirstPipeInstance`). The host name and pipe name are not configurable. `Register-NativeHost.ps1` gained a `Chromium` target (`HKCU\Software\Chromium\NativeMessagingHosts`, confirmed by the run).
- *Extension id.* Instead of injecting a `key` through the build (the plan's `KASI_E2E_KEY`), the Chromium helper copies `dist/chromium` into a temp folder and adds a freshly generated public key to that copy, so no key ever appears in a build output and `check-manifests` needs no exception. The Firefox id is fixed in its manifest.
- *Launch chain (TC-BRW-002).* The harness copy placed next to the host as `Kasi.exe` is what the host starts with `--tray`; it opens the pipe after a delay. Because a fresh install intercepts nothing, the test first lets one Kasi run so the rules are cached in the profile, ends the browser and Kasi, then starts the browser again on the same profile with a Kasi that needs 3 s: the extension must wait for it. "Kasi missing" renames `Kasi.exe`, so the host answers `APP_NOT_INSTALLED`.
- *Spike results.* Playwright's download handling does not stop `downloads.onCreated`; an extension `cancel` is reported as a cancelled download. Branded Chrome and Edge are not automated (they ignore `--load-extension`); Playwright's Chromium stands in for both, and they stay in the release-candidate checklist (`docs/qa/browser-interception.md`). Alt-click is the browser's own "download link", so Ctrl and Shift are tried on a button whose script starts the download (a `<a download>` link opened a tab instead, with no download). A slow server is a harness redirect that answers after 3 s (a chaos profile can only be selected by a request header, which a click cannot add).
- *Firefox, as far as WebDriver goes.* Install is `moz/addon/install` with `temporary: true`; the popup is opened at a fixed `moz-extension://` address (the internal uuid is set by a profile pref); Alt, Ctrl and Shift clicks use the W3C actions API. Not possible through WebDriver, and so not asserted: the toolbar badge text, a revoked host permission (unit-tested) and private windows. Run locally with geckodriver 0.37.1 and Firefox: Firefox does grant `<all_urls>` to a WebDriver-installed MV3 add-on. WebDriver refuses to navigate to `moz-extension://`, so the popup is opened from the chrome context (`geckodriver --allow-system-access`, `gBrowser.addTab` with the system principal). Firefox reports a DownloadItem's referrer as the whole page address (Chromium: the origin), and a file small enough to finish before the extension reacts is simply left to the browser, so the Firefox scenarios download 30 MB files. The launch-chain case is Chromium only: Firefox drops a temporary add-on's storage between sessions, so a restarted browser has no cached rules and intercepts nothing. One Firefox run in four showed a single timeout in the 3 s slow-server bypass case that did not repeat in five further runs; it is not understood.
- *Finding (Firefox).* Firefox reports a paused download as `state: interrupted` (error `USER_CANCELED`) with `paused` and `canResume` true. `resumeIfPaused` only resumed `in_progress` items, so on Firefox every failed or bypassed hand-off left the download paused with an empty target and a `.part` file: the browser lost it. It now resumes when `paused` is set, `canResume` is not false and the state is not `complete`; a download the user cancelled has `canResume` false.
- *Finding.* A paused download whose bytes were all in still completes, and `cancel` does nothing to a completed download. The first runs left the file on disk when the ack came after that point. `removeFile` now runs after `cancel` in both browsers (it was Firefox only).
- *Known gap, closed in M2.5a (ADR 0020).* The host reconnects to a restarted Kasi on its own and keeps the browser's port, so after the user quits Kasi the extension still counts as connected, and a download started then gets only the 2 s ack window while the host launches Kasi (up to 5 s). It falls back to the browser's copy and relies on the late-ack handling. Candidate for M2.2/M2.8 together with plan G8: the host could close the port with `APP_NOT_RUNNING` when it loses the pipe.

## Consequences

- A fresh Kasi must push a populated default list, since an empty one intercepts nothing.
- The M2.8 `rules` sender must read `hello.extensionVersion` before adding `minSizeBytes`, and the `addDownload` handler must ack on acceptance.
- Later fields follow the same rule: optional, capped, sent only to peers that declared a version able to read them.
